# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, Codex, Cursor, Copilot, Gemini CLI and any other tool that reads `AGENTS.md`) when working with code in this repository.

**About these instruction files:** `AGENTS.md` is the single source of truth — here at the root and in `apps/client/` and `apps/server/` (the closest one to the files you're editing adds workspace-specific rules on top of this one). Each `CLAUDE.md` next to them only imports its `AGENTS.md` (`@AGENTS.md`) so Claude Code loads the same content. **Edit `AGENTS.md`, never the `CLAUDE.md` stubs**, or the two will drift apart.

**Project procedures:** two repeatable procedures live as Markdown files in `.claude/commands/` — `log-progress.md` (append a `progress.txt` entry) and `bump-version.md` (cut a release). Claude Code runs them as `/log-progress` and `/bump-version`; any other agent should open the file and follow its steps by hand. "Run `/log-progress`" anywhere in this repo's docs means exactly that.

## Project

Reson8 is a self-hosted voice and text communication platform (TeamSpeak-3-style) with an Electron desktop client and a standalone Node.js server. Current version: 2.6.0, phases 1–17 complete — see "Project history" below before assuming something is unbuilt.

npm workspaces monorepo:
- `apps/client/` — Electron desktop client (TypeScript, no framework — vanilla DOM in the renderer)
- `apps/server/` — Fastify + Socket.io signaling server with mediasoup SFU (ESM, `"type": "module"`)
- `packages/shared-types/` — Socket.io event maps (`ClientToServerEvents`/`ServerToClientEvents`) and DTOs shared by both apps

docker compose -f docker-compose.dev.yml up -d   # Postgres + Redis only
```

npm run test            # vitest run

npx vitest run src/__tests__/permissions.test.ts   # single test file
npm run db:migrate      # prisma migrate dev

npx tsc --noEmit        # typecheck without emitting — the actual verification step used throughout this project's history
```

Client (`apps/client`):
```bash
npm run dev             # tsc --build && copy-html.mjs && electron .
npm run typecheck       # tsc --noEmit
npm run build:linux     # electron-builder (also :win, :mac)
```

Root:
```bash
npm run build            # tsc --build --force across all workspaces
npm run dev:server       # -> apps/server dev
npm run dev:client       # -> apps/client dev
npm run format            # prettier --write — works, prettier is installed
npm run lint              # ESLint 10 flat config (eslint.config.mjs) over the whole monorepo; must exit 0 (warnings are allowed). Needs Node >= 20.19. `npm run lint:fix` autofixes — review the diff, and never run it blindly.
```

There is no CI pipeline. `npx tsc --noEmit` (or `--build`) per affected workspace — shared-types, server, client — plus `npm run lint` from the repo root (it must exit 0) is the verification step used before treating a change as done; run the typecheck in each workspace touched. Lint is deliberately not type-aware (`tsc` is the type check) and the renderer is linted as a classic script, so only variables inside functions are checked for being unused. `npm run format` (Prettier, config in `.prettierrc.json`) is a user-run tool: the codebase was never Prettier-formatted (a repo-wide run rewrites ~60% of the files), so don't run it over the repo or include formatting-only churn in a feature commit.

Shared-types must be built (`npx tsc --build`) before server/client typecheck against changes made there, since both consume it via the `@reson8/shared-types` workspace package.

## Architecture

**Voice (SFU, not P2P mesh):** `apps/server/src/services/mediasoup.service.ts` runs mediasoup Workers/Routers; each client uploads one audio track, the server forwards it to other channel participants. Signaling is a fixed 6-step handshake driven by `apps/server/src/handlers/voice.handler.ts` and `apps/client/src/services/voice.service.ts`: `GET_ROUTER_CAPABILITIES → CREATE_WEBRTC_TRANSPORT → CONNECT_TRANSPORT → PRODUCE → CONSUME → RESUME_CONSUMER`. Active-speaker detection uses mediasoup's server-side `AudioLevelObserver` (not client-side analysis, interval currently 100ms) and broadcasts `ACTIVE_SPEAKERS` — except for the *local* user's own halo, which is computed directly from the client's own analyser tap instead (no server round-trip needed for feedback about your own voice; see `renderer.ts`'s `startMicLevelMeter()`). Before the mic track is produced, it passes through a client-side Web Audio graph built once per join in `voice.service.ts`'s `buildMicProcessingGraph()`/`buildProcessingChain()`: `micSource → [noiseCancelNode] → gateGainNode → volumeGainNode → destination`, with the settings-panel level meter tapping the graph right after the (optional) noise-cancelling stage, and an optional self-hear monitor (`setSelfHearEnabled()`) tapping post-volume straight to local playback so a user can hear exactly how they'll sound — this same chain is also built in preview mode (`startPreview()`, used outside a voice channel), not just during a real call, so all three features behave identically either way. Noise cancelling itself runs DeepFilterNet3 via a vendored WASM build (`apps/client/assets/deepfilternet/`, not the npm package's default third-party CDN) inside an `AudioWorkletNode`, with adjustable suppression strength (`setSuppressionLevel()`, 0–100, default 60 — was hardcoded to the package's maximum before Phase 14, which caused a quiet/paused voice to fade toward silence).

**Chat pagination:** channel/DM history loads via cursor pagination (`FETCH_MESSAGES`/`FETCH_DIRECT_MESSAGES`'s `before`/`limit` params) — the client fetches only the latest 20 messages on open and loads more as an `IntersectionObserver`-driven sentinel pinned to the top of the message list scrolls into view (`renderer.ts`'s `loadOlderMessages()`), preserving scroll position on every prepend. A second sentinel at the bottom drives a floating "Jump to Most Recent Message" button, which rebuilds the tab from a fresh fetch if the true latest message isn't currently loaded (e.g. after jumping to an old pinned message). Since Phase 17 paging is two-way: the fetches also take an `after` cursor and answer `hasMoreBefore`/`hasMoreAfter` exactly (the server fetches one extra row per direction — `pagination.service.ts`), and the bottom sentinel loads newer pages (`loadNewerMessages()`) after a jump. **Scroll keeper (PRD 18.12):** whether the view follows the bottom is ONE per-tab state (`tab.followBottom`), updated only by user scrolls and by code that deliberately positions the view, and read when a size change really happens — never captured at render time (that was the bug: a preview arriving after you scrolled up yanked you down, and a card whose image loaded late ended ~900 px above the bottom). A `ResizeObserver` per tab (fed by a `MutationObserver` on the list, so no insertion path can forget to register) re-applies the rule in the layout phase, before paint: following → stick; a held jump target → re-centre; otherwise → restore the recorded reading anchor (the first visible `.msg-body`). Every programmatic scroll goes through `setScroll()` (or `smoothScroll()` for animated ones, which the keeper never fights) so the scroll listener can tell it from the user; a jump target is held for 10 s or until the user takes over. Cards reserve their media box from the page's declared `og:image/video:width|height` (`aspect-ratio`), 16:9 for an undeclared video. Chromium's native scroll anchoring was left on: it already covers growth above the reading position. Rules that keep jumps correct: a jump window and newer pages render with `{ stick: false }` (rendering into an emptied list otherwise counts as "at the bottom" and re-sticks on every image load — the root cause of the old pinned-jump bug); `jumpToMessage()` sets `tab.jumpInProgress` so neither sentinel loads while it lands; a live message is NOT rendered into a detached window (`atTrueLatest === false`) — it would leave a gap — except your own, which rebuilds the tab at the present; and `ensureHistoryFilled()` runs after every load because the `IntersectionObserver` only fires on a change (an under-filled first page used to never load older history).

**Link preview:** `main.ts`'s `fetchLinkPreview()` tries the fast path in `link-preview-fetch.ts` (an `undici` fetch + metascraper + OG-tag fallback; Electron-free so it is tested in plain Node) first, escalating to a genuinely hidden `BrowserWindow` navigation (`fetchLinkPreviewViaHiddenWindow()`) only when that returns nothing. Since 18.10 the fast path is bounded and guarded (`link-preview-guard.ts`): one 8 s deadline covers connect, headers AND body; redirects are followed by hand (≤ 5) with every hop re-validated; the body is read only to `</head>` (≤ 1 MB, charset-sniffed); an `image/*` answer (not SVG, ≤ 20 MB) becomes a direct-image card without reading it; anything that isn't HTML or an image is `NOT_HTML` and never escalates to the browser window; private/loopback/link-local/CGNAT/multicast addresses and local names are refused — by URL, by redirect hop, and at connect time by a guarded DNS `lookup` (so a public name pointed at the reader's own network can't get through, nor can DNS rebinding) — and the hidden window runs in an in-memory `link-preview` partition with every request, download, popup and permission checked or denied. Results sit in a 500-entry LRU (6 h; 30 min for a fixer's signed video; 10 min for failures) with in-flight de-duplication, and Settings → Application has a "Show link previews" switch (`reson8-link-previews`) that makes no request at all when off. The connected server's own host is deliberately not special-cased: a LAN server's links simply don't preview. **Preview video playback (PRD 18.19):** a `<video>` decides whether it can seek from the FIRST response to its open-ended `Range: bytes=0-`; some hosts (the Invidious servers behind the YouTube fixer) answer that with `200` + a `Content-Range` header and no `Accept-Ranges`, which Chromium reads as "no ranges" — the progress bar can't seek (an explicit tiny range like `bytes=0-0` gets a proper 206 there, so the probe must be open-ended). The main process probes each video host once (6 h cache, `probeRangeRoute()`), and for hosts that need it re-serves the video through a privileged `reson8-media://v/<128-bit id>` protocol that forwards a validated `Range` upstream through the guarded fetch and normalizes the answer (`media-proxy.ts`: a `200` carrying a `Content-Range` becomes a `206`; only a safe header list passes; the body is streamed, never buffered). Only ids main minted for a preview's video are served (anything else is a 404), so the renderer can't make it fetch an arbitrary URL; hosts that already answer correctly (video.twimg.com) keep the direct URL. HTML fullscreen is the permission `"fullscreen"` in Electron: without a grant a video's fullscreen button never settles; it is granted only to the main window and Viewer windows (never the hidden preview session). A preview image opens the limited zoom-only viewer (`openLightbox(url, { previewOnly: true })`) instead of the link; the card text/domain and the embed-video thumbnail still open the link. **Blurred previews (PRD 18.11):** a preview's media (image, video, embed thumbnail, direct image) is always wrapped in `.lpc-blur-wrap` with an overlay, and CSS alone decides whether it is blurred: `.tab-nsfw` on the channel tab (kept in step with the CURRENT tree by `syncTabNsfwClass()` on every `renderTree()`), or `.lpc-adult` on the card (set when the site itself marks the page adult — `og:restrictions:age` ≥ 18 or `<meta name="rating">` adult/mature/restricted/RTA, detected in `link-preview-adult.ts` on both fetch paths), each gated by its own switch (`reson8-lp-nsfw-blur`, `reson8-lp-adult-blur`, applied as `body.lp-*-blur-off`) — independent of the attachment switch, whose `body.nsfw-blur-off` must never un-blur previews. Reveal is per card. Only signals actually observed are implemented; a site-specific one (Reddit's `over_18`) is added only after seeing it in a real response. Some sites block a bare HTTP client outright via IP-reputation/TLS-fingerprint bot management (e.g. Cloudflare) — no header or plugin change can get past this — but a real hidden Chromium window gets past it "for free" (confirmed live against a real bot-walled URL) since Electron already ships one, with no extra dependency needed. Capped at 2 concurrent fallback windows with a 15s timeout, since each is a genuinely expensive full renderer process. Before either, links to YouTube, X/Twitter, Instagram, Reddit, Twitch, Bluesky and Imgur first ask a "fixer" proxy (`link-fixers.ts`: koutube, fxtwitter, oginstagram, vxreddit, fxtwitch, vxbsky, imgurez — exact-hostname rules, never substring), which usually returns a direct `video/mp4` the card plays inline. A fixer answer only counts in strict mode: the final response must still be on the fixer's host (they redirect visitors they won't serve) and must carry an image or video (a title alone is their error page); otherwise the normal flow runs on the original URL. Fixers only serve recognized crawlers, so fixer requests use a UA with a `Discordbot/2.0` token (every other request keeps the plain crawler UA) — each rule can override it: fxtwitter (X) hides a video post's media from Discordbot, so its rule uses the plain UA (PRD 18.14); re-verify with curl when a fixer stops delivering media, that is what broke it. A fixer result keeps the ORIGINAL url/domain and names the real network as site name.

**Presence-quit signaling:** a socket disconnect defers presence cleanup by a grace period (`connection.handler.ts`'s `pendingDisconnects`) so a brief network drop doesn't flicker someone's presence off and on — *except* when the client explicitly called `socket.disconnect()` itself (reported as Socket.io's `"client namespace disconnect"` reason, e.g. the app quitting via `main.ts`'s `"before-quit"`/window `"close"` handlers), which finalizes immediately since there's no ambiguity about a possible reconnect.

**Socket ownership (stale-socket race):** presence, mediasoup sessions and the grace timer are all keyed by `userId`, but a reconnecting user briefly has TWO live primary sockets — the new one and the old half-open one the server only reaps at its ping timeout (up to 45s). `apps/server/src/services/socket-ownership.ts` (`SocketOwnership`) records which socket owns each `userId`: `USER_JOIN_SERVER` claims it and `supersedeSocket()` (`connection.handler.ts`) retires the displaced socket immediately; the `disconnect` handler ignores any socket that isn't the owner, and the grace-timer callback re-checks `hasOwner()` before finalizing. Without this the old socket's late `disconnect` destroyed the live socket's voice session and presence (Phase 15 incident: users vanished from the online list and dropped from voice a second time ~12s after a blip — see progress.txt). Any new `userId`-keyed teardown in a disconnect path must go through this ownership check. Viewer sockets (`role: "viewer"`) are separate and never claim ownership.

**Chat messages (multi-line + Markdown):** the chat box is a `<textarea>` (Enter sends, Shift+Enter = newline) and message text is rendered as Discord-style Markdown. Rendering lives in `apps/client/src/markdown.ts` — a *pure* module (no Electron/DOM imports) on `markdown-it` — and is exposed through the preload as the synchronous `reson8Api.renderMarkdown()` (the renderer is a plain `<script>` with no bundler and a strict CSP, so it can't import markdown-it). Output is re-checked by an allow-list sanitizer (`sanitizeMessageHtml`) before `innerHTML`, and every message goes through the single `setMessageBody()` helper (channel, DM, edit, edit broadcast — never render message text any other way). Deliberately unsupported: raw HTML, images, tables, masked links `[text](url)` (spoofing), indented code blocks. A single plain line renders inline (the pre-Markdown `[time] nick text` layout); anything with a newline or block syntax is a block. Custom `:name:` emoji are an inline rule registered before `emphasis` (names may contain underscores) and read the emoji list the renderer pushes via `setCustomEmojis()`. Run `npm run test:markdown` in `apps/client` after touching `markdown.ts` — it includes XSS vectors.

**Emoji rendering:** emoji are plain Unicode text drawn with a vendored Google Noto Color Emoji web font (`apps/client/assets/fonts/noto-color-emoji/`, family `Reson8 Emoji`, first in the font stacks) so they look identical on every OS. Two traps: Chromium cannot render the OpenType-SVG build that npm redistributions (`@fontsource/noto-color-emoji`) ship — emoji come out blank — so the files are the COLRv1 woff2 subsets served by Google Fonts; and Google's `unicode-range` includes digits, `#`, `*`, `©`, `®`, `™`, which the vendored CSS strips (documented in its header) or every number would render as an emoji glyph. Form controls don't inherit `font-family`, hence the base `button, input, textarea, select` rule.

**Reaction hover card:** reactions carry `users: [{ userId, nickname }]` (`IReactionSummary` in shared-types, optional/additive). All reaction aggregation lives in `apps/server/src/services/reaction.service.ts` (one nickname query per batch of messages) — don't re-inline it in a handler. The client card is one shared `#reaction-card` element driven by delegated events with a 1s "pointer held still" dwell.

**Message layout, grouping & the hover toolbar:** every channel/DM message is built by the shared `buildMessageShell()` (`renderer.ts`) as `.chat-msg` > `.msg-header` (avatar + nick + HH:MM) + `.msg-body` (text + "(edited)"). The 40px avatar sits in a 56px left gutter but lives INSIDE `.msg-header` (absolutely positioned), so it shows and hides with the header and grouping needs no avatar logic; `.chat-msg` has `flex-shrink: 0` because the group start's `min-height` replaces the default `min-height: auto` that kept flex items from shrinking in the scrolling list (without it messages overlapped). `loadOlderMessages()` anchors the prepend on the first visible `.msg-body`, not on the scrollHeight delta (the junction repair can drop a header and its min-height). Consecutive messages from the same author are *grouped* — a continuation (`.msg-continuation`) hides its header — when it lands within 5 minutes of the **group's first message** (not the previous one); a date divider, the "Unread Messages" separator or the sentinels break a group, and a reply (`data-is-reply`) always starts its own. `applyGrouping()`/`regroupFrom()` own this and MUST run wherever message elements are added or removed: after an append, after a prepend (it repairs the page junction), and after a delete (`removeMessageElement()`) — any new code path that inserts or removes `.chat-msg` elements has to do the same or headers go missing/duplicate. Actions (React, Reply, Edit, Pin, Delete — that order, via `insertToolbarButton()`) live in a floating `.msg-actions` toolbar, not in the reaction strip, which is `display: none` unless the message has reactions (`.has-reactions`).

**Replies:** `Message.replyToId`/`DirectMessage.replyToId` are plain columns with **no foreign key**, deliberately — `ON DELETE SET NULL` would erase the fact that a message *was* a reply, and the client says "Original message was deleted". The server resolves snippets in one batched primary-key query per page (`reply.service.ts`, mirroring `loadReactorNicknames`) and ships them as `replyTo: IReplyPreview` (one level only — a snippet never nests). A reply into another channel/conversation is refused (it would leak that text into the snippet); a missing target is accepted and renders as deleted. Client side, reply drafts live in `replyTargets` keyed by tab id, the bar is the first child of `#chat-composer`, Escape cancels it only when the emoji autocomplete didn't consume the key, and `jumpToMessage(tabId, messageId)` (channels via `FETCH_MESSAGES`, DMs via `FETCH_DIRECT_MESSAGES`' `aroundMessageId`) serves both reply snippets and the pinned bar.

**Uploads — the stored-file ledger (security-critical):** the server never trusts a file URL or Cloudinary `public_id` from a client. Every stored file is a `StoredFile` row (`kind`, `ownerId`, `claimedAt`); an HTTP upload is attributed to a user by a socket-issued bearer token (`REQUEST_UPLOAD_TOKEN`, hashed in Redis, 10 min) and returns an `uploadId`; a message/DM/emoji/icon *claims* it by id with `claimUploads()` — one atomic `UPDATE … WHERE claimedAt IS NULL AND kind = ? AND (ownerId = me OR ownerId IS NULL) RETURNING`, run on the **same transaction** as the write that uses it. Deleting always goes through `releaseStoredFile()` AFTER the referencing row is removed, using the ledger's own url/public_id and only when nothing else still references the file; a URL the ledger doesn't know is never deleted. Never persist or delete a client-supplied URL/public_id anywhere. Local-disk files are stored by their host-independent path (`/uploads/<file>`) and the client resolves them against the server address (`resolveMediaUrl()` in `preload.ts`, applied at every inbound entry point). Unused uploads are cleaned up three ways: `DISCARD_UPLOAD` (immediate), an hourly sweeper for uploads unclaimed after 24 h (`upload-sweeper.ts`), and `npm run uploads:prune` for pre-ledger leftovers. Message images live in the `attachments` table (up to 10 per message); `Message`/`DirectMessage.attachmentUrl` are deprecated and no longer written (expand/contract).

**Composer:** `#chat-composer` stacks [reply bar → attachment tray → input bar]; `switchTab()` toggles it. Picked images are `pendingAttachments` (global, not per tab): uploaded at once, at most 3 concurrently, each shown as a persistent preview card with preview/remove/retry, and Send is blocked while any is uploading or failed. Typing `:` + a letter opens the emoji autocomplete (all in `renderer.ts`; its element refs live at the top of the file because `switchTab()` calls into it during startup). It serves whichever textarea has focus: `attachEmojiAutocomplete(textarea, { onAfterInsert })` wires one (the composer and each message edit box), and that textarea's own keydown must call `handleEmojiAutocompleteKeydown(e)` first. The card opens below the caret when there's < 120px above it.

**Identity (security-critical, PRD 17.12):** no accounts or passwords. Each Electron install has a persistent UUID (`apps/client/src/instance-id.ts`) sent as `instanceId` — it is the user's id, it is broadcast to everyone, and it is therefore NOT a secret. What proves ownership is an Ed25519 key per install (`identity-key.ts`, MAIN PROCESS ONLY — `<userData>/identity-key.pem`, 0600; dev builds use an ephemeral key, like the fresh dev UUID): on every connect the preload asks `REQUEST_AUTH_CHALLENGE` (single-use nonce, 60 s), the main process signs `"reson8-auth-v1\n<nonce>\n<host>"` (`identity-proof.ts` refuses anything that isn't a server-shaped nonce + plain host), and `USER_JOIN_SERVER` carries `identity`. The server's decision is one pure function (`identity.service.ts`'s `decideIdentity()`) run BEFORE anything is written: the first valid signed join binds the key to the id (`users.publicKey`, atomic compare-and-set); afterwards other keys and unsigned joins are refused. Rollout is gradual: an unbound id still joins unsigned (pre-2.6.0 clients) unless `REQUIRE_SIGNED_IDENTITY=true`. `ADMIN_INSTANCE_ID` grants Server Admin, and with `ADMIN_KEY_FINGERPRINT` set only that key can bind or be the admin; `AUTH_ALLOWED_HOSTS` stops another server relaying this one's challenge. The screen-share Viewer authenticates with a server-issued ticket (`viewer-ticket.service.ts`) obtained by the user's own primary socket — never with a bare id. An ADMIN can `RESET_IDENTITY_KEY` (User Management → Reset key), which also disconnects the user. Since 2.7.0 every key bind, reset and identity refusal is written to an ADMIN-only **identity log** (`identity-events.service.ts`, the `identity_events` table, Settings → User Management → Identity log): recording is fire-and-forget (`void recordIdentityEvent()` — it must never delay or change a join), refusals are de-duplicated per (user, reason, key, address) for 10 minutes and capped at 10 per address per hour, rows are pruned after 90 days, and addresses are only ever sent to ADMINs. **Address bans (PRD 18.7):** bans stay per identity (a fresh install is a fresh identity), so a moderator can OPTIONALLY also ban the user's address — exactly, or its /24 (IPv4) / /64 (IPv6) — from the Ban dialog; it is never the default because a VPN dodges it and a shared network (school, office, carrier NAT) can put innocent people behind one address. Rows live in `banned_addresses` as canonical CIDRs (IPv6 as eight un-compressed hextets), the matcher is a process-wide `net.BlockList` (`address-ban.service.ts`) reloaded after every change, and the address compared is ONLY `socket.data.clientAddress` (so it is as trustworthy as `TRUST_PROXY`). The handshake only MARKS a socket (`addressBanned`); `USER_JOIN_SERVER` refuses it unless the identity check accepted the join AS `ADMIN_INSTANCE_ID`, so the designated admin can always get in to undo a mistaken range ban; a Viewer socket from a banned address is refused at the handshake. The user ban always succeeds: anything that stops the address part (unknown address, a private/loopback address behind an untrusted proxy — it would ban everyone —, a private range, a network that includes the moderator's own address) comes back as a `warning`. Unbanning a user lifts the address ban made with them. Only an ADMIN sees full networks; other moderators see `203.0.113.x`. **Approving new users (PRD 18.8):** an ADMIN can switch on "Approve new users" (Settings → Server; `servers.requireApproval`, mirrored in memory by `approval.config.ts` like the other policy switches). It only concerns identities with no `users` row: they pass every other check (password, identity decision, address ban), then `USER_JOIN_SERVER` answers `{ success: false, pending: true }` and stores a `pending_approvals` row (the nickname, the key they proved, address, name) — a waiting person is NOT a half-joined user: no `users` row, roles or presence, and the socket keeps `pendingUserId` with `userId`/`serverId` UNSET. Unsigned new identities are refused (an approval has to bind a key), a second key asking as the same id is refused, there are at most 50 requests per server and 3 per address (the refusal says only that the server isn't accepting new users), and untouched requests are pruned after 7 days. Anyone with BAN_USER (or ADMIN) sees the queue (Settings → User Management, a badge on the gear and the tab; addresses masked unless ADMIN) and can Approve, Reject, or Reject and ban (the same ban dialog, so the address options apply); approving creates the user in one transaction with the requested key already bound and tells the waiting client, which simply joins again. The designated `ADMIN_INSTANCE_ID` is never queued. **Default-deny gate:** every incoming event passes `services/packet-guard.ts` first — a socket that has not signed in (this includes one waiting for approval) can send only `USER_JOIN_SERVER`, `VIEWER_AUTHENTICATE`, `REQUEST_AUTH_CHALLENGE` and `PING_LATENCY`; everything else is dropped with `{ success: false, error: "Not signed in" }`. A handler that takes a payload always gets one, and an ack function always exists, so an event emitted without a callback can no longer crash the process (it used to: any connected socket could take the server down with one packet, and `FETCH_MESSAGES`, `USER_JOIN_CHANNEL` and `FETCH_DIRECT_MESSAGES` answered sockets that had never signed in — both found by the 18.8 event fuzz). New events are covered automatically; one that must work before sign-in has to be added to `PRE_JOIN_EVENTS`. **Server access (PRD 18.18):** removing the Member role restricts a user instead of being silently undone. "Has access" = the aggregated permissions include `CONNECT` or `ADMIN` (`access.service.ts`'s `hasServerAccess()`); Member is granted only when the user row is CREATED (`rolesToGrant()` — it used to be re-added on every join, which made removal last until the next connect; existing users already hold it so nobody loses access on upgrade). A restricted user stays connected and still sees the tree, who is online, profiles and their own settings, but cannot open text channels, send/read DMs, join voice, upload, submit emoji, nudge or screen share. Enforcement is ONE central check in the packet gate (`index.ts`): `EVENT_ACCESS` classifies every client→server event as `open` or `member` (TypeScript's `Record<keyof ClientToServerEvents, …>` refuses an unclassified new event, and a test reads the registered handlers), and `socket.data.hasAccess` is computed at join and by `applyAccessChange()`; moderator/admin events stay `open` because they carry their own `requirePermission`. Content events (`MESSAGE_RECEIVED/EDITED/DELETED`, `REACTION_UPDATED`, `CHANNEL_PIN_UPDATED`) are broadcast to the `members:<serverId>` room, joined next to `server:<serverId>` only when the user has access — structural events (tree, presence, avatars, settings) stay on `server:`. A DM to a user without access is refused (their DMs would pile up unreachable). `ASSIGN_ROLE` calls `applyAccessChange()`: on loss the user's sockets leave `members:`, their voice session is torn down quietly (the same `removeSocketFromChannel()` KICK_USER uses, without the kick message), Viewer tickets are revoked and Viewer sockets closed, and they get `ACCESS_CHANGED { hasAccess: false }`; giving the role back restores everything with no reconnect. A Server Admin never loses access (ADMIN bypass). The client shows a banner, closes channel/DM tabs (`closeTab(…, { reason: "access" })` keeps kept tabs remembered), guards every entry point with `requireServerAccess()`, and restores kept tabs when access returns. Join ack carries `hasAccess` (an older server omits it = treated as true).
**Invite codes (PRD 18.9):** a second ADMIN switch (Settings → Server; `servers.requireInvite`, mirrored by `invite.config.ts`) makes a NEW identity present a code. Codes are 12 Crockford Base32 characters (~60 bits, `crypto.randomInt`), shown ONCE at creation and stored only as a SHA-256 of the normalized code plus a four-character prefix (`invites`, `invite_uses`); `invite.service.ts` holds the pure rules (generation, normalization with Crockford substitutions, status, throttle, payload validation) and the two SQL helpers. The gate in `USER_JOIN_SERVER` sits BEFORE the approval gate and applies to new identities only (the designated admin is exempt): no code → `errorCode: "INVITE_REQUIRED"`, anything unusable (unknown, revoked, expired, used up) → one generic `INVITE_INVALID`, and 10 wrong codes from an address within 15 minutes → `INVITE_THROTTLED` (a Redis counter; the code isn't even looked at). The gate only CHECKS the code; the use is consumed by an atomic `UPDATE … WHERE uses < maxUses … RETURNING` run on the SAME transaction that creates the user — so a failed join costs nothing and N joins racing for the last use produce exactly one winner — or, with approval on, inside the approval transaction (the request stores `inviteId`; rejecting costs nothing, and approving with a dead invite is refused with a reason). Moderators (BAN_USER/ADMIN) manage invites in User Management → Invites; expiry is judged by the database clock. The client's connect form has a hidden code field revealed by the error code, never stored (not even by Remember).

**The identity key at rest (PRD 18.6):** the Ed25519 key is stored OS-encrypted (`identity-key.enc`, Electron `safeStorage`) on Windows, macOS and Linux with a real keyring — never on Linux's `basic_text` backend, where it stays a 0600 `identity-key.pem` — and a 2.6.0 plaintext PEM is migrated automatically (the plaintext is deleted only after the encrypted copy was read back and compared). An encrypted key that can't be decrypted puts the install in a **locked** state (a modal; connecting is stopped rather than joining unsigned): it NEVER mints a replacement on its own, because that would orphan every identity bound on servers. Recovery is importing a backup, or an explicit two-click "Create new identity" (the old file is kept aside). Settings → About exports/imports a scrypt+AES-256-GCM, passphrase-protected `*.reson8-identity` backup (user id + key); an import renames the replaced files aside and relaunches. This does not stop malware running as the user on Windows/Linux — it protects copied folders, backups and other OS accounts. The relay-protection list (`AUTH_ALLOWED_HOSTS`) is also managed in Settings → Server (`servers.authAllowedHosts`; env wins and locks it): the section suggests the names actually seen in accepted signed joins (Redis, capped), the server refuses to save a list that excludes the saving admin's own signed host (`checkAllowedHostsUpdate`), and `npm run identity:clear-hosts` is the recovery when a stale list locks everyone out. "Require signed identity" is also a switch in Settings → Server (`servers.requireSignedIdentity`); the `REQUIRE_SIGNED_IDENTITY` env var, when set (even to `false`), wins and locks the switch. Any new way of acting as a user must derive the user id from an authenticated socket or a ticket, never from a payload.

**Encrypted connections (PRD 18.3):** the connect box takes `host`, `host:port` or an explicit `http://`/`https://` (`parseServerAddress()`; IPv6 as `[::1]:9800`). With no scheme the client PROBES the server's TLS first (`tls-probe.ts`, main process) and applies the pure `decideScheme()` table (`tls-trust.ts`): publicly trusted → https; unknown/self-signed → a modal shows the SHA-256 fingerprint and, if the user trusts it, the certificate is PINNED (`<userData>/tls-trust.json`, `tls-store.ts`, MAIN ONLY — the renderer can only pin the certificate the last probe just showed); a different certificate for a pinned host is refused with no one-click override (remove the trust in Settings first, like SSH host keys); a server ever reached over HTTPS is never silently downgraded (typing `http://` is the explicit override); a server with no TLS is used over http with a "Not encrypted" status-bar indicator and a per-server dismissible warning. A port-less address with nothing speaking TLS on 443 still falls back to plain http on port 80 (the pre-2.7.0 behavior). **There are two TLS stacks and a pin must satisfy both:** Socket.io in the preload runs on Node's `ws` (the pin is passed as `ca` plus a SHA-256 `checkServerIdentity`, which replaces the hostname check), while uploads, images, emoji and the Viewer's media go through Chromium (`session.setCertificateVerifyProc` in `main.ts` accepts a certificate only when its SHA-256 equals a pin for that hostname and it hasn't expired; everything else gets Chromium's own verdict). Any new network path must be checked against both. `engine.io-client` sets `rejectUnauthorized: true` explicitly, so `NODE_TLS_REJECT_UNAUTHORIZED=0` does NOT relax the socket in tests — use `NODE_EXTRA_CA_CERTS`. The host the identity proof signs stays the address as typed WITHOUT a scheme (`identityHostOf()`), byte-identical to 2.6.0, so bound identities and `AUTH_ALLOWED_HOSTS` keep matching.

**Avatars (PRD 17.1/17.2):** the client sends `{ provider, hash }` (SHA-256 of the trimmed, lower-cased email — the email never leaves the client) on every join and via `SET_AVATAR`; the server NEVER accepts a URL, it builds the Libravatar/Gravatar URL from a fixed template (`avatar.service.ts`) and stores it in `users.avatarUrl`, broadcasting `USER_AVATAR_UPDATED`. Messages/DMs carry the author's CURRENT `avatarUrl`. Users without one get Libravatar's generated wavatar keyed by `sha256(userId)` (never the raw id). Every avatar is one `.avatar[data-avatar-user-id]` element (`createAvatarElement()`/`applyAvatar()` in `renderer.ts`): initials underneath, the image fading in over them, falling back stored → default → initials; a per-user switch turns external avatars off entirely. Clicking an avatar or nickname opens the profile card (`GET_USER_PROFILE`; "member since" is `User.createdAt`, written once at first login).

**Tabs (PRD 17.5/17.6):** clicking a text channel opens it in the single preview tab (`previewTabId`, italic), replaced in place by the next one; "Keep Tab Open" (tab or tree context menu) makes it kept (bookmark icon) and remembers it per server in `reson8-kept-tabs`, restored unfocused with lazy history after the first channel tree — keyed by the tree payload's `serverId`, because the first tree arrives before the `connected` event. `closeTab(id, { reason })` decides the bookkeeping (`"disconnect"` keeps the store). An open, unfocused channel tab shows the tree's red unread dot via `refreshTabUnread()`, driven by the same `unreadChannelIds` + mute state as the tree. DM tabs have no modes.

**Permissions:** bitwise flags on `bigint` role columns, defined in `packages/shared-types/src/models.ts` (`PermissionFlags`: `CONNECT`, `SPEAK`, `MANAGE_CHANNELS`, `MANAGE_ROLES`, `KICK_USER`, `BAN_USER`, `ADMIN`, `MANAGE_EMOJIS`). `apps/server/src/services/permissions.service.ts` aggregates a user's roles via bitwise OR; `ADMIN` bypasses all checks. Socket.io handlers are gated with `requirePermission()` from `apps/server/src/middleware/permissions.middleware.ts`; `requireAnyPermission()` in the same file gates a handler shared by more than one permission (e.g. `GET_ALL_USERS`, needed by both `MANAGE_ROLES` and `BAN_USER` holders for the User Management tab).

**Presence:** tracked in Redis (`apps/server/src/services/presence.service.ts`), not Postgres — who's connected to which server/channel, with a TTL refreshed on activity. On `USER_JOIN_SERVER`, `hydrateOccupants()` in `connection.handler.ts` walks the channel tree and populates occupants from Redis before emitting `CHANNEL_TREE_UPDATE`. `resolveNickname()` falls back to Postgres when a Redis presence read races a reconnect (see progress.txt PRD 3.2).

**Protocol contract:** `packages/shared-types/src/socket-events.ts` (`ClientToServerEvents`/`ServerToClientEvents`) is the source of truth for the client↔server wire format. When a feature crosses that boundary, update shared-types first — both apps typecheck against it.

**Data model:** Prisma/Postgres (`apps/server/prisma/schema.prisma`) holds `Server`, `Channel` (self-referencing tree via `parentId`, re-parentable after creation via `CHANNEL_MOVED`, cycle-checked server-side; `iconEmoji`/`iconUrl` give text channels a custom tree icon, mutually exclusive, no distinct "category" `ChannelType` — a channel is a category simply by having children), `User`, `Role`, `Message`, `DirectMessage`, `BannedUser`, `Reaction`, `ChannelRead` (per-user-per-channel unread cursor), `CustomEmoji` (server-uploaded emoji, PENDING/APPROVED), `StoredFile` (the upload ledger — see "Uploads" above) and `Attachment` (a message/DM's images, in order). `Message`/`DirectMessage` also carry `replyToId` (a plain column — see "Replies"). Channel tree is flattened→nested in `apps/server/src/services/channel-tree.service.ts`.

**Client process boundaries:** `main.ts` (Electron main — window, tray, global shortcuts for PTT, permission handler for mic access, link-preview fetching via `metascraper`, native context menu) → `preload.ts` (contextBridge API surface, `reson8Api`, 60+ methods) → `renderer/renderer.ts` (vanilla TS DOM UI, no framework/build tooling beyond tsc).

**Electron gotchas that have bitten this project before** (see progress.txt for the incidents):
- `getUserMedia` is silently blocked by default — `session.defaultSession.setPermissionRequestHandler` in `main.ts` must auto-grant mic/audio permissions.
- Detached `new Audio()` elements produce no sound in the renderer; audio elements must be `document.createElement("audio")`, appended to `document.body`, and removed after use.
- Files referenced by the main process (tray icon, sound alerts under `apps/client/assets/`) must be listed in electron-builder's `build.files` in `apps/client/package.json` or they silently vanish from packaged builds while working fine in dev.
- electron-updater's GitHub provider needs `latest.yml`/`latest-linux.yml`/`latest-mac.yml` (electron-builder generates them locally under `apps/client/release/` alongside the installers) uploaded as release assets on every GitHub release — `npm run build:*` alone does not publish anything, so a release built and uploaded by hand without those yml files leaves every platform's update check silently failing (v1.3.0 → v1.4.0 incident, see progress.txt).
- A `main.ts`/`preload.ts`/`voice.service.ts` static `import` of an ESM-only npm dependency (a package with no real `"require"` export condition, or one whose own `package.json` sets `"type": "module"` — which makes Node treat *all* its plain `.js` files as ESM regardless of which export condition points at one) compiles to a `require()` call under this project's CommonJS `tsconfig` and crashes the whole preload script at startup with `ReferenceError: exports is not defined` (the `deepfilternet3-noise-filter` incident, Phase 13, see progress.txt) — check a candidate dependency's `package.json` `"type"`/`"exports"` *before* adding it. A plain `await import(...)` isn't a safe fix either: TypeScript rewrites dynamic `import()` back into a deferred `require()` under this same CommonJS target, hitting the identical crash lazily instead of at startup. The confirmed-working escape hatch when an ESM-only dependency is unavoidable is an indirect-eval dynamic import — `new Function("specifier", "return import(specifier)")` — which TypeScript can't see or rewrite (see `voice.service.ts`'s `dynamicImport` helper). That helper only works with an actual URL, though — calling it with a *bare* package name (`dynamicImport("some-package")`) throws `Failed to resolve module specifier` in a real (non-sandboxed) Electron preload, both unpacked and packed into a real `.asar`: unlike Node's own `import()`, this path has no concept of bare specifiers/node_modules resolution and needs a real URL. Resolve the bare name to an absolute `file://` URL first — `require.resolve()` (safe even for an ESM-only package: it only computes a path via the "require" export condition, it doesn't execute the file) then derive the actual ESM sibling file and `pathToFileURL(...).href` it — see `voice.service.ts`'s `resolveNoiseCancelModuleUrl()` (the v2.2.1 noise-cancelling incident, Phase 13, see progress.txt — this bare-specifier form never worked in any environment, dev or packaged, despite passing typecheck and the preload-crash fix).
- `apps/client/src/renderer/index.html`'s CSP `script-src` must include `blob:` — an `AudioWorkletNode`/`AudioWorklet.addModule()` built from an in-memory `Blob` + `URL.createObjectURL()` (the noise-cancelling engine builds its processor this way) is governed by the `script-src`/`script-src-elem` CSP directive, not `worker-src` as the name might suggest, and without it fails with the unhelpful `AbortError: Unable to load a worklet's module.` (no explicit CSP violation surfaces in the toast — only in the console) (v2.2.1 incident, see progress.txt).
- On Windows, an app-icon re-launch that "froze" the window was addressed (hypothesis-driven, user-confirmed OK) by two things in `main.ts`: minimize-to-tray intercepts `will-minimize` and `hide()`s instead of hiding from inside the post-hoc `minimize` event (which left the window both minimized and hidden), and Chromium's `CalculateNativeWinOcclusion` feature is disabled on `win32` (it can wrongly mark a restored window occluded and stop painting it). All "bring the window forward" paths (second-instance, tray click, tray Restore) go through `showMainWindow()`, which logs window state. Window size/position/maximized persist via `apps/client/src/window-state.ts` (hand-rolled, validated against current displays; Wayland ignores app-set positions).
- Image-viewer actions that need Node/Electron (`openExternal`, clipboard, fetching image bytes without CORS) go through validated main-process IPC (http(s) only, `image/*`, 25 MB cap, 15s timeout) — never direct renderer access.
- Never pass a secret to a window through `webPreferences.additionalArguments`: they end up on the process's command line, readable by other local users (`/proc`). The Viewer window's ticket is kept by `main.ts` per webContents id and fetched over IPC (`viewer-get-ticket`) instead (PRD 17.12).
- Installers currently ship **unsigned** (no code-signing certificate) — on Windows, `main.ts` replaces `NsisUpdater`'s `verifyUpdateCodeSignature` with a verifier that always resolves `null` (not a boolean; it's a `(publisherNames, path) => Promise<string | null>` function per electron-updater's API). Without this, electron-updater checks a downloaded update's Authenticode publisher against the publisher name baked into the *currently-installed* app's own `app-update.yml` and rejects a legitimate unsigned update with "not signed by the application owner" (v2.2.0 incident — hit when updating a client that had been built and installed while still signed, see progress.txt). If code signing is ever reintroduced, that override must be removed again so updates are actually verified — see the "Code Signing" section in the root README.

- The main window must never navigate away from the app's own page: a file dropped on Chromium's default drop target navigates the window to that file and replaces the whole UI. `main.ts` cancels it with a `will-navigate` handler (defense in depth) and the renderer swallows every drag that carries `Files` (`dragover`/`drop` guard) — text drags, including the channel tree's own reorder drag, are left alone.
- Any payload that carries a file URL (message `attachments`, emoji `imageUrl`, channel `iconUrl`) must be run through `resolveMediaUrl()` in `preload.ts` before reaching the renderer — new local-disk files arrive as server-relative paths (`/uploads/x.png`) and render as broken images/icons otherwise. A v2.4.0 client does not do this, which is why it cannot show *new* locally-stored files from a v2.5.0 server.

## Environment

Server needs `apps/server/.env` (copy from `.env.example`): `DATABASE_URL`, `REDIS_URL`, `PORT` (9800), `MEDIASOUP_ANNOUNCED_IP`; optional `ADMIN_INSTANCE_ID`, `SERVER_PRIVATE_PASSWORD`, `TLS_CERT_FILE`/`TLS_KEY_FILE` (native HTTPS/WSS, hot-reloaded; only one of the two stops the boot) and `TRUST_PROXY` (which proxies' forwarded-address headers to believe; unset = none, `true` is refused), `MEDIASOUP_PRIVATE_ANNOUNCED_IP` (LAN/WAN dual-announce for hairpin NAT), `CLOUDINARY_*` (image uploads fall back to local disk storage if unset), and the identity settings `REQUIRE_SIGNED_IDENTITY`, `ADMIN_KEY_FINGERPRINT`, `AUTH_ALLOWED_HOSTS` (see "Identity" above and `.env.example`).

Ports: 9800 (Fastify + Socket.io signaling), 10000–10100 UDP/TCP (mediasoup media), 5432 (Postgres), 6379 (Redis).
