# AGENTS.md — apps/server

Guidance specific to the Reson8 server. See the repo-root `AGENTS.md` first for architecture and cross-cutting conventions (shared-types-first workflow, progress.txt logging requirement, etc).

## Commands

```bash
npm run dev            # tsx watch src/index.ts — auto-restarts on change
npm run build           # tsc
npm run start            # node dist/index.js — run the built server
npx tsc --noEmit         # typecheck without emitting (verification step)
npm run test              # vitest run
npm run test:watch        # vitest
npx vitest run src/__tests__/permissions.test.ts   # single test file
npm run db:generate       # prisma generate (after schema.prisma changes)
npm run db:migrate        # prisma migrate dev (creates + applies a migration)
npm run db:push           # prisma db push (schema sync without a migration)
npm run identity:clear-hosts -- --yes   # clears a stale allowed-names list (restart the server afterwards)
```

Requires `.env` (copy from `.env.example`) and `docker compose -f docker-compose.dev.yml up -d` running from the repo root for Postgres + Redis.

## Structure

- `src/handlers/*.handler.ts` — one file per Socket.io event domain (connection, voice, channel, message, dm, admin, moderation, reaction). This is where new client↔server events get wired up after being added to `packages/shared-types/src/socket-events.ts`. `upload.handler.ts` holds the upload-pipeline events (`REQUEST_UPLOAD_TOKEN`, `DISCARD_UPLOAD`). `profile.handler.ts` (Phase 17) holds `SET_AVATAR` and `GET_USER_PROFILE`; the identity events (`REQUEST_AUTH_CHALLENGE`, `REQUEST_VIEWER_TICKET`, the join decision) live in `connection.handler.ts`, and `RESET_IDENTITY_KEY` in `admin.handler.ts`.
- `src/services/` — stateful business logic consumed by handlers: `mediasoup.service.ts` (SFU worker/router/transport lifecycle, AudioLevelObserver), `presence.service.ts` (Redis-backed online/channel tracking), `permissions.service.ts` (bitwise role aggregation), `channel-tree.service.ts` (flat rows → nested tree), `client-address.ts` (the client's address with `TRUST_PROXY` rules — see Conventions), `socket-ownership.ts` (which socket owns each `userId` — see the root `AGENTS.md`'s "Socket ownership"), `reaction.service.ts` (the one place reactions are aggregated, with reactor nicknames), `message-text.ts` (`normalizeNewlines`: CRLF → LF before length checks/persistence). Phase 16 added `stored-file.service.ts` (the upload ledger: claim/release/discard/sweep, upload tokens), `attachment.service.ts` (a message's images), `reply.service.ts` (reply snippets and the reply-target rules) and `upload-sweeper.ts` (the hourly sweep). Phase 17 added `avatar.service.ts` (validates `{ provider, hash }`, builds the stored URL — never accepts a URL), `profile.service.ts` (the profile card's data), `pagination.service.ts` (latest/before/after/around queries, one extra row per direction → exact `hasMoreBefore`/`hasMoreAfter`), `identity.service.ts` (challenge, Ed25519 verification, fingerprints and the pure `decideIdentity()` join table) and `viewer-ticket.service.ts` (hashed, Redis-backed Viewer tickets). Phase 18 added `client-address.ts` and `address-ban.service.ts` (canonical CIDRs, the private-range guard, masking, the in-memory ban matcher), `auth-hosts.service.ts` (the allowed-names list: validation, the lock-out guard, observed names in Redis), `identity-events.service.ts` (the identity log: fire-and-forget recording with de-duplication and a per-address cap, page building, retention pruning, the "unprotected active users" count), `approval.service.ts` (the approval gate decision, limits, DTO masking, stale-request pruning), `ban.service.ts` (the one ban routine shared by `BAN_USER` and reject-and-ban), `packet-guard.ts` (the default-deny gate and packet normalization) and `invite.service.ts` (invite codes: generation, normalization, status, throttle, the atomic claim), `admin-users.ts` (the User Management list: who is listed, the row mapping), `access.service.ts` (who has access, the per-event classification, which roles a join grants), `access-change.ts` (applies a role change to live sockets, rooms, voice and viewers) and `voice-session.service.ts` (server-side removal from a voice channel).
- `src/middleware/permissions.middleware.ts` — `requirePermission()` guard used to gate handlers by `PermissionFlags`; `requireAnyPermission()` for a handler shared by more than one permission (e.g. `GET_ALL_USERS`, needed by both `MANAGE_ROLES` and `BAN_USER` holders for the User Management tab).
- `src/plugins/` — Fastify plugins registering Prisma and Redis clients on the `app` instance.
- `src/config/mediasoup.config.ts` — Worker/Router/Transport settings, including the public/private dual-announce-IP logic for LAN/WAN NAT traversal. `src/config/tls.config.ts` (`TLS_CERT_FILE`/`TLS_KEY_FILE`: validated pair, certificate hot-reload by watching the directories, a failed reload keeps the old certificate). `src/config/identity.config.ts` reads `REQUIRE_SIGNED_IDENTITY`, `ADMIN_KEY_FINGERPRINT` and `AUTH_ALLOWED_HOSTS` at call time. `src/config/upload.config.ts` holds the upload tunables (`ALLOW_TOKENLESS_UPLOADS`, token TTL, the 24 h unclaimed-upload TTL, sweep interval).
- `src/routes/upload.route.ts` — REST (not Socket.io) endpoints for image uploads (`/api/upload`, `/api/upload/emoji`), animated-GIF custom emoji (`/api/upload/emoji-animated`, its own larger size cap + GIF-only MIME allowlist), and custom text-channel icons (`/api/upload/channel-icon`, shares the emoji route's 512KB cap, no approval-queue gating since channel icons are already admin-only via `UPDATE_CHANNEL`'s `MANAGE_CHANNELS` check); dual-backend (local disk vs Cloudinary) selected by presence of `CLOUDINARY_*` env vars. Every route authenticates BEFORE reading the body (`Authorization: Bearer <token>`; a bad token is a 401, no header is accepted as an ownerless upload while `ALLOW_TOKENLESS_UPLOADS` is true) and records the file in the ledger, replying `{ url, publicId, uploadId }`.
- `prisma/schema.prisma` — source of truth for the data model; `prisma/seed.ts` creates the default server/channels/roles (idempotent, upsert-based). `scripts/prune-orphan-uploads.mjs` (`npm run uploads:prune`) is plain ESM so it runs in the production image; its pure logic is exported and typed by a sibling `.d.mts` so a vitest test can import it.
- `src/__tests__/` — vitest unit tests (`channel-tree`, `permissions`, `socket-ownership`, `reaction.service`, `message-text`) — pure-logic tests, no DB/Redis required. The Socket.io handlers themselves are not unit-tested; keep logic that needs testing in a pure service like these. Phase 17 added `avatar.service`, `profile.service`, `pagination.service` and `identity.service` tests (the latter generates real Ed25519 keys). Phase 16 added `stored-file.service`, `attachment.service`, `reply.service` and `prune-orphan-uploads` tests (still pure logic — anything touching Postgres was verified against a throwaway database, see below).

## Conventions worth knowing

- Anything `userId`-keyed that a `disconnect` can tear down (mediasoup session, presence, the grace timer) must be guarded by `SocketOwnership` — a user can have an old and a new socket at once, and the stale one's late disconnect must not touch the live one's state.
- Identity (PRD 17.12): a user id is public, never proof. `USER_JOIN_SERVER` runs `decideIdentity()` after the password/ban checks and BEFORE any write; the nonce comes from `socket.data` (never the payload) and is consumed whatever the outcome; binding is a compare-and-set on `publicKey IS NULL`. Anything new that acts as a user must take the user id from an authenticated socket (`socket.data.userId` after a join) or a server-issued ticket — never from a payload. Viewer sockets authenticate with a ticket; the legacy id path is only for unbound ids with a live session while unsigned joins are allowed.
- Client address (PRD 18.2): read it ONLY from `socket.data.clientAddress`, which `index.ts`'s `io.use()` sets with `resolveClientAddress()`. Never read `x-forwarded-for`/`cf-connecting-ip` yourself — forwarded headers count only from peers listed in `TRUST_PROXY`, otherwise any client could choose its own address (bans, the identity log and approval limits all key on it).
- Access (PRD 18.18): classify every NEW client→server event in `EVENT_ACCESS` (`access.service.ts`) — `member` unless it is sign-in, a structural read, the user's own settings, or a moderator/admin action with its own permission check. Content that only members may see is broadcast with `io.to(membersRoom(serverId))`, never `server:<id>`; structural events (tree, presence, avatars, settings) stay on `server:`. The cached `socket.data.hasAccess` is for this gate only — moderation checks keep `requirePermission()`. Anything that changes a user's roles must call `applyAccessChange()`. Voice teardown from the server side goes through `voice-session.service.ts` (`removeSocketFromChannel`), shared by KICK_USER and access loss.
- Membership (PRD 18.17): `user_servers` is written on every join (next to the role upserts) and by the approval transaction; User Management lists members OR role holders (`adminUsersWhere()`/`mapAdminUser()` in `services/admin-users.ts`), so a user whose last role was removed stays listed with `roles: []`. A new place that creates a user must also create the membership. Note the related pre-existing behavior: every join re-adds the `role-default` (Member) role — removing Member does not keep anyone out (PRD 18.18 changes that).
- Packet guard (PRD 18.8): `services/packet-guard.ts` runs on EVERY incoming event (`socket.use` in `index.ts`) — default-deny until `socket.data.userId` + `serverId` exist (allowlist: `PRE_JOIN_EVENTS`), and it normalizes the packet so `(payload, ack)` and `(ack)` handlers always receive a payload/ack function. Name the callback `ack` in a new `(ack) => …` handler (that is how the guard recognizes it). Never rely on a handler for the sign-in check; do not add pre-sign-in events lightly.
- Invite codes (PRD 18.9): never store, log or return a plain code (the `CREATE_INVITE` ack is the only place it leaves); the join gate only checks, and the use is claimed with `claimInviteUse()` on the transaction that creates the user (or the approval transaction) — keep it there, a claim outside it can leak a use on a failed join. Add any new refusal state to the single generic `INVITE_INVALID` message so codes can't be probed. Expiry is compared with the database clock (`now()` in SQL), never `Date.now()`.
- Approval queue (PRD 18.8): a waiting person has NO `users` row, role or presence — only a `pending_approvals` row and `socket.data.pendingUserId`. Gate decisions live in the pure `decideApprovalGate()`; the gate in `USER_JOIN_SERVER` runs AFTER the identity decision and the address-ban check and BEFORE any write; the designated admin is exempt. `approval.handler.ts` is BAN_USER-gated except flipping the switch (ADMIN, `UPDATE_SERVER_SETTINGS`). Rejecting with a ban goes through `executeBan()` (`ban.service.ts`, shared with `BAN_USER`) so the address options behave identically. Moderators are kept in the `moderators:<serverId>` room by `syncModeratorRoom()` — call it after anything that changes someone's roles.
- Address bans (PRD 18.7): enforce through `addressBans.isBanned(socket.data.clientAddress)` only, never a header; keep the "designated admin gets in" exemption in `USER_JOIN_SERVER` (it must come AFTER the identity decision); call `reloadAddressBans()` after any `banned_addresses` write; the address half of `BAN_USER` must never fail the user ban (return a `warning`).
- Identity log (PRD 18.4): record with `void recordIdentityEvent(app, …)` — never `await` it in `USER_JOIN_SERVER`, it swallows its own errors by design. Anything that reads the log (it carries client addresses) checks ADMIN inside the handler. `GET_SERVER_SETTINGS` adds the identity-policy fields for ADMIN callers only and does so with `getUserPermissions`/`isAdmin`, NOT `requirePermission` (which emits an ERROR event on denial — wrong for a probe every user makes). `requireSignedIdentity()` is env-over-database: the stored value is mirrored in memory (`setDbRequireSigned`) so a join never reads the database.
- Server summary (PRD 19 A1): `GET_SERVER_SUMMARY` (`nudge.handler.ts`, next to `GET_SERVER_SETTINGS`) is open to every signed-in user, restricted ones included, so it must stay free of admin-only data (addresses, fingerprints, keys, identity-policy details). The counting rules are the pure `buildServerSummary()` in `services/server-summary.ts`; roles are aggregated for ONE server with `aggregatePermissions()` — never OR a user's roles across servers. Counts are per `userId` (= per install), not per person.
- Server icon (PRD 19 A2): `POST /api/upload/server-icon` is the first upload route that opts in to byte validation (`handleUpload`'s `UploadOptions`: `requireToken`, `authorize`, `validate`) — ADMIN and a token are checked BEFORE the body is read, then `validateServerIcon()` (`services/image-sniff.ts`, pure, no dependency, never SVG) sniffs the real bytes, requires them to match the declared MIME type and 256–4096 px, and names the stored file from the SNIFFED type (`server-icon.<ext>`), never the client's name. The icon is set only by `UPDATE_SERVER_SETTINGS { iconUploadId }` (claim + `servers.update` in one transaction; `null` removes; the replaced file is released after the commit); `servers.iconUrl` is counted by `countFileReferences()`. `@fastify/static` applies its own Cache-Control AFTER `setHeaders`, so `index.ts` turns `cacheControl` off and sets it in `setHeaders` (icons immutable, everything else `public, max-age=0`). Sniffing the other routes is A10.
- Voice session timer (PRD 19 A3): `voiceSessionStartedAt` lives in `services/voice-session.service.ts` (one map, re-exported by `connection.handler.ts`). Any NEW `PRESENCE_UPDATE` for a voice room must be built with `presencePayload()` — it carries `sessionStartedAt` and clears the entry when the occupant set is empty; hand-building `{ channelId, occupants }` drops the timer on every client. Trees (join and broadcast) are annotated with `annotateSessionStarts()`. Never clear the map from a raw `disconnect` path (the grace period keeps the room occupied).
- Screen share cap (PRD 19 A4): a `screen-video` PRODUCE counts live shares, produces and assigns `session.screenVideoProducer` inside ONE `withChannelLock(channelId, …)` (`services/channel-lock.ts`), otherwise two simultaneous last-slot requests both pass; `SET_SCREEN_SHARE_STATE` mirrors the check. `MediasoupService.countScreenVideoProducers()` checks `.closed` and takes an `exceptKey` so a sharer never counts against themselves. The cap is `MAX_SCREEN_SHARES_PER_ROOM` in shared-types; the client mirrors the number. Mic and screen-audio never take the lock.
- Avatars: never accept or store a client-supplied avatar URL — only `{ provider, hash }` through `parseAvatarSelection()`/`buildAvatarUrl()`.
- History fetches go through `parseHistoryQuery()`; add `after`-style paging to any new message list the same way (one extra row per direction).
- Reactions are aggregated only via `reaction.service.ts`; message/DM history load every reactor's nickname in one query per page (`loadReactorNicknames`).
- New Socket.io events always start in `packages/shared-types/src/socket-events.ts` (both `ClientToServerEvents` and `ServerToClientEvents` as needed), then get a handler here.
- Presence (who's online, who's in which channel) lives in Redis, not Postgres — don't add DB queries for that; use `presence.service.ts`.
- Permission checks go through `hasPermission`/`hasAnyPermission`/`isAdmin` in `permissions.service.ts`, never inline bit math in a handler.
- **Never trust a client-supplied file URL or Cloudinary `public_id`** — not to persist, not to delete. Files are used by *claiming* an upload id (`claimUploads()`, an atomic compare-and-set) on the **same `$transaction` client** as the write that uses it, and are removed with `releaseStoredFile()` only *after* the referencing row is gone (DB first, so a failed delete never loses a file), using the ledger's own url/public_id and a reference-count check (`countFileReferences` matches local files by name, so the relative and the pre-v2.5.0 absolute URL forms both count). Any new feature that stores a file must go through the ledger (add a `StoredFileKind`), and any new table that references files must be added to `countFileReferences()` and `collectChannelFileUrls()` or its files will be deleted from under it. Details and the threat model are in the root `AGENTS.md`.
- Replies: validate with `parseReplyToId` + `isChannelReplyAllowed`/`isDmReplyAllowed` (a target in another channel/conversation is refused; a missing one is accepted), never inline; add `loadReplyPreviews()` to any new path that returns messages so snippets stay one query per page.
- Migrations that need a backfill: generate the SQL with `npx prisma migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma --shadow-database-url <scratch db> --script` (it never touches the dev DB), then hand-append the backfill. Verify on a throwaway database — create `reson8_scratch` in the dev Postgres container, apply the older migrations with `psql`, insert realistic rows, apply the new one, then `prisma migrate deploy` on a fresh scratch DB — and drop it afterwards. Don't use `migrate dev` to test a migration against the dev database.
- Booting the real server for an end-to-end test: `dotenv/config` loads `apps/server/.env` **regardless of the working directory**, and never overrides variables that are already set — so pass explicit `DATABASE_URL`, `REDIS_URL` (use a separate Redis db number), `PORT`, and an empty `SERVER_PRIVATE_PASSWORD=` or the test silently talks to your dev database / hits the join password. The server also reads `package.json` from the cwd (version config), so a scratch cwd needs a copy. Seed only *after* the server has created its `Server` row.
- `resolveNickname()` in `connection.handler.ts` is the pattern for any lookup that might race a Redis presence write during reconnect — prefer Redis, fall back to Postgres, only default to a placeholder as a last resort.
