PROJECT OVERVIEW
================
Reson8 is a high-performance, self-hosted voice and text communication platform
for desktop (Electron). It replicates the TeamSpeak 3 experience — low-latency
voice, hierarchical channel trees, and private server ownership — while
integrating modern persistent text channels.

Tech Stack: Electron + TypeScript, Fastify + Socket.io, mediasoup (SFU),
PostgreSQL + Prisma, Redis, Docker.

Monorepo structure:
  apps/client/            — Electron desktop client
  apps/server/             — Node.js signaling + SFU server
  packages/shared-types/    — Shared DTOs, enums, and Socket.io event types

For build commands, environment variables, ports, and architecture details,
see the root CLAUDE.md (and apps/client/CLAUDE.md, apps/server/CLAUDE.md) —
not duplicated here to avoid drift between docs.

Feature/Fix: PRD 16.1 — "Don't warn me again" for NSFW channels

  Problem: Opening an NSFW text channel always showed the confirmation modal,
  even after the user had already accepted it many times, and even when
  re-focusing a tab that was already open. Users asked to be able to dismiss
  the warning for good.

  Solution: The NSFW modal now has a "Don't warn me again for NSFW channels"
  checkbox, and a new "Content" section in Settings -> Application has a
  "Warn before opening NSFW channels" toggle to turn the warning back on.
  The preference is one global per-install flag (decided with the user:
  covers all NSFW channels, not one channel).

  Client Changes:
    - renderer.ts: isNsfwWarningEnabled()/setNsfwWarningEnabled() accessors
      (try/catch around localStorage; anything other than an explicit "true"
      dismissal means warn, which is also the fallback when storage is
      unavailable).
    - handleChannelClick(): the NSFW branch now prompts only when
      node.isNsfw && isNsfwWarningEnabled() && !chatTabs.has(node.id). An
      already-open NSFW tab was confirmed when it was opened, so re-focusing
      it from the tree no longer re-prompts.
    - The checkbox is reset to unchecked every time the modal opens. The
      tick is persisted only when Continue is pressed; Cancel and backdrop
      close discard it.
    - openSettingsPanel() re-syncs the Settings toggle from storage on every
      open, since the modal can change the value while Settings is closed.
      The toggle shows "checked = warn" (inverse of the stored key) and
      takes effect immediately on change.
    - index.html: checkbox row in #nsfw-confirm-modal with a new
      .modal-check-row style; "Content" section + #chk-nsfw-warn toggle row
      in the Application panel (PRD 16.2 adds its row to the same section).

  localStorage Keys:
    reson8-nsfw-warning-dismissed = "true" when the warning is dismissed
    (key absent = warn, the default)

Feature/Fix: PRD 16.2 — Optional image blurring in NSFW channels (per user)

  Problem: Every image in an NSFW text channel was always blurred behind a
  "click to reveal" overlay, with no way for a user who doesn't want that to
  turn it off.

  Solution: A per-user toggle, "Blur images in NSFW channels", in Settings ->
  Application -> Content (the section created by PRD 16.1). On by default,
  which keeps today's rendering exactly. Off shows NSFW-channel images like
  any other image (no blur, no overlay); clicking still opens the viewer.

  Client Changes:
    - The switch is CSS-driven instead of a render-time branch: the message
      builder still always wraps NSFW images in .msg-image-nsfw-wrap +
      overlay, and a `body.nsfw-blur-off` class overrides the blur
      (filter/transform none) and hides the overlay. Flipping the toggle
      therefore updates every already-rendered message instantly, in both
      directions, with no re-render or scroll jump. The image's own click
      handler (-> openLightbox) keeps working once the overlay is hidden.
    - renderer.ts: isNsfwBlurEnabled()/setNsfwBlurEnabled()/
      applyNsfwBlurPreference() (try/catch around localStorage; only an
      explicit "false" disables the blur), applied once at startup, on the
      toggle's change event, and the checkbox is re-synced in
      openSettingsPanel().
    - index.html: the two body.nsfw-blur-off rules next to the NSFW thumbnail
      CSS, and the #chk-nsfw-blur toggle row in the Content section.
    - DM images were never blurred and are unaffected either way.
    - PRD 16.10 (multi-image messages) must keep wrapping every NSFW image
      in .msg-image-nsfw-wrap so this toggle keeps covering each tile.

  localStorage Keys:
    reson8-nsfw-blur-images = "false" when blurring is off (absent = on)

Feature/Fix: PRD 16.3 — Highlight the text channel being viewed (eye icon)

  Problem: On busy servers there was no indication in the channel tree of
  which text channel's chat tab was currently open. Text channels never got
  the .active class (that only marks the connected voice channel), so the
  open chat looked identical to every other row.

  Solution: The text channel whose tab is the active tab now gets a
  `.viewing` highlight (one step above the hover tint, below the joined-voice
  .active style) plus a small muted eye SVG at the far right of the row,
  with a "You're viewing this channel" tooltip.

  Client Changes:
    - New `.tree-channel.viewing` class, deliberately separate from `.active`
      so the voice-channel semantics are untouched; `.viewing:hover` keeps the
      same background so hovering doesn't flicker it lighter/darker.
    - renderer.ts: createViewingIcon() builds the eye span (aria-label
      "Currently viewing"); renderChannel() adds the class + icon when
      node.id === activeTabId (text channels only), appended last so the
      name's flex:1 pushes it to the right of any unread dot / NSFW badge.
    - updateViewingIndicator() is a targeted DOM update, NOT renderTree():
      a full re-render would lose collapsed-category state (same reason
      markChannelUnread() avoids it). It clears the previous row, then marks
      the row matching activeTabId; the Server Log and DM tabs match no
      `.tree-channel[data-channel-id]` row, so they just clear the highlight.
    - Called at the end of switchTab(); closeTab() already routes through
      switchTab("server-log") when the active tab is closed, and any full
      renderTree() re-derives the state from activeTabId in renderChannel().

Feature/Fix: PRD 16.4 — Mute text channels (per user, client-side)

  Problem: On busy servers a lot of text channels with unread dots clutter the
  tree, and there was no way for a user to opt out of the notifications for
  channels they don't care about.

  Solution: Any user can right-click a text channel and choose "Mute Channel" /
  "Unmute Channel". A muted channel shows no unread dot or bold unread name and
  is rendered faded (icon and name) like a disabled row, but stays fully
  clickable. It is a purely local preference: no permission, no server event,
  no wire-format change.

  Client Changes:
    - Menu: the mute item is first in the channel context menu, followed by a
      new .ctx-menu-divider, and is offered only on openable text channels
      (renderChannel passes canMute=true; voice channels and category rows via
      renderCategory do not get it).
    - Visuals: `.tree-channel.muted .ch-icon/.ch-name` at opacity 0.45 (0.7 on
      hover so the name stays readable). Combines with the PRD 16.3 `.viewing`
      highlight.
    - Unread is still TRACKED while muted: unreadChannelIds, markChannelRead()
      and the server's per-user read cursor are untouched. Only the painting is
      suppressed (renderChannel skips the .unread class/dot for muted
      channels; markChannelUnread() adds to the set then returns before
      touching the DOM). Unmuting therefore reveals what arrived meanwhile.
    - setChannelMuted() persists, then applyChannelMuteState() does a targeted
      DOM update (toggles .muted/.unread and the dot) instead of renderTree(),
      which would reset collapsed categories.
    - Persistence: JSON { [serverId]: channelId[] } so different Reson8 servers
      never mix lists. Reads validate the shape (malformed or unavailable
      storage is treated as empty) and every access is in try/catch. The set
      is loaded per server from the channel-tree handler (ensureMutedChannels
      Loaded) and reset on disconnect.
    - Pruning: each channel-tree update drops muted ids whose channel no longer
      exists, so deleted channels don't accumulate. Skipped for an empty tree
      (a transient state) so a blip can never wipe the list.

  localStorage Keys:
    reson8-muted-channels = JSON object mapping serverId -> array of muted
    channel ids (key/entry removed when a server's list becomes empty)

Feature/Fix: PRD 16.5 — Floating message action toolbar (foundation for 16.6 and 16.11)

  Problem: Message actions (react, edit, pin, delete) were appended inside the
  reaction strip, which had `min-height: 20px` on EVERY message so the
  hover-only buttons had somewhere to appear. That reserved a fixed empty row
  under each message, which defeats message grouping (PRD 16.6) and left no
  home for the Reply button (PRD 16.11).

  Solution: Structural refactor only — every existing action keeps working,
  it just moves into a floating hover toolbar at the message's top-right
  (user-approved, per print_discord_grouped_messages.png).

  Client Changes:
    - buildReactionBar(msgId, isDm, reactions) now builds ONLY the pills,
      plus a trailing small "add reaction" button once at least one pill
      exists. The strip is `display: none` unless it has `.has-reactions`, so
      it takes no space until a reaction is added and "reinstates" its space
      the moment one is (updateReactionBar() rebuilds it on reaction-updated).
      min-height was removed. The old ownerId parameter and the owner lookup
      in updateReactionBar() are gone since the strip no longer holds
      owner-only buttons.
    - New buildMessageActions(msgId, isDm, ownerId): a role="toolbar" with
      React and (own messages) Delete. attachEditButton()/attachPinButton()
      now take the toolbar and slot in through insertToolbarButton(), which
      inserts before Delete, giving the deterministic order React, Edit, Pin,
      Delete (PRD 16.11 will slot Reply right after React). Buttons keep their
      btn-react / btn-edit-msg / btn-pin-msg / btn-delete-msg classes since
      other code queries them; the edit button's 2-minute self-removal timer
      is unchanged. All buttons got aria-labels and type="button".
    - Visibility: the toolbar is absolute (top -14px, right 8px), hidden by
      default, shown on `.chat-msg:hover`, `:focus-within` (keyboard access)
      and `.actions-open`, which openReactionPicker() sets on the message so
      the toolbar doesn't vanish as the pointer moves into the picker;
      closeEmojiPicker() clears it. The picker's left edge is now clamped to
      the window, since the toolbar sits at the message's right edge.
    - A delegated mouseover adds `.actions-inside` (toolbar tucked inside at
      top 2px) for a message within ~18px of its scroll container's top, so
      the first message's toolbar isn't clipped.
    - `.chat-msg` got position: relative, a faint hover tint, and 6px
      padding balanced by -6px margin so the tint has breathing room without
      shifting content.
    - Pinned marker: the old `.btn-pin-msg.active` stayed visible without

Feature/Fix: PRD 16.6 — Group consecutive messages, header layout, HH:MM timestamps

  Problem: Every message was an independent inline line ("HH:MM:SS nick text")
  with its own nickname, seconds-resolution timestamp and margins, so busy
  chats were cluttered with repeated nicknames.

  Solution: Discord-style layout (user-approved). Each message has a header
  line (nickname + HH:MM) and its text on its own line(s) below. A message
  from the same author within 5 minutes of the FIRST message of the current
  group becomes a "continuation": no header, tight spacing. Applies to
  channel and DM chats; the Server Log is untouched.

  Client Changes:
    - DOM: both builders now share buildMessageShell(): .chat-msg >
      .msg-header (.msg-nick + .msg-time) + .msg-body (.msg-text +
      .msg-edited), with data-created-at. The header is always rendered and
      hidden by CSS on `.msg-continuation`, so regrouping is only a class
      toggle.
    - Rule: shouldGroupMessage() is a pure function — same author, createdAt
      not before the previous message, and createdAt minus the GROUP's first
      message's time under GROUP_WINDOW_MS (5 min). Any non-.chat-msg sibling
      between two messages (date divider, "Unread Messages" separator,
      sentinels) breaks the group. A reply (data-is-reply="1", set by PRD
      16.11) always opens its own group; that condition is a no-op until then.
    - applyGrouping(el) recomputes one element from its previous sibling and
      returns whether it changed (data-grouped, data-group-start, classes).
      regroupFrom(startEl) always recomputes the start and keeps cascading
      only while elements actually change, which bounds the work.
    - Where it runs: append (renderChatMessage/renderDmMessage, covering
      initial load, live messages, jump/rebuild) calls applyGrouping right
      after insertion; prependOlderMessages() calls regroupFrom after
      inserting the page, which also repairs the junction with the
      previously-first message (inside the scroll-anchor measurement, so
      scroll position stays correct); removeMessageElement() regroups from
      the next message after a delete (a removed head promotes the next line;
      removing an in-between message can merge two runs).
    - Time: formatMessageTime() = toLocaleTimeString with hour+minute only
      (respects the OS 12/24h preference). The header time's tooltip, and a
      continuation's tooltip, show the full date and time. The continuation
      tooltip is set on the whole message element rather than on .msg-body,
      because an image-only continuation has an empty body that can't be
      hovered. The Server Log's own timestamps are a separate path, unchanged.
    - "(edited)" moved from after the time to the end of .msg-body
      (ensureEditedLabel(), used by the edit and edit-broadcast paths), and is
      hidden via :has() while the inline edit textarea is open.
    - Spacing: group start margin-top 8px (0 right after a sentinel, date
      divider or unread separator); continuation margin-top -2px to cancel
      the container's flex gap. Reactions need no special handling: PRD 16.5
      made the strip take space only when it has reactions.
    - Solo-emoji messages, Markdown block/inline text, long-message
      truncation and link previews operate on .msg-text / the message
      element as before; block text lost its old margin-top since text is now
      always below the header.

    apps/client/src/renderer/index.html
    apps/client/src/renderer/renderer.ts

  Verification:
    npx tsc --noEmit in apps/client passes; npm run test:markdown passes. The

Feature/Fix: PRD 16.7 — Emoji autocomplete while typing :name

  Problem: Emoji could only be inserted through the picker. Custom emoji could
  be typed as :name: but only if the user remembered the exact name, and
  Unicode emoji had no typed form at all.

  Solution: Typing ":" followed by a letter in the chat box opens a floating
  card just above the colon (per print_discord_emoji_autocomplete.png) with
  emoji on the left and :name: on the right, covering both custom and Unicode
  emoji. It filters as the user types and closes on no match, a closing colon,
  whitespace, blur, tab switch, send, or the emoji picker opening.

  Client Changes:
    - Trigger: /(?:^|[\s([{"'])(:([a-zA-Z][a-zA-Z0-9_+-]{0,31}))$/ against the
      text before the caret, so "http://x", "10:30" and "a:b" never trigger.
      Group 1 is ":query", group 2 is "query". Ignored during IME composition.
    - Search (searchEmojiForAutocomplete): ranked name prefix, name-word
      prefix, keyword prefix (how ":laug" finds 🤣, like the reference's
      :rofl:), then substring; ties favour custom emoji, then shorter names;
      max 10. The Unicode index is built once lazily; the custom list is read
      live. toEmojiSnakeName() is now shared with emojiShortName() (reaction
      card) so both name an emoji identically.
    - Card: one shared #emoji-autocomplete element (header "Emoji matching
      :query", rows with glyph/<img> + name, role=listbox/option with
      aria-activedescendant on the textarea). Opens upward, left-aligned to the
      colon, clamped inside the window, max-height fitted to the space above.
      The colon's coordinates come from a local mirror-div helper
      (getTextareaCharCoords) instead of a dependency (no bundler).
    - Keys: Up/Down move (wrapping), Enter/Tab select WITHOUT sending (the
      handler runs first in the chatInput keydown), Escape closes only the card
      (stopPropagation, so PRD 16.11's reply cancel won't also fire),
      Shift+Enter closes the card and inserts a newline. Mouse: hover
      highlights, mousedown is prevented so the textarea keeps focus.
    - Selecting inserts the emoji CHARACTER for Unicode (only custom :name:
      text renders as an emoji) and :name: for custom, plus a trailing space
      unless whitespace already follows. Typing the closing ":" of a complete
      Unicode name (":red_heart:") converts it in place; custom names are left
      as typed since they already render.
    - State/element refs live next to chatInput at the top of the file, not
      beside the logic, because switchTab()/sendChatMessage() call
      closeEmojiAutocomplete() and can run before the later section evaluates
      (a const TDZ otherwise).
    - Out of scope: the inline message-edit textarea and the picker's own
      search box (the module takes the textarea from chatInput only).

--- Entry: 07/10/2026 ---

Feature/Fix: PRD 16.8 — Server-side upload ownership (stored-file ledger + upload tokens) [SECURITY]

  Problem: The server trusted file URLs and Cloudinary public_ids sent by the
  client — on SEND_MESSAGE / SEND_DIRECT_MESSAGE, CREATE_CUSTOM_EMOJI and
  UPDATE_CHANNEL (icon) — then later DELETED whatever those values pointed at
  (deleting a message/DM, an admin rejecting an emoji, replacing a channel
  icon). A modified client could reference another user's already-posted file
  from its own message and delete that message to get the victim's file
  removed, pass an arbitrary public_id to cloudinary.destroy() (any asset in
  the server's Cloudinary account), or submit an emoji pointing at someone's
  image for an admin to reject. It could also post an external URL as an
  "attachment" (a tracking pixel logging every viewer's IP).

  Solution: The server now keeps its own record of every file it stores (the
  `stored_files` ledger). Anything that wants to USE a file must claim it
  there first; the URL/public_id that get persisted — and later deleted —
  always come from the ledger, never from a client value.

  Database Changes:
    - New StoredFile model + StoredFileKind enum (MESSAGE_ATTACHMENT,
      CUSTOM_EMOJI, CHANNEL_ICON): url (unique, canonical), publicId, kind,
      ownerId (null = tokenless upload), claimedAt (null = unclaimed),
      createdAt, index on (claimedAt, createdAt) for PRD 16.9's sweeper.
    - Migration 20261007120000_add_stored_file_ledger, with a backfill: every
      file already referenced by a message, DM, custom emoji or channel icon
      becomes a claimed ledger row. Legacy absolute local URLs are normalized
      to "/uploads/<file>" (regexp_replace); the same file under two hosts
      collapses to one row (ON CONFLICT DO NOTHING); Cloudinary URLs and
      public_ids pass through. NOT yet applied to the dev database (see
      Verification / Next Step).

  Server Changes:
    - routes/upload.route.ts: authenticates BEFORE reading the multipart body
      (Authorization: Bearer <token>; unknown/expired/malformed token -> 401;
      no header -> accepted as ownerless while ALLOW_TOKENLESS_UPLOADS is
      true), then records the file in the ledger and replies { url, publicId,
      uploadId }. If recording fails the stored file is removed. Each route
      passes its kind.
    - handlers/upload.handler.ts (NEW): REQUEST_UPLOAD_TOKEN. Mints a random
      32-byte token mapped to the socket's userId in Redis, stored under the
      SHA-256 of the token (a Redis dump holds no usable tokens), 10-minute
      TTL. Refused for viewer sockets and sockets that haven't joined.
    - services/stored-file.service.ts (NEW): claimUploads() is one atomic
      `UPDATE ... WHERE claimedAt IS NULL AND kind = ? AND (ownerId = me OR
      ownerId IS NULL) RETURNING` — a compare-and-set, so concurrent claims
      can't both win and there's no read-then-write window. It runs on the
      SAME transaction client as the write that uses the file (message, DM,
      emoji, channel update), so a failed write rolls the claim back and a
      failed claim aborts the write. releaseStoredFile() runs AFTER the
      referencing row is removed (DB first) and deletes the physical file only
      if the file is in the ledger (a URL the server never stored is never
      touched) and nothing else still references it (matched by file name, so
      relative and legacy absolute forms both count). Also: normalizeUploadUrl,
      parseClaimRequest, token helpers, UploadClaimError.

Feature/Fix: PRD 16.9 — Orphaned upload cleanup (discard, sweeper, channel delete, one-time prune)

  Problem: Files are uploaded the moment a user picks them, long before a
  message, emoji or icon uses them, so abandoned ones piled up forever: an
  image picked then removed or never sent, an emoji/icon upload that failed or
  was cancelled after the file went up, and — because messages cascade-delete
  with their channel but their files didn't — every image in a deleted
  channel. Files left from before PRD 16.8 had the same problem.

  Solution: Four layers, all built on the PRD 16.8 ledger (which is what
  makes "unreferenced" knowable).

  Server Changes:
    - DISCARD_UPLOAD (new socket event, upload.handler.ts): throws away the
      caller's own UNCLAIMED upload at once. discardUnclaimedUpload() is a
      single atomic `DELETE ... WHERE claimedAt IS NULL AND ownerId = me
      RETURNING`, so an attached file, someone else's upload, or an ownerless
      (legacy) upload can never be discarded this way. Viewer sockets and
      malformed ids are refused.
    - Sweeper (services/upload-sweeper.ts, started from index.ts): first run
      60s after boot, then hourly, never overlapping, timers unref()'d and
      cleared in Fastify's onClose. sweepUnclaimedUploads() deletes unclaimed
      uploads older than 24h in batches of 500. The `claimedAt IS NULL` test is
      repeated on the OUTER delete on purpose: if a claim lands between the
      batch being picked and the delete, Postgres re-checks the outer predicate
      against the claimed row and skips it (a sub-select alone is not
      re-evaluated), so a file that was just attached is never swept. Each
      file still goes through the reference-count check before it is
      physically deleted. Constants live in config/upload.config.ts.
    - DELETE_CHANNEL: collectChannelFileUrls() gathers the channel's message
      attachments and its own icon BEFORE the delete; the channel is deleted
      (DB first), the ack is sent, then releaseStoredFiles() runs in the
      background with bounded concurrency (20) so a channel with thousands of
      images never delays the ack. Child channels are re-parented, not
      deleted, so their files are untouched, and a file another row still
      references (e.g. a DM) survives via the reference-count guard.
    - Prune script (scripts/prune-orphan-uploads.mjs + .d.mts, `npm run
      uploads:prune`): plain ESM so it runs in the production image (the
      Dockerfile already copies all of apps/server). Dry run by default;
      --apply deletes; --min-age-hours (default 24) protects in-flight uploads;
      --dir. A file is kept if its name is in the ledger or referenced by any
      messages/direct_messages/custom_emojis/channels row in ANY URL form
      (relative or the old absolute), or by the `attachments` table once PRD
      16.10 creates it (detected with to_regclass, so this script needs no
      change then). Dotfiles are skipped; an unknown flag exits 2 with usage.
      Local disk only — Cloudinary is documented as a manual step.
    - New helpers in stored-file.service.ts: mapWithConcurrency (never
      rejects), discardUnclaimedUpload, sweepUnclaimedUploads,
      collectChannelFileUrls, releaseStoredFiles.

  Client Changes:
    - preload.ts: discardUpload(uploadId) with a 5s timeout (a pre-v2.5.0
      server never answers; harmless, the sweep covers it).
    - renderer.ts: a fire-and-forget discardUpload() helper that can never
      block or fail the UI. Called when the ✕ on a ready attachment is
      pressed (new discardPendingAttachment(); sending still just clears the
      tray and does NOT discard), when a new image replaces the pending one,
      and when an emoji / animated-emoji / channel-icon submit fails after its
      file was uploaded (try/finally around the submit). A send that fails
      leaves its upload for the sweeper.

  Shared Types Changes: DISCARD_UPLOAD event (additive).

  Docs: README gets a "Maintenance — Uploaded Files" section (what is cleaned
  automatically, the prune script for local disk incl. the docker compose exec
  form, and the manual Cloudinary comparison).
