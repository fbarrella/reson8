Feature/Fix: Server-side TLS, Caddy setup and trusted client addresses (PRD 18.2)

  Problem: The server only spoke plain HTTP/WS, so chat, DMs, upload tokens
  and the whole Socket.io session were readable on the network path unless a
  self-hoster happened to put a proxy in front. Separately, the address used
  in logs came from `cf-connecting-ip`/`x-forwarded-for` taken from ANY
  client, so it was whatever the client claimed — harmless while it only fed
  logs, but address bans (18.7), the identity log (18.4) and the approval
  limits (18.8) all key on it.

  Solution:
    Trusted client address
      - services/client-address.ts (pure): `parseTrustProxy()`,
        `normalizeAddress()` (::ffff:a.b.c.d -> IPv4, zone ids dropped),
        `resolveClientAddress()` built on @fastify/proxy-addr (now a direct
        dependency, same major Fastify 5 uses). Unset/false trusts nothing;
        "true" is REFUSED with a warning (trusting every hop makes the address
        client-controlled again); an invalid list also trusts nothing. A
        non-IP header value can never become the address.
      - index.ts's `io.use()` middleware sets `socket.data.clientAddress`
        for primary and viewer sockets before any handler runs (deviation
        from the PRD, which put it in the connection handler: 18.7 needs it
        at handshake time). `connection.handler.ts` just reads it. Fastify
        gets the same list via its `trustProxy` option.
    Native TLS
      - config/tls.config.ts: `readTlsEnv()` (both or neither; only one is a
        startup error), `loadTlsMaterial()` (a mismatched key/cert pair is
        rejected by `createSecureContext`), `watchTlsFiles()` (watches the
        DIRECTORIES because renewals swap files/symlinks, debounced 1 s,
        12 h safety reload, a failed reload keeps the previous certificate).
      - index.ts: `Fastify({ https })` when configured, minVersion TLSv1.2,
        startup log line states the mode; an unreadable certificate stops
        the boot — it never falls back to plain HTTP.
    Deployment
      - docker-compose.caddy.yml + deploy/caddy/Caddyfile (caddy:2.11-alpine,
        looked up on Docker Hub, never `latest`): automatic Let's Encrypt,
        RESON8_DOMAIN required (clear error without it), sets TRUST_PROXY to
        uniquelocal by default. Port 9800 stays published for pre-2.7.0
        clients.
      - docker-compose.yml: passes TLS_CERT_FILE/TLS_KEY_FILE/TRUST_PROXY, a
        commented ./certs volume. It also passes REQUIRE_SIGNED_IDENTITY,
        ADMIN_KEY_FINGERPRINT and AUTH_ALLOWED_HOSTS, which 2.6.0 documented
        but docker-compose.yml never forwarded (so they could not be set in
        a compose deployment) — empty defaults, same as unset.
      - README "Encryption (HTTPS)" section (Caddy, native TLS with the
        openssl recipe, nginx block, TRUST_PROXY), .env.example block.

  Behavior change to call out in the release notes: behind a proxy WITHOUT
  TRUST_PROXY, logs now show the proxy's address instead of the forwarded one.

Feature/Fix: Encrypted connections in the client — HTTPS first, trusted self-signed certificates, lock indicator (PRD 18.3)

  Problem: The client always built `http://host[:port]`: a typed `https://`
  was silently stripped and connected over plain HTTP, an IPv6 address could
  not be entered (the box split on ":"), and an empty address quietly became
  `localhost`. There was no way to use a server that has a self-signed
  certificate, and no indication of whether the connection was encrypted.

  Solution:
    Address + decision (pure, tls-trust.ts)
      - `parseServerAddress()`: host, host:port, [::1]:port, optional
        http/https/ws/wss prefix; refuses paths, queries, credentials, bad
        ports with specific messages; an explicit default port (":80") is
        kept because the URL class drops it. `identityHostOf()` is
        byte-identical to what 2.6.0 signed (unit-tested against a copy of
        the old parser) so bound identities and AUTH_ALLOWED_HOSTS keep
        matching. `decideScheme()` is the PRD's table, one test per row.
    Probe + pins (main process)
      - tls-probe.ts classifies a server: trusted / untrusted (+ the
        presented certificate) / no-tls (a plain HTTP server, or a TCP
        server that accepts and never answers) / unreachable. IPC `tls-probe`
        returns the result, any pin and the HTTPS memory in ONE round trip;
        the PEM never reaches the renderer.
      - tls-store.ts (`<userData>/tls-trust.json`, atomic writes, corrupt
        file -> empty): pins by SHA-256 + the "reached over HTTPS" memory.
        `tls-trust-certificate` only pins the certificate the LAST probe of
        that host:port just showed (5-minute window) and never overwrites a
        different existing pin (the SSH model: remove the old trust first).
    Two TLS stacks
      - Socket.io in the preload runs on Node `ws`: a pinned connection is
        given `ca: [pinned PEM]` plus a SHA-256 `checkServerIdentity`.
      - Uploads, images, emoji and the Viewer's media use Chromium:
        `session.defaultSession.setCertificateVerifyProc` accepts a
        certificate ONLY if its SHA-256 equals a pin for that hostname and it
        hasn't expired; everything else gets Chromium's verdict (-3).
      - The Viewer window gets the same pin through `viewer-get-tls-options`
        (main remembers each Viewer's server by webContents id).
    UI
      - Trust modal (fingerprint, subject, names, expiry, reason, Copy;
        Cancel is the focused default) and a red changed-certificate modal
        with no override. Status-bar "Encrypted" / "Not encrypted" lock; a
        per-server dismissible banner for unencrypted connections
        (`reson8-tls-http-warning-dismissed`); Settings -> Application ->
        Trusted certificates list with Remove.
      - A port-less address with nothing speaking TLS on 443 still falls back
        to plain http on port 80 (the old behavior), unless that host was
        reached over HTTPS before. The renderer's duplicate `serverBaseUrl`
        (assigned, never read) is gone; `api.getServerBaseUrl()` replaces it.

  Deviations from the PRD: the probe/store were split into Electron-free
  modules (tls-probe.ts, tls-store.ts taking a path) so they are tested
  against real servers in plain Node; the verify hook has no `errorCode === 0`
  branch (it returns -3 unless pinned, which is the same outcome with less
  code); one `tls-probe` IPC instead of probe + separate pin/remembered calls.

Feature/Fix: Identity log and a "Require signed identity" switch (PRD 18.4)

  Problem: Key binds and refused joins were only written to the server's
  console, so an admin could not see from the app who bound a key (the
  trust-on-first-use window) or who was being refused. REQUIRE_SIGNED_IDENTITY
  was an environment variable only — changing it needed a restart and shell
  access, and nothing said when turning it on was safe.

  Solution:
    Database (migration 20261012120000_add_identity_events, additive)
      - `identity_events` (kind BOUND/RESET/REFUSED, userId, nickname at the
        time, reason KEY not message text, fingerprint, address, host,
        actorId, createdAt; indexes on (serverId, createdAt desc) and
        (userId, createdAt desc)); no relation to User on purpose, so
        refusals of ids that never became users are kept and rows outlive
        users. `servers.requireSignedIdentity` (default false).
    Server
      - identity-events.service.ts: `recordIdentityEvent()` is fire-and-forget
        and never throws; refusals are de-duplicated per (server, user,
        reason, key, address) for 10 min (Redis SET NX) and capped at 10 per
        address per hour (a flood of bogus ids from one address); stored
        fields are length-bounded; `pruneIdentityEvents()` hourly, 90 days.
      - Recorded at every existing log point of the join path (bind, bind on
        create, both race-lost refusals, the identity refusal, a malformed
        proof) and in RESET_IDENTITY_KEY (with the fingerprint that was
        forgotten and the acting admin).
      - GET_IDENTITY_EVENTS: ADMIN-checked inside the handler; cursor
        pagination (`before` + limit 1-100), page decorated with current
        nicknames, actor nicknames and a `privileged` flag (holds ADMIN or
        MANAGE_ROLES) using two small lookups per page.
      - identity.config: the effective value is env-over-database
        (`resolveRequireSigned`); any non-empty env value locks the switch,
        including `false`, and an EMPTY value (what docker-compose passes) is
        treated as unset. The stored value is mirrored in memory
        (`setDbRequireSigned`, loaded at boot and on every update) so a join
        costs no database read; a change takes effect on the next join.
      - GET_SERVER_SETTINGS adds requireSignedIdentity, ...LockedByEnv and
        `unprotectedActiveUsers` (no bound key, joined in the last 30 days)
        for ADMINs only, via getUserPermissions/isAdmin — not
        requirePermission, which would emit a PERMISSION_DENIED error to
        every non-admin on a plain read.
    Client
      - User Management: an "Identity log" button (ADMIN only) opens the log
        in place with Back, "Load older" paging, a per-user "Log" button on
        each row and a "Show everyone" reset. Each row: kind badge, nickname
        (+ "now X" when renamed), a "privileged" tag, plain-words reason,
        address/host, fingerprint, time. All dynamic text via textContent.
      - Settings -> Server: the switch, a note with the unprotected count

Feature/Fix: Allowed connection names managed in Settings — relay protection (PRD 18.5)

  Problem: AUTH_ALLOWED_HOSTS (the only defense against a malicious server
  relaying this server's sign-in challenge to its own visitors) was an
  environment variable only. It is off by default because a server reachable
  under several names must list ALL of them, and an admin had no way to learn
  which names people actually type — so in practice it stayed off.

  Solution:
    - `servers.authAllowedHosts text[]` (migration
      20261013120000_add_auth_allowed_hosts, additive, default empty).
      Effective list = AUTH_ALLOWED_HOSTS when non-empty (locks the setting),
      else the stored list (mirrored in memory like 18.4's switch, loaded at
      boot, refreshed on update — takes effect on the next join). Empty = the
      check is off, as before.
    - auth-hosts.service.ts: `parseAllowedHostsInput` (array, <= 50, each
      host or host:port, lower-cased, de-duplicated, bounded error text),
      `checkAllowedHostsUpdate` (the lock-out guard), observed names in Redis
      (`HINCRBY` count + last-seen per accepted signed join; distinct names
      capped at 200 per server because a client picks its own host string;
      90-day expiry refreshed on use; never throws).
    - The guard: a non-empty list must contain the host the SAVING admin's own
      session was signed for (`socket.data.authHost`, set from the accepted
      proof), else it is refused naming that host, because they'd be refused
      on their next reconnect and could not undo it from the UI. An empty
      list is always allowed, and so is an admin on an unsigned session
      (unsigned joins aren't subject to the host check at all).
    - GET_SERVER_SETTINGS (ADMIN callers only) adds authAllowedHosts,
      authAllowedHostsLockedByEnv and observedAuthHosts (top 50 by use);
      UPDATE_SERVER_SETTINGS accepts authAllowedHosts, refused while the env
      var is set. Refusals already land in the identity log from 18.4 as
      `hostNotAllowed`, so an admin who forgot a name sees it immediately.
    - `npm run identity:clear-hosts [-- --yes]` (plain ESM like uploads:prune,
      typed by a .d.mts): lists the stored list(s), asks, clears, says to
      restart the server (the list lives in memory) and notes when the env
      var still applies. This is the recovery for a list that went stale
      (domain changed) when nobody can open the Settings tab any more.
    - Client: Settings -> Server -> "Connection names (relay protection)":
      the observed names as a checklist with sign-in counts and last-seen, an
      Add box (same shape as the server accepts; Enter adds), a status line

Feature/Fix: Identity key encrypted at rest + passphrase-protected backup (PRD 18.6)

  Problem: The Ed25519 private key was a plain PKCS#8 PEM (0600) in the
  userData folder, so a copy of that folder — a backup, a synced folder — was
  a copy of the identity. And if the key was ever lost there was no recovery
  at all: an unreadable PEM silently minted a NEW key, orphaning every
  identity bound on servers until an admin reset each one.

  Solution:
    Storage (identity-store.ts, Electron-free; identity-key.ts is the adapter)
      - `identity-key.enc` = Electron safeStorage (DPAPI / Keychain /
        libsecret / KWallet), used only where it is RELIABLE: Windows and
        macOS, and Linux only when `getSelectedStorageBackend()` isn't
        "basic_text"/"unknown" (there the "encryption" is a fixed key anyone
        can read, so the file stays a 0600 PEM instead of pretending).
      - Migration of a 2.6.0 PEM: encrypt -> write .enc atomically -> read it
        back, decrypt, compare DER -> only THEN delete the PEM. Any failure
        leaves the PEM where it was and removes only the .enc that attempt
        created. A leftover plaintext copy of the SAME key next to a working
        .enc (interrupted migration) is removed; a DIFFERENT PEM is left alone.
      - LOCKED state: an .enc that can't be decrypted (keyring reset, moved to
        another account) never creates a replacement. Public key, signing and
        export all return null, nothing on disk changes, and the preload stops
        the connect (emits `identity-locked`) instead of joining unsigned — an
        unsigned join of a bound id would only fail with a confusing "another
        device" error.
    Backup (identity-backup.ts, pure)
      - `*.reson8-identity`: scrypt N=2^17 r=8 p=1 (128 MiB, async so main
        stays responsive) + AES-256-GCM, header bound in as AAD, passphrase
        NFC-normalized, >= 10 characters. A wrong passphrase and a tampered
        file are indistinguishable by design ("Wrong passphrase or damaged
        file"). Cost parameters in a file are NEVER trusted: anything but our
        exact values is "unsupported" before any hashing. The payload (user
        id + PKCS#8 key) is validated as a UUID + a real Ed25519 key, and a
        backup that couldn't be restored is never written.
    Flows (main-process IPC; the renderer only passes passphrases and gets
    fingerprints back; file dialogs and key bytes stay in main)
      - Settings -> About: storage line ("Stored encrypted by your operating
        system" / protected file / temporary dev identity), Export, Import.
      - Import: pick file (64 KB cap, opaque token) -> passphrase -> a
        comparison of the backup's identity with the current one ->
        "Replace and restart". The replaced key and instance-id files are
        renamed aside (never deleted); then `app.relaunch(); app.quit()` so
        the graceful-disconnect handler runs. Importing the identity already
        in use is detected and changes nothing.
      - Locked dialog: Import backup, or "Create new identity" which needs a
        second click (it orphans every binding; the old file is kept aside).
      - Dev builds (ephemeral identity) disable both buttons with a reason.

    - Seeking: the Invidious host behind the fixer answers Chromium's first
      request (`Range: bytes=0-`) with `200` + Content-Range, no
      Accept-Ranges; Chromium reads that as "no range support". An explicit
      small range (`bytes=0-0`, `0-1`, `1000000-1000099`) gets a proper 206 —
      so the first design (a 0-0 probe) wrongly judged the host fine; the
      probe is open-ended, like the request that matters.

  Solution:
    - "fullscreen" is granted in the permission handler ONLY to the main
      window and Viewer windows (the hidden preview session denies all).
    - `media-proxy.ts` (pure) + `reson8-media://v/<id>` protocol: the main
      process probes each video host once (6 h cache); a host that needs it is
      re-served through the proxy, which forwards a validated Range upstream
      via the guarded fetch (18.10 rules, manual redirects, only headers under
      a deadline), turns a `200`+Content-Range into a `206`, passes only safe
      headers and streams the body. Only ids main minted are served (else
      404). Hosts that answer correctly keep the direct URL.
    - CSP: `reson8-media:` in media-src only (not connect-src).
    - Preview image click -> `openLightbox(url, { previewOnly: true })` with
      stopPropagation; text/domain and the embed thumbnail still open the link;
      with 18.11's blur the first click reveals, the next opens the viewer.
