- Reson8 Client
    - [NEW FEATURE] "Reson8 client auto updater" - The Reson8 app is published on github everytime there is a new version using the "Releases" feature. I would like to, instead of making the user re-download the newest release from the github page everytime a new version is published, have a way to check for new versions once when the app is opened and, if there actually is a new version, a way for the user to click a "update" button and then let the app do the rest by itself without the user needing to do anything. Let's use the electron-updater package to perform this. Also add the publish information to the electron package json: provider - github; owner - fbarrella; repo - reson8. The update logic should be exactly as described: once the app is open, the client will try to contact the github repo to check if there is a new release. If it manages to fetch the info, then it only does one time. If it fails to fetch, it should retry 3 times with 20 seconds of wait time. Then, on the success case it should prompt a modal to inform that there is a new update and that the user should update. But it should also present a button to confirm update and one to cancel if the user doesn't want to do it at the moment. It should be disclosed that some features might fail if not updated. Also, the auto updater should be triggered manually by the user from a new tab on the settings menu called "About the app". this section must have the app logo, the app version, a small description and a button called check for updates. This way the user can check for the updates whenever it wants to and not just when the app starts. the button should follow the same logic for fetch and retry. Always consider and follow the best practices when in this context.

    - [NEW FEATURE] "Settings 'audio' tab to tweak client sounds volumes" - Currently there is no way for the user to control nudge, general sound effects or even the global voice chat volumes. All of that is currently absolutely uncontrollable. So let't implement a new tab containing sliders for each of the mentioned sections. A slider to control the nudge volume, a slider to control the general sound alerts volume and a slider to control the general voice chat volume. All of the sliders must affect only the user client since this is no global server configuration. These settings must also be saved. And about the general voice chat slider, it must control the entire voice chat audio volume, all users at the same time and, then, the per user volume slider must control the users volume under the global volume setting. So, for instance, if the general volume slider is at 90%, then a participant into the voice chat normally starts with its personal volume slider at 100% and, if the user wants to lower its volume to 80% it will be able to. So its 80% of the 90% general volume. Take this into consideration and plan this feature carefully. Always consider and follow the best practices when in this context.

    - [FIX] "Session timer blinks everytime a the user mutes, unmutes, deafens or undeafens" - As the title says, when into a voice chat session, the session timer goes blank and then comes back (it maintains the time correctly though) everytime one of the described actions (mutes, unmutes, deafens or undeafens) are taken. This makes me thing that it might actually be related to the muted and deafened visual cues appearing by the side of the user name, because this started to happen after the implementation of these cues. Check into this and fix it.

    - [IMPROVEMENT] "Muted and Deafened actions and visual cues should accumulate" - When a user is deafen it SHOULD BE muted at the same time. So, currently when a user deafens itself, it only stops hearing but it can still be speaking and the deafened icon substitutes the muted icon. The app allows the user to be deafen but not muted. The ideal implementation would be for the user to be able to mute/unmute itself but still hear (then only the mic muted icon appears and the current mic muted sound alert is triggered), but NOT BE ABLE to speak when it is deaf. So, when the user clicks the deafen button, the mute action should be taken automatically and the visual cues should accumulate (muted mic icon and deafen icon one by the side of eachother). The sound alert should still be only the deafen one, there is no need to sound alert both mute and deaf at the same time because it looks like sound spam. And when a user unchecks the deafen, it resumes both sound and mic at the same time. Also, only the deafen sound should be triggered to avoid sound spam. If the user mutes itself first, it should follow the traditional mute action with mute sound alert and muted icon, but then, if the user comes to deafen itself while being muted, the deafen command only controls the audio, because the user wouldn't want to start hearing again and have its mic automatically resumed. So in this case the deafen action should stop the sounds, aggregegate the deaf icon and trigger the deafen sound alert. But when undeafened, it should only resume the sound and not mic, remove the deafen icon and not the muted, and trigger the undeafened sound. As questions if anything is still dubious. Always consider and follow the best practices when in this context.

    - [FIX] "If a user send a message into a text channel, then disconnects and connects again, the channel shows as unread even though the last message was from the user itself" - So, basically the title. Whan a user is the last one to send a message to a text channel, whenever it disconnects and connects again, the text channel shows as if his own message is unread so it falsely flags the text channel as if there is a new unread message, even if the user was the one who wrote it. Let's fix this behaviour.
