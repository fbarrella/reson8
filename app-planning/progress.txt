PROJECT OVERVIEW
================
Reson8 is a high-performance, self-hosted voice and text communication platform
for desktop (Electron). It replicates the TeamSpeak 3 experience — low-latency
voice, hierarchical channel trees, and private server ownership — while
integrating modern persistent text channels.

Tech Stack: Electron + TypeScript, Fastify + Socket.io, mediasoup (SFU),
PostgreSQL + Prisma, Redis, Docker.

Monorepo structure:
  apps/client/            — Electron desktop client
  apps/server/             — Node.js signaling + SFU server
  packages/shared-types/    — Shared DTOs, enums, and Socket.io event types

For build commands, environment variables, ports, and architecture details,
see the root CLAUDE.md (and apps/client/CLAUDE.md, apps/server/CLAUDE.md) —
not duplicated here to avoid drift between docs.

Full unabridged entry-by-entry history (every bug's root cause, every file
touched, every verification step) for everything summarized below lives in
app-planning/archive/progress-phases-1-8.txt (phases 1-8) and
app-planning/archive/progress-phases-9-10.txt (phases 9-10). The original
PRDs that drove this work are in app-planning/archive/ (PRD.md,
Reson8_Evolutions_PRD.md, Reson8_Improvements_PRD.md,
Reson8_NextSteps_PRD.md, Reson8_Phase10_PRD.md). Reach for the archive
when you need the "why" behind a specific decision that this summary
compresses away.

--- Entry: 13/08/2026 ---

Feature/Fix: Phase 11 — PRD 11.1: Fix Random Voice Chat Disconnections

  Problem: Voice chat participants would intermittently and
  unpredictably get dropped from a voice channel with no clear
  trigger. An audit of the full voice lifecycle (Socket.io signaling +
  mediasoup WebRTC handshake) found several independent gaps: nothing
  ever re-established a voice channel after a Socket.io reconnect
  (the server fully tears down mediasoup + presence on every
  disconnect, but the client never replayed the join handshake on
  reconnect); a 10s/5s Socket.io ping/pong timeout tight enough to
  trip a full disconnect on ordinary jitter (GC pause, laptop
  sleep/wake); no client- or server-side WebRTC connection-state
  monitoring, so a pure ICE-level drop (independent of the signaling
  channel) went completely undetected; and a single mediasoup worker
  crash called process.exit(1), taking down every voice session on
  the server instead of just the ones on that worker.

  Solution: Comprehensive fix addressing all four gaps, plus two
  related bugs found during the audit.

  Server Changes:
    - apps/server/src/index.ts: retuned Socket.io pingInterval/
      pingTimeout from 10_000/5_000 to 25_000/20_000 (Socket.io's own
      defaults), which alone removes a class of false-positive
      disconnects.
    - apps/server/src/services/mediasoup.service.ts: MediasoupService
      now extends EventEmitter. Added workerChannels (Worker → Set
      <channelId>) and channelWorker (channelId → Worker) tracking,
      maintained in getOrCreateRouter()/removeRouter(). The worker
      "died" handler no longer calls process.exit(1) — a new
      handleWorkerDeath() looks up exactly which channels were hosted
      on the dead worker, drops the now-unrecoverable routers/
      sessions/observers for just those channels, spawns a
      replacement worker to keep the pool size stable, and emits a
      "workerDied" event with the affected channelIds. Also added an
      icestatechange listener on WebRtcTransport alongside the
      existing dtlsstatechange one — mediasoup's ICE state has no
      "failed" value (unlike DTLS), so a stuck "disconnected" state
      is given a 10s grace period (ICE can self-recover) before the
      transport is force-closed.
    - apps/server/src/handlers/voice.handler.ts: registered a
      one-time mediasoup.on("workerDied", ...) listener that emits
      the new VOICE_SESSION_LOST event to every affected
      `channel:${channelId}` room. Also fixed producer.on
      ("transportclose") to emit PRODUCER_CLOSED to the rest of the
      channel — previously this only nulled the session's producer
      locally, so any transport-level close that wasn't routed
      through the explicit CLOSE_PRODUCER/leave/kick paths (e.g. the
      new ICE-grace-period close above) left peers holding a phantom
      consumer.

  Shared Types Changes:
    - packages/shared-types/src/socket-events.ts: added
      VOICE_SESSION_LOST: (payload: { channelId: string; reason:
      string }) => void to ServerToClientEvents.

  Client Changes:
    - apps/client/src/services/voice.service.ts: added
      connectionstatechange listeners on both sendTransport and
      recvTransport. "disconnected" gets a 4s grace period (mirroring
      the server-side ICE grace period) before being treated as a
      real failure; "failed" is terminal immediately. Reports through
      a new public onConnectionLost callback, at most once per join
      (connectionLossReported flag, reset in cleanup()). Also added a
      bounded retry (3 attempts, 1s apart) to queueConsumeProducer(),
      surfacing a final failure through a new onError callback
      instead of only console.error.
    - apps/client/src/preload.ts: added module-level
      lastVoiceChannelId (set on every successful joinVoiceChannel(),
      cleared on leaveVoiceChannel()/disconnect()) and a new
      attemptVoiceRejoin(channelId) helper that replays the full
      USER_JOIN_CHANNEL + voiceService.joinVoiceChannel() handshake,
      retrying up to 3 times (1.5s apart) before giving up and
      clearing lastVoiceChannelId. Wired to fire from three triggers:
      (1) the socket "connect" handler, when lastVoiceChannelId is
      set (i.e. this is a reconnect, not the first-ever connect); (2)
      VoiceService.onConnectionLost, for a pure WebRTC-level failure
      with no Socket.io disconnect; (3) a new VOICE_SESSION_LOST
      socket listener, for the server-initiated worker-crash case.
      Emits voice-reconnecting / voice-reconnected / voice-rejoin-
      failed / voice-connection-lost / voice-error events for the
      renderer to react to.
    - apps/client/src/renderer/renderer.ts: added a
      findChannelNodeById() tree-lookup helper, and handlers for the

      applies the saved global voice volume and mute/deafen state to
      the fresh VoiceService instance, and reseeds
      previousOccupantIds so the next presence update doesn't fire a
      spurious join sound; voice-rejoin-failed falls back to a clean
      "left voice" state; voice-connection-lost and voice-error log
      to the server log tab.
    - apps/client/src/renderer/index.html: added
      #voice-panel.reconnecting CSS (pulsing amber presence dot)

--- Entry: 13/08/2026 ---

Feature/Fix: Phase 11 — PRD 11.2: Fix Voice Session Timer Starting From Negative Numbers

  Problem: Joining a voice channel would briefly show the session
  timer starting at a negative value (e.g. -1:00 or -2:00) before
  counting up to positive. Root cause: the client computed elapsed
  time as `Date.now() - new Date(sessionStartedAt).getTime()`, i.e.
  its own wall clock diffed against a server-issued absolute
  timestamp, with no correction for clock skew between the two
  machines — any skew where the client's clock read behind the
  server's surfaced directly as a negative timer.

  Solution: Derive a client↔server clock offset from the existing
  ping/latency round trip and apply it everywhere sessionStartedAt is
  diffed against, instead of only clamping the visible symptom.

  Shared Types Changes:
    - packages/shared-types/src/socket-events.ts: PING_LATENCY's ack
      signature changed from `() => void` to `(serverTime: number) =>
      void` — the server now hands back its own current timestamp on
      every ping.

  Server Changes:
    - apps/server/src/handlers/connection.handler.ts: the PING_LATENCY
      handler now calls `ack(Date.now())` instead of `ack()`.

  Client Changes:
    - apps/client/src/preload.ts: added module-level clockOffsetMs
      (starts at 0, reset to 0 on disconnect). New
      measureLatencyAndClockOffset() helper replaces the two ad-hoc
      PING_LATENCY call sites (the 3s interval and the immediate
      post-connect measurement) with one shared implementation that
      computes both latencyMs (unchanged RTT calculation) and
      clockOffsetMs using the standard NTP-style approximation:
      offset ≈ serverTime - (localSendTime + rtt / 2). New
      getClockOffset(): number bridge method exposes the latest
      estimate, mirroring the existing getLatency().
    - apps/client/src/renderer/renderer.ts: added a correctedNow() =
      Date.now() + api.getClockOffset() helper (and the matching
      getClockOffset() declaration on the Reson8Api interface). Both
      elapsed-time computation sites — the synchronous timer-badge
      render inside renderChannel() and the 1s setInterval tick that
      updates both the tree badge and the voice panel timer — now
      call correctedNow() instead of a raw Date.now(). formatDuration()
      additionally clamps its input to a minimum of 0 before
      formatting, as a defense-in-depth safety net for any residual
      skew (the offset is a single round-trip estimate, not a full
      NTP sync), not the primary fix.

--- Entry: 13/08/2026 ---

Feature/Fix: Phase 11 — PRD 11.4: Post-Update "What's New" Modal

  Problem: Reson8 had no way to tell a user what changed after an
  update — the auto-updater (Phase 10) installs new versions silently,
  with no in-app summary of what's new beyond manually visiting
  GitHub Releases.

  Solution: On startup, compare the running app version against the
  last version the user actually dismissed this modal for; if they
  differ, fetch that version's GitHub release notes and show them
  once, dismissible via a "Got it" button that persists the new
  version so it doesn't reappear until the next bump.

  Main Process Changes (main.ts):
    - New fetchReleaseNotes(version) — fetches
      https://api.github.com/repos/fbarrella/reson8/releases/tags/v{version}
      (5s timeout via AbortController), returns { name, body, htmlUrl }
      or null on any failure (offline, rate-limited, no matching
      tag). Follows the same fetch-from-main pattern already used by
      fetchLinkPreview().
    - New ipcMain.handle("fetch-release-notes", ...) wired to it.
    - No new "open external" IPC needed — the existing
      mainWindow.webContents.setWindowOpenHandler() already routes
      any http(s) window.open() call from the renderer through
      shell.openExternal(), so the modal's "View on GitHub" button
      reuses that.

  Client Bridge (preload.ts):
    - fetchReleaseNotes(version): Promise<{name, body, htmlUrl} | null>
      bridge method.

  Renderer Changes (renderer.ts, index.html):
    - checkForWhatsNew(currentVersion), called right after the
      existing api.getAppVersion() call in the About-tab startup
      hydration. Compares currentVersion against
      localStorage["reson8-last-seen-version"]:
        - unset (first-ever launch) → silently records currentVersion,
          no modal (a brand-new install shouldn't be greeted with a
          "what's new since your last version" prompt).
        - differs → calls fetchReleaseNotes(); on success shows the
          new #whats-new-modal; on failure (null) does nothing this
          launch — the version is deliberately NOT marked as seen
          yet, so the check retries on the next launch instead of
          the notification being silently lost to one bad network
          moment.
        - matches → no-op.
      The "seen" marker is only written when "Got it" is clicked.
      Clicking the backdrop closes the modal like other modals in

Feature/Fix: "What's New" Modal Silently Skipped on Upgrade From a
Pre-11.4 Client

  Problem: After manually uploading the missing latest*.yml files to
  the v1.4.0 GitHub release (closing out the prior entry above), the
  user confirmed the auto-update itself now worked end-to-end — but

  v1.4.0 itself. checkForWhatsNew() in renderer.ts treats an unset
  reson8-last-seen-version localStorage key as "first-ever launch,
  nothing to announce" and silently records the current version
  without showing the modal — a deliberate design choice so
  brand-new installs aren't greeted with a "what's new since your
  last version" prompt. But a v1.3.0 client (which predates this
  feature entirely) never wrote that key either, so on the very
  first launch after auto-updating from v1.3.0 to v1.4.0, this code
  saw the same "unset" state as a truly fresh install and incorrectly
  took the silent-record path, permanently losing the modal for that
  transition.

  before" signal instead of inventing a new one:
  apps/client/src/instance-id.ts's persisted instance-id.txt file,
  written on this client's actual first-ever launch, independent of
  any single feature's own state. Added hasExistingInstanceId() to
  instance-id.ts (must be called before getInstanceId(), which
  creates the file as a side effect), wired through a new
  is-existing-install IPC handler in main.ts, a new
  isExistingInstall() preload bridge method, and a matching Reson8Api
  interface entry in renderer.ts. checkForWhatsNew() now only takes
  the silent "brand-new install" path when isExistingInstall() is
  false; otherwise (an unset marker on an existing install) it falls
  through to fetch and show the current version's release notes,
  same as any other version bump.

Feature/Fix: Linux/Wayland Screen-Share Fixes, VP9 Black-Video Root
Cause, Packaging Build Fix, and Viewer UI Polish

  Problem: Live testing on the user's CachyOS/KDE Plasma (Wayland)
  machine, continuing from the 13/08/2026 entry's screen-sharing
  work, surfaced several distinct issues: (1) the in-app Selection
  Modal was redundant on Wayland, since desktopCapturer.getSources()
  already drives the OS-level xdg-desktop-portal picker itself; (2)
  once a Linux/Wayland bypass was attempted, real screen captures
  always rendered black on the viewer side, on every platform, not
  just Wayland; (3) `npm run build:linux`, `build:win`, and the
  newly-added `release:all` (PRD 12.5) all failed outright with
  "Cargo.lock must be under apps/client/"; and (4) three smaller
  Viewer/UI issues once video was working: the "Started sharing"
  log showed an empty/generic source name, the Viewer's "Exit
  Stream" button didn't read as a destructive action, and the
  Share Screen button's icon didn't change to signal "stop sharing"
  while active.

  Linux/Wayland Screen-Share Bypass:
    Per user decision, the bypass applies only when Wayland is
    actually detected (XDG_SESSION_TYPE=wayland or WAYLAND_DISPLAY
    set), not to all Linux sessions — X11 has no OS-level picker to
    defer to, so it keeps the existing in-app Selection Modal.
    preload.ts exposes a new `isLinuxWayland` flag; renderer.ts's
    Share Screen click handler branches on it.

    Went through three iterations before landing on a working
    approach, each confirmed live against the real portal (not
    guessed):
      1. First attempt: renderer calls the existing
         `get-desktop-sources` IPC handler, then
         `startScreenShareVideo(source.id)` (the same
         getUserMedia({chromeMediaSourceId}) path the modal already
         used). Confirmed broken: showed the OS picker a *second*
         time inside the getUserMedia call, the resulting video was
         black, and the log showed `Started sharing ""` — the
         getSources() placeholder source's `name` field is empty at
         that point.
      2. Second attempt: switched capture to
         navigator.mediaDevices.getDisplayMedia() directly (new
         voiceService.startScreenVideoProducingViaSystemPicker()).
         Confirmed broken differently: rejected immediately with
         "Not supported" — Electron requires a
         session.setDisplayMediaRequestHandler to be registered at
         all before getDisplayMedia() works, contrary to an initial
         (wrong) assumption that omitting it falls back to a native
         Wayland picker.
      3. Final approach: registered
         session.defaultSession.setDisplayMediaRequestHandler in
         main.ts's createWindow(), whose handler calls
         desktopCapturer.getSources() itself (via a new shared
         getDesktopSourcesWithTimeout() helper, refactored out of
         the existing get-desktop-sources handler, keeping the same
         20s hang-protection for a broken portal backend) and calls
         back with the first source. This unifies picker-selection
         and stream-negotiation into getDisplayMedia()'s single
         request/callback cycle instead of two independent IPC round
         trips. Note: `useSystemPicker` (DisplayMediaRequestHandlerOpts)
         was investigated and confirmed, from Electron 34.5.8's own
         bundled type definitions, to be "currently available for
         MacOS 15+ only" — not usable here, despite external
         information suggesting otherwise.

    Real source name for the "Started sharing" log: since
    getDisplayMedia()'s resulting MediaStreamTrack.label comes back
    empty for portal-based captures, main.ts's
    setDisplayMediaRequestHandler now stashes the real
    DesktopCapturerSource.name it saw (module-level
    lastScreenShareSourceName) right before granting it, exposed via
    a new get-last-screen-share-source-name IPC handler that
    preload.ts's startScreenShareViaSystemPicker() reads right after
    the stream resolves, preferring it over the empty track label.

  VP9 SVC Black-Video Root Cause (separate bug, not Wayland-specific):
    The black video during bypass testing was NOT primarily a
    Wayland/portal issue. Electron main-process stderr showed, ~45s
    after a successful capture grant: `libvpx_vp9_encoder.cc:
    "Flexible mode is required for screenshare with several spatial
    layers"` → `simulcast_encoder_adapter.cc: InitEncode failed
    WEBRTC_VIDEO_CODEC_ERR_PARAMETER` → `video_stream_encoder.cc:
    Failed to initialize the encoder... Error: -4`.
    voice.service.ts's screen-video Producer used `scalabilityMode:
    "L3T3_KEY"` (3 spatial + 3 temporal layers, K-SVC) — Chromium's
    VP9 encoder rejects multi-spatial-layer K-SVC outright for any
    track flagged as screen content, so the encoder never
    initialized and no frame was ever sent to any viewer, on any
    platform. This had been silently broken since the original
    Phase 12 implementation; a synthetic canvas-sourced test track
    used in the prior session's investigation wasn't flagged as
    screen content, so it never hit this and masked the bug (the
    mediasoup/transport/Viewer-window pipeline itself was never
    actually broken). Fixed by switching to `scalabilityMode:
    "L1T3"` (single spatial layer, still temporal scaling) —
    confirmed working end-to-end live. Multi-resolution SVC (not
    just multi-framerate) can be revisited later, but needs a
    flexible-mode-compatible scalability mode, not K-SVC, and must
    be verified against a real screen capture, not a synthetic one.

  Packaging Build Fix (build:linux, build:win, release:all):
    Root cause: `@reson8/native-audio` and `@reson8/shared-types`

    symlinks whose real target (packages/native-audio,
    packages/shared-types) sits outside apps/client/. Two separate
    electron-builder code paths choke on that: (a) the asar
    packager's per-file relative-path check (getRelativePath in
    app-builder-lib), which throws for any packaged file whose real
    disk path is both outside apps/client/ and contains no literal

    `to` destination; and (b) a second, independent automatic
    production-dependency walk electron-builder runs whenever
    something is listed under `dependencies`, which resolves the
    same symlinks itself and hits the identical crash.

    Fix, in apps/client/package.json's `build` config and a new
    apps/client/scripts/before-pack.mjs (beforePack hook):
      - before-pack.mjs stages real, filtered copies of both
        packages under apps/client/.release-vendor/ (gitignored)
        before packing — genuinely under apps/client/, so the
        relative-path check never needs its node_modules-searching
        fallback.
      - `files` maps that staging dir to the correct
        node_modules/@reson8/... destination via `from`/`to`
        entries, with the raw symlinked paths explicitly excluded
        from the blanket node_modules/**/* glob.
      - `asarUnpack` points at the staging-relative path
        (.release-vendor/native-audio/prebuilds/**/*.node), not the
        final node_modules/... path — the asar unpack-pattern check
        matches a file's source-relative path, not its mapped
        destination, so this had to change too (confirmed via a
        second bug where the .node binary packed into the asar
        proper instead of unpacking, ELF binaries can't dlopen from
        inside an asar).
      - `@reson8/native-audio` and `@reson8/shared-types` moved from
        `dependencies` to `devDependencies` — not because they're
        dev-only (they're required at runtime, shipped via the
        staging mechanism instead), but so electron-builder's
        separate automatic dependency walk skips them entirely.

  Windows Crash — Root-Caused via Real Event Viewer Data:
    Windows Event Viewer's Application Error report gave exception
    code 0xC0000374 (STATUS_HEAP_CORRUPTION), faulting module
    ntdll.dll. Traced to `packages/native-audio/src/windows.rs`'s
    `activate_process_loopback_client()`: it builds a raw PROPVARIANT
    with `vt = VT_BLOB` whose `blob.pBlobData` points at
    `&mut activation_params` — a plain stack local, never allocated
    via `CoTaskMemAlloc`. Confirmed against the actual
    `windows-core-0.58.0` crate source (cached locally, not
    guessed): `PROPVARIANT`'s `Drop` impl unconditionally calls
    `PropVariantClear`, which for `VT_BLOB` frees `pBlobData` via
    `CoTaskMemFree` — freeing a non-heap pointer through the process
    heap allocator, corrupting it. The corruption was only detected
    later, on some unrelated allocation, which is why the crash's
    timing only loosely correlated with when audio capture started
    (masked by concurrent WGC video-capture noise in the logs, which
    turned out to be an unrelated red herring). Fixed with
    `std::mem::forget(prop)` right after the synchronous
    `ActivateAudioInterfaceAsync` call — `prop` never legitimately
    owned anything `PropVariantClear` needed to touch.

Feature/Fix: Long Chat Message Truncation With "See More"/"See
Less" (Phase 12 sub-phase, item 5/11)

  Problem: Long channel messages rendered at full length with no
  truncation at all — confirmed via investigation that this feature
  (described in the request as an existing behavior with a
  persistence bug) doesn't exist anywhere in the current codebase.
  Built fresh per explicit user clarification: truncate to a few
  lines with a "See more" expand toggle, and deliberately do NOT
  persist the expanded state anywhere — it should reset to
  truncated on a channel switch, an app restart, AND when the window
  is minimized (to tray or a plain OS minimize), not just stay
  expanded until manually re-collapsed.

  Solution: `attachMessageTruncation()` applies a `-webkit-line-

  message never gets the clamp class at all, so it keeps flowing
  inline after the nickname exactly as before — no visual change for

  state is stored anywhere outside these DOM classes, so:
    - Channel switch away and back already resets it for free —
      `loadChannelMessages()` rebuilds the tab's message list (and

    - App restart already resets it for free — nothing survives

      keeps running and the DOM stays untouched while just hidden —

      existing "minimize" handler (fires for both minimize-to-tray
      and a plain OS minimize) through to a new
      `collapseAllExpandedMessages()` that finds and re-collapses
      every currently-expanded message.
    - Also wired into both places a message's `.msg-text` gets
      rebuilt after this feature's own initial render: the editor's
      own optimistic post-edit DOM update, and `applyMessageEdit()`
      (the MESSAGE_EDITED broadcast other viewers receive) — an edit
      can just as easily turn a short message long as the reverse,

Feature/Fix: Fixed Per-User Local Volume/Mute Having No Audible Effect,
Added "Muted for You" Indicator (Phase 12 sub-phase, item 8/11)

  Problem: the per-participant local volume slider and "Mute Locally"
  button (right-click an occupant in a voice channel) appeared to do
  nothing — audio played at full, unchanged volume regardless of the
  slider position or mute state.

  Investigation: every layer of the feature — the preload/interface
  wiring, context-menu construction and event handlers, CSS, and the
  Web Audio GainNode graph in voice.service.ts — read as structurally
  correct with no bug findable by static analysis (confirmed
  independently by both a fork's investigation and a direct re-read).
  Live diagnostics (temporary console logging, added and later
  removed) were needed to actually find it: `applyOverrideForUser()`
  was confirmed to correctly locate the live GainNode for the target
  user and drive `gain.gain.value` all the way to `0.000`, yet audio
  stayed fully audible — and a DOM dump confirmed there was no
  phantom/duplicate `<audio>` element or untracked consumer either.
  A kill-test (fully quitting the remote client mid-conversation,
  which immediately silenced the audio) confirmed the sound really
  was coming from Reson8's own WebRTC pipeline, not another source.

  Root cause: `consumeProducer()` fed the per-participant GainNode
  graph via `ctx.createMediaElementSource(audioElement)`, on the
  assumption (standard Web Audio behavior, and the design already in
  place per PRD 4.1/4.2 — "GainNode-per-participant Web Audio graph")
  that capturing an `<audio>` element for a Web Audio graph redirects
  the element's own native output exclusively into that graph. That
  redirection turned out to be unreliable in this Electron/Chromium
  build specifically for `srcObject`/live-MediaStream-backed elements
  (as opposed to `src="file"` elements, where the redirection is
  solid): with the element left unmuted, the GainNode's value had
  zero audible effect since the element's own native playback path
  was still the thing actually producing sound, entirely bypassing
  the graph. (A first fix attempt — muting the element outright while
  still sourcing the graph from it via `createMediaElementSource`
  — produced total silence for both participants instead, which
  proved the graph was never the real audible output path at all.)

  Solution: switched the graph's source node from
  `ctx.createMediaElementSource(audioElement)` to
  `ctx.createMediaStreamSource(stream)`, tapping the same
  `MediaStream` directly and independently of the `<audio>` element.
  The `<audio>` element is still created, appended to `document.body`,
  and played (per root CLAUDE.md's "detached audio element" gotcha,
  to keep the MediaStreamTrack actively flowing/decoded) but is now
  explicitly `muted = true`, since the GainNode graph — sourced
  independently via `createMediaStreamSource` — is the sole intended
  audible route. This makes the per-user GainNode unambiguously
  authoritative regardless of any element-capture quirks.

  Also added, since the underlying mechanism was already being
  touched: a light-blue "muted for you" mic-slash icon next to an
  occupant's name in the voice-channel tree (`OCC_LOCALLY_MUTED_ICON`
  in renderer.ts, reusing `OCC_MUTED_ICON`'s shape with `var(--accent)`
  instead of `var(--danger)`), shown only to the client who locally
  muted that occupant — distinct from the existing red icon, which
  reflects the occupant's own server-broadcast self-mute and is
  visible to everyone. Wired to re-render immediately on toggling
  "Mute Locally" (`renderTree(currentTree)`) rather than waiting for
  an incidental tree update to pick up the new localStorage state.

Feature/Fix: Fixed Nicknames Showing "Unknown" in Online Users Modal
After Long Sessions (Phase 12 sub-phase, item 9/11)

  Problem: a user connected for 3+ hours could show up as "Unknown"
  in the Online Users modal, despite their nickname displaying
  correctly everywhere else (e.g. inside the voice channel itself).

  Root cause: Redis presence hashes carry a 1-hour TTL (`USER_TTL`
  in presence.service.ts), refreshed on activity — but nothing
  refreshed it on pure *inactivity*/idle presence. A
  `PresenceService.heartbeat(userId)` method already existed
  specifically to refresh this TTL, but had zero callers anywhere in
  the codebase — no client→server event ever invoked it. Any session
  idle (voice-inactive, no channel/message activity) for longer than
  the 1-hour TTL had its presence hash silently expire out of Redis;
  `getUserPresence()`'s fallback (`nickname: data.nickname ??
  "Unknown"`) then kicked in for that user in the Online Users
  modal specifically, since that's the one place presence is looked
  up in bulk for users who may no longer have a live hash. Other UI
  (e.g. inside a voice channel) resolves nicknames via a different,
  already-camera-locked-on-the-occupant path that doesn't hit this
  same fallback.

  Solution: rather than adding a brand new periodic client→server
  event solely for this, wired the heartbeat into the existing
  `PING_LATENCY` handshake — already emitted by every connected
  client every ~3 seconds for RTT/clock-offset measurement (PRD
  11.2), far more often than the 1-hour TTL needs. The server's
  `PING_LATENCY` handler now also calls
  `presence.heartbeat(socket.data.userId)` (fire-and-forget, never
  blocking the latency ack) alongside its existing instant ack. Zero
  added client-side code and zero added network traffic — reuses a
  signal that was already firing continuously for the entire
  lifetime of any connected session.

  Key Files Modified:

Feature/Fix: Fixed Deafen Not Applying to Participants Consumed After
Toggle-On (Phase 12 sub-phase, item 10/11)

  Problem: a user joining a voice channel *after* local deafen was
  already activated could still sometimes be heard — deafen only
  reliably silenced participants who were already being consumed at
  the moment it was toggled on.

  Root cause: `toggleDeafen()` silenced sound by setting
  `audio.muted = true/false` directly on each currently-tracked
  `<audio>` element — a one-shot pass over whoever existed in
  `audioElements` at that instant. `consumeProducer()`, which runs
  for every participant consumed *afterward*, never checked
  `_isDeafened` at all, so a newly-consumed participant's element
  always started unmuted regardless of the current deafen state.

  This bug was about to get considerably worse as a side effect of
  entry (10) above: that fix made every remote `<audio>` element
  permanently `muted = true` (audible output now flows solely through
  the per-user GainNode graph via `createMediaStreamSource`), which
  would have made `toggleDeafen()`'s `audio.muted` toggling
  completely inert for everyone, not just late joiners — caught and
  fixed here before it shipped.

  Solution: introduced a single `computeGainForUser(userId)` helper
  that derives a participant's GainNode value from three inputs —
  their per-user volume/mute override, the master volume attenuator,
  and `_isDeafened` (deafen wins outright, forcing 0 regardless of
  anything else) — and wired every gain-setting site through it:
  `consumeProducer()`'s initial gain, `applyOverrideForUser()`
  (per-user slider/mute), and `setGlobalVoiceVolume()` (master
  slider), all previously duplicating the override-only formula
  inline. `toggleDeafen()` no longer touches `<audio>.muted` at all;
  it flips `_isDeafened` and then re-derives every currently-tracked
  consumer's gain via the same helper. Because `consumeProducer()`
  now consults `_isDeafened` through that same helper, a participant
  consumed after deafen was toggled on starts correctly silenced —
  fixing both the original bug and the regression entry (10) would
  otherwise have introduced.

Feature/Fix: Connection Resilience for Weak/Flaky Networks

  Problem: user-supplied server logs from a live session (a client on
  a weak signal) showed repeated Socket.io `ping timeout`/`transport
  close` disconnects over ~15 minutes. Investigation of
  connection.handler.ts found the `disconnect` handler had zero grace
  period: the instant a socket dropped, it immediately wiped the
  user's Redis presence and broadcast USER_LEFT/PRESENCE_UPDATE to
  the whole server. The client's existing reconnection logic
  (Socket.io auto-reconnect + `attemptVoiceRejoin` in preload.ts)
  would then reconnect within a second or two and rejoin — but from
  every *other* client's perspective this was indistinguishable from
  a real leave+rejoin: renderer.ts plays
  `user_disconnected_from_channel.mp3` then
  `user_joined_channel.mp3` for the whole channel, and the occupant
  list flickers, every time the flaky user blips. Separately, the
  existing ICE-disconnected grace timers (client 4s / server 10s,
  from PRD 11.1) only ever waited-then-killed a degraded WebRTC
  transport — mediasoup supports `restartIce()` to recover a live
  transport without destroying its producer/consumers, and nothing in
  the codebase called it, so even a pure media-path hiccup (socket
  fine, only the UDP path degraded) escalated to a full voice-channel
  rejoin instead of a silent in-place recovery.

  Solution: four independent fixes, chosen with the user after
  presenting the diagnosis via AskUserQuestion (all four selected):

  1. Disconnect grace period (server): `connection.handler.ts`'s
     `disconnect` handler no longer immediately calls
     `presence.leaveChannel`/`presence.leaveServer` or broadcasts
     USER_LEFT/PRESENCE_UPDATE. Mediasoup cleanup (PRODUCER_CLOSED +
     `mediasoup.cleanupUserSession`) still happens immediately — that
     transport is tied to the dead socket either way, and the client
     rebuilds a fresh one on rejoin regardless. The presence
     removal + broadcast is now deferred via a `setTimeout`
     (`DISCONNECT_GRACE_MS = 10_000`) keyed by `userId` in a new
     `pendingDisconnects` map, run through a new `finalizeDisconnect()`
     helper. `USER_JOIN_SERVER` checks this map first and clears the
     timer if the same `instanceId` reconnects within the window, so
     a brief blip never triggers the leave broadcast (and therefore
     never triggers the leave/join sound pair or occupant-list
     flicker) at all.
  2. ICE restart on transient transport drops (shared-types + server
     + client): new `RESTART_ICE` Socket.io event
     (`{transportId} -> {success, iceParameters?}`). Server:
     `MediasoupService.restartTransportIce()` finds the send/recv
     transport by ID in the user's session and calls mediasoup's
     `transport.restartIce()`; a new handler in `voice.handler.ts`
     wires this up. Client: `voice.service.ts`'s
     `handleTransportConnectionStateChange` now takes the transport
     instance too, and on `"disconnected"` immediately fires a new
     `attemptIceRestart()` (guarded by an `iceRestartInFlight` Set
     keyed by transport ID) which calls the new
     `signaling.restartIce()` and applies the result via
     mediasoup-client's `transport.restartIce({iceParameters})`. The
     existing grace timer (bumped 4s -> 6000ms to give the restart
     round-trip room) still runs in parallel as a fallback —if the
     restart doesn't recover the connection (or signaling is down
     too), `reportConnectionLost()` still fires and the existing full
     `attemptVoiceRejoin()` path in preload.ts is unchanged as the
     safety net.
  3. Unlimited Socket.io reconnection attempts (client): preload.ts's
     `io()` call had `reconnectionAttempts: 5` (~17s of backoff before
     giving up entirely, per Socket.io's default delay/cap), which
     could strand a user on a connection bad enough to need more than
     a few retries — requiring a manual reconnect even though the new
     server-side grace period is happy to wait far longer. Changed to
     `reconnectionAttempts: Infinity` (delay/backoff unchanged).
  4. Log noise (server): `permissions.middleware.ts`'s
     `requirePermission()` logged every denial at `warn` level,
     including routine capability probes (MANAGE_ROLES/MANAGE_EMOJIS
     checks that fire on every join for every non-admin user to
     decide whether to show admin UI) — not a bug (the client already
     silently ignores `PERMISSION_DENIED`, per
     `renderer.ts:2437`), but this was drowning out genuine signal
     while reading server logs during this investigation. Downgraded
     to `debug`.

    apps/server/src/handlers/voice.handler.ts — new RESTART_ICE

Feature/Fix: Phase 13.1 (PRD 13.2) — Fix Choppy Noise Gate With a Real Attack/Hold/Release Envelope

  Problem: The microphone noise gate cut audio abruptly whenever the signal
  dipped below the configured dB threshold, even briefly mid-sentence during
  normal speech variance — there was no fade or hold, just an instant
  on/off, making voice chat choppy for anyone using the feature.

  Solution: Root cause was `hookAnalyser()` toggling `track.enabled` as a
  hard boolean every 50ms based on an RMS→dB read — a MediaStreamTrack can
  only snap on/off, it can never fade, so any real envelope required
  replacing the boolean toggle with a GainNode driven by real Web Audio
  automation. This meant introducing an always-on send-side processing
  graph in `voice.service.ts` — previously `startProducing()` produced the
  raw `getUserMedia` track directly, with zero Web Audio graph on the send
  path; the noise gate's old analyser ran on a *cloned* track purely for
  metering, entirely separate from what got produced.

  New architecture (built once per join in `startProducing()`, torn down
  only on full `cleanup()` or before a rebuild):
    localStream → micSourceNode → gateGainNode → micDestinationNode → produce()
  with `analyser` tapping `micSourceNode` in parallel (pre-gate), so gate
  decisions and the settings meter always read the true, ungated input
  level. The destination node's track — not the raw mic track — is what
  gets produced from now on.

  The gate itself (`startGateLoop()`) still polls every 50ms, but now
  drives `gateGainNode.gain` through `linearRampToValueAtTime()`:
  attack ~15ms when the signal crosses back above threshold, a 350ms hold
  once it drops below (absorbing brief pauses without any change), and
  only then a 200ms release ramp to silence — versus the previous instant
  cut. Enabling/disabling the gate (`enableSensitivity()`/
  `disableSensitivity()`) no longer tears down or rebuilds any
  AudioContext/analyser — it only starts/stops this loop and, on disable,
  ramps the gate back open — so the mic-processing graph now survives
  toggling the feature on and off mid-call, which it needs to since PRD
  13.3 (mic volume slider) and PRD 13.1 (noise cancelling) are planned to
  extend this exact same graph rather than each building their own.

  This also let the old clone-the-track-for-analysis approach be deleted
  entirely (`_analysisTrack` field and all): since the gate no longer
  touches `track.enabled`, the raw track always carries the true signal, so
  the analyser can tap the same `micSourceNode` used for the gate instead
  of needing an isolated cloned-track AudioContext.

  Key Files Modified:
    apps/client/src/services/voice.service.ts — new always-on send-side
      graph (`micSourceNode`, `gateGainNode`, `micDestinationNode`,
      `buildMicProcessingGraph()`, `teardownMicProcessingGraph()`),
      envelope-based gate (`startGateLoop()`, `stopGateLoop()`,
      `readAnalyserLevel()`, `GATE_ATTACK_SEC`/`GATE_HOLD_SEC`/
      `GATE_RELEASE_SEC`), `startProducing()` now produces the graph's

Feature/Fix: Phase 13.3 (PRD 13.1) — AI Microphone Noise Cancelling (DeepFilterNet3, WASM/AudioWorklet)

  Problem: No way to suppress background noise (keyboard clicks, fan noise)
  beyond the existing hard-threshold noise gate, which cuts audio rather
  than cleaning it. The source request specifically asked for a real
  AI-based denoiser (DeepFilterNet) running client-side via WASM in an
  AudioWorklet, toggleable without ever tearing down the voice connection.

  Solution: Evaluated available options for a browser-usable DeepFilterNet3
  WASM build (no official one exists) and settled on the npm package
  `deepfilternet3-noise-filter` (pinned at 1.3.0), specifically its
  LiveKit-agnostic `DeepFilterNet3Core` export — inspected its actual
  compiled output (not just its README) to confirm real behavior: it embeds
  the entire AudioWorkletProcessor as a self-contained code string (blob-URL
  loaded, no separate worklet file to ship), fetches a ~16.4MB df_bg.wasm +
  ~8MB DeepFilterNet3_onnx.tar.gz model, `WebAssembly.compile()`s the wasm
  on the calling thread, and passes the compiled module + raw model bytes
  into the worklet at construction — with an already-built `SET_BYPASS`
  message the worklet honors by copying input straight to output, which is
  exactly the "toggle without tearing down the graph" behavior this feature
  needed.

  Asset sourcing (confirmed with user): the package's default behavior
  fetches both files from a third-party CDN (cdn.mezon.ai) at runtime,
  which conflicts with this project's self-hosted/no-third-party-servers
  design and would make every install depend on an external host staying
  up indefinitely. Downloaded both files once and vendored them into
  `apps/client/assets/deepfilternet/v3/{pkg/df_bg.wasm,models/
  DeepFilterNet3_onnx.tar.gz}` (~24MB added to the repo), and pointed the
  package's `assetConfig.cdnUrl` at that local path (relative to
  dist/renderer/index.html, `../../assets/deepfilternet` — the exact same
  relative-path convention already used for sound-alert assets) instead of
  the default CDN. No electron-builder config changes were needed for the
  assets themselves (`assets/**/*` was already in `files`); confirmed via
  `mediasoup-client`'s identical hoisting that regular npm deps hoisted to
  the monorepo root `node_modules` already package correctly today.

  Dependency hygiene: `deepfilternet3-noise-filter` has a `livekit-client`
  peerDependency needed only for `tsc` to resolve its .d.ts (the actual
  compiled JS never references livekit-client at runtime — confirmed by
  grepping the compiled output) — installing it pulled in ~14MB+5.5MB of
  LiveKit/protobuf code we never use. Excluded `node_modules/livekit-client`
  and `node_modules/@livekit/**` from the packaged build via new `!`
  entries in `apps/client/package.json`'s `files` array, leaving them
  present for typechecking but absent from installers.

  Graph integration: extended the send-side mic processing graph (PRD 13.2/
  13.3, this same phase) with the AudioWorkletNode as the *first* stage:
    micSourceNode → [noiseCancelNode] → gateGainNode → volumeGainNode → destination → produce()

  denoised signal, not raw input. `buildMicProcessingGraph()` is now async

Feature/Fix: Phase 13.6 — Fix Preload Script Crash From Noise-Cancelling Dependency (regression in PRD 13.1)

  Problem: After PRD 13.1 (noise cancelling), the entire client broke on
  launch — clicking "Connect" did nothing, and the bottom status bar never
  showed an instance ID. Both symptoms traced to a single root cause: the
  preload script itself was crashing at load time, so none of its API
  (including the Connect flow and the "connected" event that populates the
  instance ID display) was ever exposed to the renderer.

  Root Cause (confirmed by actually launching the app with
  `ELECTRON_ENABLE_LOGGING=1`, not just re-reading the diff): the vendored
  `deepfilternet3-noise-filter` package declares `"type": "module"` in its
  own package.json. `voice.service.ts`'s static
  `import { DeepFilterNet3Core } from "deepfilternet3-noise-filter"`
  compiles (this project's tsconfig targets CommonJS) to a top-level
  `require("deepfilternet3-noise-filter")`, executed unconditionally the
  moment preload.js loads (since preload.ts constructs a VoiceService at
  module scope). Node resolves the package's "require" export condition to
  `dist/index.js`, but because the package's own `"type": "module"` marks
  all its plain `.js` files as ESM regardless of which export condition
  pointed at them, that file gets parsed as an ES module — which has no
  `exports` global — while its actual body still assumes one (a Rollup
  CJS-shaped build), producing `ReferenceError: exports is not defined`,
  crashing preload.js entirely. This is a dual-package-hazard bug in the
  dependency's own publish output, not something fixable by changing our
  import style alone in the naive way.

  First attempted fix — a plain `await import(...)` inside the already-
  lazy `ensureNoiseCancelInitialized()` — was insufficient on its own:
  confirmed in the compiled output that TypeScript rewrites dynamic
  `import()` to `Promise.resolve().then(() => require(...))` when the
  compiler's own module target is CommonJS, hitting the identical crash,
  just deferred to first use instead of app startup (better, but the
  feature itself would still be completely broken).

  Actual Fix: an indirect-eval dynamic import —
  `new Function("specifier", "return import(specifier)")` — invoked as
  `dynamicImport("deepfilternet3-noise-filter")`. Because the literal
  `import(...)` keyword lives inside a string passed to the `Function`
  constructor rather than in real parsed source, TypeScript's compiler
  can't see or rewrite it; at runtime it's a genuine dynamic import
  resolved through Node's real ESM loader (the package's "import"
  condition, `dist/index.esm.js`), sidestepping the CJS/ESM mismatch
  entirely. Verified empirically with a standalone `node -e` script
  before wiring it in, then confirmed against the compiled
  `voice.service.js` output that no `require()` call remains for this
  package. The class's *type* (for `noiseCancelCore`'s field type and the
  helper's return type) is still available via a type-only
  `import("deepfilternet3-noise-filter").DeepFilterNet3Core` query, which
  is fully erased at compile time and emits no require/import of its own.
