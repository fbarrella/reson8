PROJECT OVERVIEW
================
Reson8 is a high-performance, self-hosted voice and text communication platform
for desktop (Electron). It replicates the TeamSpeak 3 experience — low-latency
voice, hierarchical channel trees, and private server ownership — while
integrating modern persistent text channels.

Tech Stack: Electron + TypeScript, Fastify + Socket.io, mediasoup (SFU),
PostgreSQL + Prisma, Redis, Docker.

Monorepo structure:
  apps/client/            — Electron desktop client
  apps/server/             — Node.js signaling + SFU server
  packages/shared-types/    — Shared DTOs, enums, and Socket.io event types

For build commands, environment variables, ports, and architecture details,
see the root CLAUDE.md (and apps/client/CLAUDE.md, apps/server/CLAUDE.md) —
not duplicated here to avoid drift between docs.

Full unabridged entry-by-entry history (every bug's root cause, every file
touched, every verification step) for everything summarized below lives in
app-planning/archive/progress-phases-1-8.txt (phases 1-8),
app-planning/archive/progress-phases-9-10.txt (phases 9-10), and
app-planning/archive/progress-phases-11-13.txt (phases 11-13). The original
PRDs that drove this work are in app-planning/archive/ (PRD.md,
Reson8_Evolutions_PRD.md, Reson8_Improvements_PRD.md,
Reson8_NextSteps_PRD.md, Reson8_Phase10_PRD.md, Reson8_Phase11_PRD.md,
Reson8_Phase12_PRD.md, Reson8_Phase13_PRD.md). Reach for the archive when
you need the "why" behind a specific decision that this summary
compresses away.

--- Entry: 30/08/2026 ---

Feature/Fix: Remove code signing from the client build pipeline; stop electron-updater rejecting unsigned updates on Windows

  Problem: The v2.2.0 GitHub release (built while a Windows Authenticode
  certificate was configured via CSC_LINK) shipped a signed installer. A
  user updating an already-installed, previously-signed client on Windows
  hit an auto-update failure: "New version 2.2.0 is not signed by the
  application owner" — the certificate chain terminated in an untrusted
  root ("Codegic CA G2"). Rather than chase a trusted certificate, the
  decision was to drop code signing entirely for now and ship unsigned
  installers until a better certificate is available.

  Solution: Removed the whole opt-in code-signing wrapper around
  electron-builder and disabled electron-updater's Windows signature
  check so unsigned updates are accepted:
  - Deleted `apps/client/scripts/build-signed.mjs` (the wrapper that
    loaded `.env.local` and shelled out to `electron-builder`) and
    `apps/client/scripts/local-env.mjs` (the `.env.local` loader it and
    `scripts/release-all.mjs` both used), plus the committed
    `apps/client/.env.local.example` template. `build:win`/`build:linux`/
    `build:mac` in `apps/client/package.json` now call `electron-builder`
    directly instead of going through the wrapper.
  - `scripts/release-all.mjs` no longer imports/calls `loadLocalEnv()`
    before its `electron-builder` steps.
  - Root-caused the actual runtime failure: `NsisUpdater` (from
    `electron-updater`) reads a `publisherName` baked into the
    *currently-installed* app's own `app-update.yml` (written by
    electron-builder at build time, from whatever signing cert was
    present then) and, if present, runs a PowerShell Authenticode check
    on every downloaded update against it — this is why a client that
    had been built+installed while still signed kept failing even once
    future builds stopped signing. Fixed in `apps/client/src/main.ts` by
    overriding `NsisUpdater`'s `verifyUpdateCodeSignature` (Windows only,
    behind a `process.platform === "win32"` guard) with a verifier that
    always resolves `null` — per electron-updater's own API this is a
    `(publisherNames, path) => Promise<string | null>` function, not a
    boolean, so `= false` alone does not compile and would not have
    worked correctly either.
  - Updated the "Code Signing" section in the root `README.md` to
    describe the current unsigned state instead of the old CSC_LINK
    setup guide (Windows SmartScreen / macOS Gatekeeper implications for
    an unsigned build, and a note to remove the `verifyUpdateCodeSignature`
    override again if signing is reintroduced later).
  - Added a new Electron gotcha bullet to root `CLAUDE.md` documenting
    this incident and the fix, so a future re-introduction of signing
    doesn't forget to remove the override.
  - Left `apps/client/certs/` and `apps/client/.env.local` (both
    gitignored, never tracked) untouched — they may contain the user's
    real private key/password material, so they were not read or
    deleted; the user can remove them by hand if desired.

  Key Files Modified:

--- Entry: 30/08/2026 ---

Feature/Fix: Fix "Couldn't enable noise cancelling" in the packaged v2.2.0 release (CSP blocked the local asset fetch)

  Problem: The user installed the real v2.2.0 release on both Windows and
  Linux and reported that toggling AI Noise Cancelling always failed
  immediately with "Couldn't enable noise cancelling", reproducing on
  every platform (macOS suspected too, untested). This path had never
  actually been verified in a packaged build before release — the PRD
  13.1 entry's own Verification section explicitly left "a packaged —
  not just dev — build still finds the vendored assets" as pending the
  user's own hands-on test, and that test only happened now.

  Solution: Root-caused by reading the vendored dependency's actual
  compiled code (`node_modules/deepfilternet3-noise-filter/dist/
  index.esm.js`) rather than guessing: `AssetLoader.fetchAsset()` calls a
  plain `fetch()` against the configured `cdnUrl` (here, the relative
  path `../../assets/deepfilternet`, resolved against the loaded page's
  own URL). Since the whole client loads over `file://`, that fetch
  targets a `file://.../assets/deepfilternet/v3/pkg/df_bg.wasm` (and the
  `.../models/DeepFilterNet3_onnx.tar.gz` model) URL — and
  `apps/client/src/renderer/index.html`'s CSP `<meta>` tag's `connect-src`
  directive was `ws: wss: http: https:`, which never included the `file:`
  scheme. Chromium's Fetch implementation enforces CSP `connect-src`
  scheme restrictions, so every `fetch()` call `AssetLoader` made was
  silently CSP-blocked, throwing (`TypeError: Failed to fetch`) inside
  `ensureNoiseCancelInitialized()` → `createNoiseCancelNode()`, caught by
  `setNoiseCancelEnabled()`'s catch block and surfaced via `onError` as
  the generic "Couldn't enable noise cancelling." toast. Nothing else in
  the client uses `fetch()` for local assets (sound alerts/images use
  `<audio src>`/`<img src>`, which aren't governed by `connect-src`), so
  this exact failure mode had never been exercised by any other feature —
  platform-independent, so the Windows/Linux (and presumably macOS)
  failures all share this one cause.

  Fix: added `'self' file:` to the `connect-src` directive in
  `apps/client/src/renderer/index.html`'s CSP meta tag, so local
  `file://` fetches are permitted alongside the existing
  ws/wss/http/https schemes.

Feature/Fix: PRD 14.1 + PRD 14.2 — Chat/DM opens at the most recent message;
cursor-paginated chat history with infinite-scroll-up (Phase 14, items 1-2)

  Problem: Text chats and DMs sometimes opened scrolled to a stale position
  — "a day behind or even a few days behind" — instead of the true latest
  message. Separately, every channel/DM tab fetched its entire message
  history in one unbounded request on open; the server's FETCH_MESSAGES/
  FETCH_DIRECT_MESSAGES handlers already supported before/limit cursor
  pagination (confirmed via a fresh audit, not just progress.txt's earlier
  Phase 4 claim), but nothing client-side ever used it — a from-scratch
  client feature, not a wiring gap.

  Solution:
  Root cause of the scroll bug: attachment <img> elements had no `load`
  listener to re-correct scrollTop once async image decode grew
  scrollHeight (only the link-preview path re-corrected scroll before), and
  revisiting an already-loaded tab never re-scrolled to bottom at all —
  both fixed together with the pagination work since they touch the same
  rendering code.

  Client Changes (apps/client/src/renderer/renderer.ts, index.html):
  - `ChatTab` gained `topSentinelEl`/`scrollObserver`/`oldestLoadedTimestamp`/
    `oldestRenderedDateKey`/`hasMoreOlder`/`loadingOlder`/`initialLoadDone`.
    `openChatTab`/`openDmTab` create a permanent top sentinel (first child
    of `messagesEl`) and attach a per-tab `IntersectionObserver` (root:
    `messagesEl`) via new `setupInfiniteScroll()`; `closeTab` disconnects it.
  - `loadChatHistory` now fetches only `CHAT_PAGE_SIZE` (20) messages
    initially for channels. For DMs it uses `max(20, unreadCountHint)`
    capped at the server's 100-message limit — `unreadCountHint` comes from
    the existing `GET_UNREAD_DM_PARTNERS` per-partner `unreadCount`, now
    threaded through `openDmTab`'s new optional third parameter — so the
    pre-existing "Unread Messages" separator still lands correctly even
    with a deep unread backlog, instead of silently breaking once the page
    size shrank to 20.
  - New `loadOlderMessages()` fires when the sentinel scrolls into view and
    fetches the next page via the existing `before`/`limit` cursor contract
    (zero server or shared-types changes needed). New
    `prependOlderMessages()` inserts the batch right after the sentinel,
    recomputing date-section dividers correctly — it removes whatever
    divider previously marked the "start of loaded history" edge (no longer
    valid once even-older content is inserted above it) and reseeds the
    day-boundary lookback from `oldestRenderedDateKey`.
  - Scroll-position preservation on prepend: records `scrollHeight` before/
    after insertion and adjusts `scrollTop` by the exact delta (the
    standard Slack/Discord/Teams anchor technique), so the user's reading
    position never visibly jumps.
  - `renderChatMessage`/`renderDmMessage` split into pure element builders
    (`buildChatMessageElement`/`buildDmMessageElement`, shared by both the
    forward-append and the new backward-prepend paths) plus thin render
    wrappers that check `isNearBottom(messagesEl)` before appending and only
    auto-stick to the bottom if the user was already there — applied
    consistently to the new message itself, the attachment image's async
    `load` event (the actual scroll-bug root cause), and the async
    link-preview card's load (`injectLinkPreview`'s new `onLoaded` callback
    replaces its old hardcoded unconditional scroll-to-bottom).
  - `switchTab()` now forces scroll-to-bottom whenever a loaded chat tab is
    (re)focused, so revisiting an already-open tab also always lands on the
    latest message rather than resuming a stale remembered position.
  - `jumpToPinnedMessage`'s full `messagesEl.innerHTML` wipe-and-rebuild
    (which would otherwise destroy the sentinel and desync the new cursor
    state) now explicitly rebuilds the sentinel and resets `hasMoreOlder` to
    `true` (optimistic — a window-centered fetch never guarantees it hit
    the true start of history), so the next scroll-up still works
    correctly afterward.

Feature/Fix: PRD 14.4 — Fix the intermittent DM "wake up" sound alert not
playing (Phase 14, item 4)

  Problem: The `hey_wake_up.mp3` DM notification sound intermittently
  failed to play. Root cause found via static code reading (no live
  reproduction needed): in the `dm-received` handler
  (`apps/client/src/renderer/renderer.ts`), when the DM tab didn't already
  exist (a new or previously-closed conversation), the code called
  `openDmTab(partnerId, partnerNick)` — which synchronously calls
  `switchTab(tabKey)`, setting `activeTabId` to the new tab — *before* the
  sound-alert logic further down checked
  `const isTabActive = activeTabId === tabKey`. That check therefore always
  evaluated to true in exactly this case, regardless of whether the user
  was actually looking at a different tab a moment earlier. Net effect: the
  sound was silently suppressed only in the narrow combination of (a) a
  new/reopened DM conversation AND (b) the window being OS-focused (on some
  other tab) — every other case (already-open tab, or window unfocused) was
  already correct, which is exactly why it read as "intermittent" rather
  than "always broken."

  Solution: Captured `wasTabActive = activeTabId === tabKey` at the very
  top of the handler, immediately after computing `tabKey` and before the
  tab-exists/auto-open branch runs — i.e. before `openDmTab()`'s side
  effect can change `activeTabId`. The sound-alert check below now uses
  this captured `wasTabActive` instead of re-reading `activeTabId` after
  the fact.

    apps/client/src/renderer/renderer.ts

  Verification:
