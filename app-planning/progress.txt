PROJECT OVERVIEW
================
Reson8 is a high-performance, self-hosted voice and text communication platform
for desktop (Electron). It replicates the TeamSpeak 3 experience — low-latency
voice, hierarchical channel trees, and private server ownership — while
integrating modern persistent text channels.

Tech Stack: Electron + TypeScript, Fastify + Socket.io, mediasoup (SFU),
PostgreSQL + Prisma, Redis, Docker.

Monorepo structure:
  apps/client/            — Electron desktop client
  apps/server/             — Node.js signaling + SFU server
  packages/shared-types/    — Shared DTOs, enums, and Socket.io event types

For build commands, environment variables, ports, and architecture details,
see the root AGENTS.md (and apps/client/AGENTS.md, apps/server/AGENTS.md; the
CLAUDE.md files next to them just import these) — not duplicated here to
avoid drift between docs.

Full unabridged entry-by-entry history (every bug's root cause, every file
touched, every verification step) for everything summarized below lives in
app-planning/archive/progress-phases-1-8.txt (phases 1-8),
app-planning/archive/progress-phases-9-10.txt (phases 9-10),
app-planning/archive/progress-phases-11-13.txt (phases 11-13),
app-planning/archive/progress-phases-14-15.txt (the v2.2.1 patch work,
phases 14 and 15), app-planning/archive/progress-phase-16.txt (phase 16),
and app-planning/archive/progress-phase-17.txt (phase 17).
The original PRDs that drove this work are in

PHASE 1 — Signaling & Presence (Foundation)
  Fastify + Socket.io server (port 9800), Redis-backed presence tracking,
  Electron shell, typed Socket.io event maps, initial Prisma schema
  (Server/Channel/User/Role/Message), flat→nested channel-tree builder.

PHASE 2 — The Voice Bridge (mediasoup)
  mediasoup SFU integrated; full 6-step WebRTC handshake (GET_ROUTER_
  CAPABILITIES → CREATE_WEBRTC_TRANSPORT → CONNECT_TRANSPORT → PRODUCE →
  CONSUME → RESUME_CONSUMER); two-way audio; mute/deafen controls.
  Notable fixes: Electron mic-permission auto-grant, silent-audio race
  (queued consumption until recv transport ready), ICE announced-IP
  defaulting, detached-Audio()-element silence (must attach to DOM),
  deafen-toggle state flag, voice-control UI overflow.

PHASE 3 — Relational Logic & Hierarchy
  DB seeding (default server/channels/roles), channel CRUD over Socket.io,
  three-pane TeamSpeak-style UI (tree + log + status bar), click-to-join

  Docker Compose (server + Postgres + Redis).
  Notable fixes: window.confirm() unusable in Electron renderer (replaced

PHASE 13 FOLLOW-UP — v2.2.1 patch (30/08/2026, 4 entries)
  - Code signing removed from the client build pipeline (the signed v2.2.0
    installer broke auto-update on Windows with "not signed by the
    application owner"): the signing wrapper/env-loader scripts were
    deleted, and `main.ts` now overrides `NsisUpdater`'s
    `verifyUpdateCodeSignature` (Windows only) with a verifier that always
    resolves `null`. Root cause: electron-updater checks each downloaded
    update's Authenticode publisher against the publisher name baked into
    the CURRENTLY-INSTALLED app's own `app-update.yml`, so a client built
    while still signed kept rejecting legitimate unsigned updates. Must be
    removed again if signing is ever reintroduced.
  - AI noise cancelling "Couldn't enable noise cancelling" in packaged
    builds took THREE separate fixes behind one identical generic toast —
    found only by driving the real app over the DevTools protocol, not by
    guessing: the CSP blocked the local `fetch()` of the vendored WASM
    (`connect-src` needed `file:`); a bare-specifier `dynamicImport(
    "pkg")` never worked in any environment (Blink resolves only real
    URLs — resolve to a `file://` URL via `require.resolve()` first); and
    the CSP `script-src` needed `blob:` for the Blob-built AudioWorklet
    module. All now standing gotchas in root CLAUDE.md.
  - v2.2.1 release: combined release notes (so users landing straight on
    v2.2.1 still see v2.2.0's features — the What's New modal only fetches
    the exact running tag), and macOS added to `release:all`.

PHASE 15 — Rich Chat & Sturdier Connections (PRD 15.x — 11 items from
app-planning/nextsteps.txt, reached v2.4.0)
  - Stale-socket race (PRD 15.1, confirmed 5-for-5 from the server log): a
    reconnecting user has an old half-open socket and a new one at once;
    the old one's late `disconnect` ran userId-keyed cleanup that killed
    the LIVE socket's voice session (a second drop ~12s later) and, via an
    uncancelled grace timer, deleted its presence (user in a channel but
    absent from the online list). Fixed with a `SocketOwnership` registry
    (`services/socket-ownership.ts`): join claims ownership and retires
    the displaced socket, `disconnect` ignores non-owners, and the grace
    timer re-checks `hasOwner()`. PRD 15.2 concluded the underlying drops
    were connectivity-side (half-open connections from the network path)
    and unfixable in-app, left the Socket.io ping settings alone, and
    added diagnostics (connect address, disconnect transport/lifetime,
    the disconnect reason and reconnect duration in the Server Log tab)
  - Small fixes/chores: own voice halo now gated on the mic actually
    transmitting (not muted/deafened, PTT held) (15.3); a disabled — not
    hidden — Ban button on your own User Management row, server self-ban
    guard already existed (15.4); pinned bar restyled dark amber with
    measured 9.8:1 contrast via `--pin-*` tokens (15.5); window size,
    position and maximized state persisted by a hand-rolled
    `window-state.ts` validated against current displays (15.6)
  - Windows re-launch freeze (15.7) — hypothesis-driven, never reproduced:
    minimize-to-tray now intercepts `will-minimize` instead of `hide()`ing
    from inside `minimize`, Chromium's `CalculateNativeWinOcclusion` is
    disabled on win32, and one `showMainWindow()` helper (with state
    logging) serves second-instance/tray click/tray Restore. User
    confirmed OK on hand-test
  - Google Noto Color Emoji bundled as a vendored web font so emoji match
    on every OS (15.8). Two traps found while building it: Chromium can't
    render the OpenType-SVG build that `@fontsource` ships (emoji come out
    blank — use Google Fonts' COLRv1 woff2), and Google's own
    `unicode-range` includes digits/#/*/©/®/™ (stripped locally, or every
    number renders as an emoji)
  - Image viewer rebuilt (15.9): icon toolbar (zoom, copy image, copy
    link, open in browser, download, separate Close), "Sent by" pill, zoom
    from fit up to 200% of natural size via transform-only pan/zoom;
    clipboard/open/fetch go through validated main-process IPC
  - Multi-line messages + Discord-style Markdown (15.10): textarea input
    (Enter sends, Shift+Enter newline), pure `markdown.ts` on markdown-it
    exposed via the preload, a renderer allow-list sanitizer, one
    `setMessageBody()` for channel/DM/edit, masked links and raw HTML/
    images/tables deliberately disabled; plain single lines keep the
    original inline layout; server normalizes CRLF to LF. `npm run
    test:markdown` smoke-tests syntax and XSS vectors
  - Reaction hover card (15.11): a 1s still-pointer card with the big
    emoji, its name and who reacted; reactions now carry `users` (additive
    `IReactionSummary`), aggregated in one `reaction.service.ts` (one

  - Phase 15 wrap-up bumped to v2.4.0, release notes, docs

PHASE 16 — Replies, Grouped Chat & Secure Uploads (PRD 16.x — 11 items: 8 from
app-planning/nextsteps.txt, plus two upload-pipeline findings from the PRD's own
audit and one enabling refactor; reached v2.5.0. Three DB migrations.)
  - Small preferences and chat polish (16.1-16.4): a global "Don't warn me

  - Hover toolbar refactor (16.5): the reaction strip's `min-height` reserved an
    empty row on EVERY message just so hover-only buttons had somewhere to
    appear, which defeated grouping and left no home for Reply. React, Reply,
    Edit, Pin and Delete moved into a floating `.msg-actions` toolbar; the
    strip now takes space only when a message has reactions.
  - Grouped messages (16.6): Discord-style header (nick + HH:MM) over the text;
    consecutive same-author messages within 5 minutes of the GROUP'S FIRST
    message become continuations; a reply always starts its own group.
    `applyGrouping()`/`regroupFrom()` run on append, prepend (repairing the page
    junction) and delete, with a cascade that stops once nothing changes.
  - Emoji autocomplete (16.7): `:` + a letter opens a card above the colon
    (mirror-div coordinates, ranked name/word/keyword/substring search, custom
    first on ties); Unicode emoji insert as the character, custom as `:name:`;
    Enter/Tab select without sending, Escape closes only the card.
  - Follow-ups found in hand-testing: the NSFW switch row had been stretched by
    the modal's generic `label`/`input` rules (now a scoped switch row), and
    reaction pills were enlarged after the grouped layout shrank them.
  - SECURITY — upload ownership (16.8): the server trusted client-supplied
    attachment/emoji/icon URLs and Cloudinary public_ids and later DELETED
    whatever they pointed at, so a modified client could get another user's
    file (or any asset in the Cloudinary account) deleted, or post an external
    URL as an "attachment". Now every stored file is a `StoredFile` ledger row;
    uploads are attributed by a socket-issued bearer token (hashed in Redis,
    10 min); a file is claimed once, by its owner, for its own kind, by an
    atomic compare-and-set on the SAME transaction as the write that uses it;
    deletion uses only the ledger's url/public_id, after the referencing row is
    gone, and only when nothing else references the file. Decision with a user-
    visible cost: the server stores the host-independent path (`/uploads/x`)
    because the old client composed ABSOLUTE URLs and storing a client-built
    URL lets a client choose the host; clients resolve it with
    `resolveMediaUrl()`. So a v2.4.0 client cannot show NEW locally-stored
    images/emoji/icons from a v2.5.0 server (Cloudinary and older content are
    fine); a v2.5.0 client still works against an older server (it also sends
    the legacy fields). Tokenless (v2.4.0) uploads stay accepted as ownerless,
    claim-once, behind `ALLOW_TOKENLESS_UPLOADS`. Side finding, by code reading
    (not reproduced): local-disk deletion of message images had never worked,
    since the stored URL never started with `/uploads/`.
  - Orphaned-upload cleanup (16.9): `DISCARD_UPLOAD` (removing a picked image or
    a failed emoji/icon submit deletes the file at once), an hourly sweeper for

Feature/Fix: Server-side TLS, Caddy setup and trusted client addresses (PRD 18.2)

  Problem: The server only spoke plain HTTP/WS, so chat, DMs, upload tokens

  self-hoster happened to put a proxy in front. Separately, the address used

      - services/client-address.ts (pure): `parseTrustProxy()`,

Feature/Fix: Encrypted connections in the client — HTTPS first, trusted self-signed certificates, lock indicator (PRD 18.3)

  Problem: The client always built `http://host[:port]`: a typed `https://`
  was silently stripped and connected over plain HTTP, an IPv6 address could
  not be entered (the box split on ":"), and an empty address quietly became
  `localhost`. There was no way to use a server that has a self-signed
  certificate, and no indication of whether the connection was encrypted.

  Solution:
    Address + decision (pure, tls-trust.ts)
      - `parseServerAddress()`: host, host:port, [::1]:port, optional
        http/https/ws/wss prefix; refuses paths, queries, credentials, bad
        ports with specific messages; an explicit default port (":80") is
        kept because the URL class drops it. `identityHostOf()` is
        byte-identical to what 2.6.0 signed (unit-tested against a copy of
        the old parser) so bound identities and AUTH_ALLOWED_HOSTS keep
        matching. `decideScheme()` is the PRD's table, one test per row.
    Probe + pins (main process)
      - tls-probe.ts classifies a server: trusted / untrusted (+ the
        presented certificate) / no-tls (a plain HTTP server, or a TCP
        server that accepts and never answers) / unreachable. IPC `tls-probe`
        returns the result, any pin and the HTTPS memory in ONE round trip;
        the PEM never reaches the renderer.
      - tls-store.ts (`<userData>/tls-trust.json`, atomic writes, corrupt
        file -> empty): pins by SHA-256 + the "reached over HTTPS" memory.
        `tls-trust-certificate` only pins the certificate the LAST probe of
        that host:port just showed (5-minute window) and never overwrites a
        different existing pin (the SSH model: remove the old trust first).
    Two TLS stacks
      - Socket.io in the preload runs on Node `ws`: a pinned connection is
        given `ca: [pinned PEM]` plus a SHA-256 `checkServerIdentity`.
      - Uploads, images, emoji and the Viewer's media use Chromium:
        `session.defaultSession.setCertificateVerifyProc` accepts a
        certificate ONLY if its SHA-256 equals a pin for that hostname and it
        hasn't expired; everything else gets Chromium's verdict (-3).
      - The Viewer window gets the same pin through `viewer-get-tls-options`
        (main remembers each Viewer's server by webContents id).

Feature/Fix: Identity key encrypted at rest + passphrase-protected backup (PRD 18.6)

  Problem: The Ed25519 private key was a plain PKCS#8 PEM (0600) in the
  userData folder, so a copy of that folder — a backup, a synced folder — was
  a copy of the identity. And if the key was ever lost there was no recovery
  at all: an unreadable PEM silently minted a NEW key, orphaning every
  identity bound on servers until an admin reset each one.

  Solution:
    Storage (identity-store.ts, Electron-free; identity-key.ts is the adapter)
      - `identity-key.enc` = Electron safeStorage (DPAPI / Keychain /
        libsecret / KWallet), used only where it is RELIABLE: Windows and
        macOS, and Linux only when `getSelectedStorageBackend()` isn't
        "basic_text"/"unknown" (there the "encryption" is a fixed key anyone
        can read, so the file stays a 0600 PEM instead of pretending).
      - Migration of a 2.6.0 PEM: encrypt -> write .enc atomically -> read it
        back, decrypt, compare DER -> only THEN delete the PEM. Any failure
        leaves the PEM where it was and removes only the .enc that attempt
        created. A leftover plaintext copy of the SAME key next to a working
        .enc (interrupted migration) is removed; a DIFFERENT PEM is left alone.
      - LOCKED state: an .enc that can't be decrypted (keyring reset, moved to
        another account) never creates a replacement. Public key, signing and
        export all return null, nothing on disk changes, and the preload stops
        the connect (emits `identity-locked`) instead of joining unsigned — an
        unsigned join of a bound id would only fail with a confusing "another
        device" error.
    Backup (identity-backup.ts, pure)
      - `*.reson8-identity`: scrypt N=2^17 r=8 p=1 (128 MiB, async so main
        stays responsive) + AES-256-GCM, header bound in as AAD, passphrase
        NFC-normalized, >= 10 characters. A wrong passphrase and a tampered
        file are indistinguishable by design ("Wrong passphrase or damaged
        file"). Cost parameters in a file are NEVER trusted: anything but our
        exact values is "unsupported" before any hashing. The payload (user
        id + PKCS#8 key) is validated as a UUID + a real Ed25519 key, and a
        backup that couldn't be restored is never written.
    Flows (main-process IPC; the renderer only passes passphrases and gets
    fingerprints back; file dialogs and key bytes stay in main)
      - Settings -> About: storage line ("Stored encrypted by your operating
        system" / protected file / temporary dev identity), Export, Import.
      - Import: pick file (64 KB cap, opaque token) -> passphrase -> a
        comparison of the backup's identity with the current one ->
        "Replace and restart". The replaced key and instance-id files are
        renamed aside (never deleted); then `app.relaunch(); app.quit()` so
        the graceful-disconnect handler runs. Importing the identity already
        in use is detected and changes nothing.
      - Locked dialog: Import backup, or "Create new identity" which needs a
        second click (it orphans every binding; the old file is kept aside).
      - Dev builds (ephemeral identity) disable both buttons with a reason.

Feature/Fix: Link-preview videos can go fullscreen and seek; preview images open the limited viewer (PRD 18.19)

  Problem: (1) a preview video's fullscreen button did nothing; (2) YouTube
  preview videos often couldn't seek; (3) a preview image opened the link, not
  the image viewer.

  Step 0 (headless, unfixed, real app): a koutube video: seekable = [0, 0],
  setting currentTime to half left it at 0; an X video: seekable = [0, 31.5],
  seek to 15.7 worked. requestFullscreen() on both: never settled (3 s).

  Root causes:
    - Fullscreen: Electron asks for a permission named "fullscreen" for an
      element's requestFullscreen(); the session handler only granted the
      microphone names, so it never settled.
    - Seeking: the Invidious host behind the fixer answers Chromium's first
      request (`Range: bytes=0-`) with `200` + Content-Range, no
      Accept-Ranges; Chromium reads that as "no range support". An explicit
      small range (`bytes=0-0`, `0-1`, `1000000-1000099`) gets a proper 206 —
      so the first design (a 0-0 probe) wrongly judged the host fine; the
      probe is open-ended, like the request that matters.

  Solution:
    - "fullscreen" is granted in the permission handler ONLY to the main
      window and Viewer windows (the hidden preview session denies all).
    - `media-proxy.ts` (pure) + `reson8-media://v/<id>` protocol: the main
      process probes each video host once (6 h cache); a host that needs it is
      re-served through the proxy, which forwards a validated Range upstream
      via the guarded fetch (18.10 rules, manual redirects, only headers under
      a deadline), turns a `200`+Content-Range into a `206`, passes only safe
      headers and streams the body. Only ids main minted are served (else
      404). Hosts that answer correctly keep the direct URL.
    - CSP: `reson8-media:` in media-src only (not connect-src).
    - Preview image click -> `openLightbox(url, { previewOnly: true })` with
      stopPropagation; text/domain and the embed thumbnail still open the link;
      with 18.11's blur the first click reveals, the next opens the viewer.
