PROJECT OVERVIEW
================
Reson8 is a high-performance, self-hosted voice and text communication platform
for desktop (Electron). It replicates the TeamSpeak 3 experience — low-latency
voice, hierarchical channel trees, and private server ownership — while
integrating modern persistent text channels.

Tech Stack: Electron + TypeScript, Fastify + Socket.io, mediasoup (SFU),
PostgreSQL + Prisma, Redis, Docker.

Monorepo structure:
  apps/client/            — Electron desktop client
  apps/server/             — Node.js signaling + SFU server
  packages/shared-types/    — Shared DTOs, enums, and Socket.io event types

For build commands, environment variables, ports, and architecture details,
see the root CLAUDE.md (and apps/client/CLAUDE.md, apps/server/CLAUDE.md) —
not duplicated here to avoid drift between docs.

Full unabridged entry-by-entry history (every bug's root cause, every file
touched, every verification step) for everything summarized below lives in
app-planning/archive/progress-phases-1-8.txt. The original PRDs that drove
this work are in app-planning/archive/ (PRD.md, Reson8_Evolutions_PRD.md,
Reson8_Improvements_PRD.md). Reach for the archive when you need the "why"
behind a specific decision that this summary compresses away.

Feature/Fix: Fix Shortcut Sound Alerts for Mute/Deafen/Disconnect (PRD 4.15)

  Problem: The mute/unmute and deafen/undeafen sound alerts only played
  when triggered via their on-screen buttons. Triggering the same
  actions via keyboard shortcuts produced no sound. Root cause: the
  click handlers (btnMute/btnDeafen/btnLeaveVoice) and the keyboard-
  shortcut keydown branches independently duplicated the same state-
  mutation logic (api.toggleMute()/toggleDeafen()/leaveVoiceChannel() +
  updateVoiceUI()), but only the click handlers ever called
  SoundAlert.play(...) — the shortcut path never had it added.

  Solution: Extracted the duplicated logic into three shared helpers —
  toggleMuteAndNotify(), toggleDeafenAndNotify(), leaveVoiceAndNotify()
  — each ending with the appropriate SoundAlert.play() call (preserving
  the existing PTT-mode lock/unlock branching inside the mute helper).
  Both the click handlers and the shortcut keydown branches now call
  these helpers instead of duplicating logic, so the two trigger paths
  can no longer drift apart. This also fixes the disconnect shortcut,
  which had the identical bug (no sound) despite not being explicitly
  named in the original report — same root cause, so fixed alongside
  mute/deafen per an explicit scoping decision made while drafting
  app-planning/Reson8_NextSteps_PRD.md (PRD 4.15).

Feature/Fix: Self-Mute / Self-Deafen Status Icons (PRD 4.3)

  Problem: When a user muted their mic or deafened themselves, other
  voice channel participants had no way to know — it looked like they
  were being ignored. IUserPresence.isMuted/isDeafened already existed
  in the shared type and in every PRESENCE_UPDATE payload, but were
  hardcoded to `false` in 6 separate places server-side (5 in
  connection.handler.ts, 1 in moderation.handler.ts), because
  voiceService.toggleMute()/toggleDeafen() were purely client-local and
  never told the server anything had happened — the fields existed but
  always lied.

  Solution:
    - Extended presence.service.ts's Redis-backed per-user hash to also
      store isMuted/isDeafened; added PresenceService.setVoiceState().
    - Refactored connection.handler.ts's duplicated resolveNickname()
      helper into an exported buildOccupant() that returns a full
      IUserPresence (including real isMuted/isDeafened) from a single
      presence.getUserPresence() call. Replaced all 6 hardcoded-false
      occupant-construction call sites (connection.handler.ts x5,
      moderation.handler.ts x1) with buildOccupant().
    - Added a new SET_VOICE_STATE client→server event
      (packages/shared-types/src/socket-events.ts), handled in a new
      handler in voice.handler.ts: updates presence, then rebuilds and
      re-broadcasts PRESENCE_UPDATE for the user's current channel
      (reusing connection.handler.ts's exported voiceSessionStartedAt
      map so this broadcast doesn't blank out the active session timer
      on other clients).
    - Client emits SET_VOICE_STATE from the toggleMuteAndNotify()/
      toggleDeafenAndNotify() helpers (added in PRD 4.15) and once right
      after successfully joining a voice channel, so state is synced
      correctly on join and after a reconnect.
    - renderOccupants() in renderer.ts now renders a small red
      (var(--danger)) inline-SVG mic-muted and/or headphones-deafened
      icon next to an occupant's name based on occ.isMuted/isDeafened.
      Also fixed updateOccupants(), which was silently dropping
      isMuted/isDeafened when applying live PRESENCE_UPDATE payloads to
      the tree (it previously only mapped userId/nickname through).

  Edge Cases Handled:
    - Deliberately did NOT wire this into the PTT press/release
      key-hold handlers. isMuted represents a deliberate mute action (or
      PTT-lock toggle), not momentary PTT silence between talk bursts —
      wiring it to every key press/release would cause the icon to
      flicker on every PTT tap with no real signal value. This was a
      considered deviation from the original plan file after re-reading
      the exact PTT code during implementation.
    - Reconnect-while-muted: state is re-synced to the server
      immediately after (re)joining a voice channel, so observers don't
      see a stale "unmuted" icon after someone drops and rejoins.

Feature/Fix: Per-User Local Volume Levels (PRD 4.1)

  Problem: While in a voice channel, there was no way to adjust how loud
  a specific participant sounded to you personally — voice.service.ts
  hardcoded every remote <audio> element's volume to 1.0 with no per-
  participant control, and had no concept of userId at all (consumers/
  audio elements were keyed only by consumerId, with the userId↔producerId
  association discarded in preload.ts right after triggering consumption).

  Solution: This is a purely client-local feature — nothing is sent to
  the server, and nothing changes for other participants.
    - voice.service.ts: threaded userId through queueConsumeProducer()/
      consumeProducer() (pendingProducers now stores {producerId, userId}
      pairs instead of bare producer IDs) and added a consumerIdToUserId
      map.
    - Each consumed participant is now routed through a dedicated Web
      Audio graph: MediaElementAudioSourceNode -> GainNode ->
      destination, using a lazily-created playbackAudioContext (kept
      separate from the existing mic-analysis AudioContext used by the
      noise gate, since their lifecycles are unrelated). GainNode.gain
      supports 0–200% (the existing .volume property caps at 100%, so a
      real Gain node was required to allow boosting quiet talkers).
    - remoteUserOverrides: Map<userId, {volumePercent, muted}> holds the
      desired state per user regardless of whether they're currently
      being consumed — setLocalUserVolume()/setLocalUserMute() update
      this map and immediately re-apply gain to any live consumer for
      that user; if the user isn't in-channel yet, the override is
      simply read back when their producer is eventually consumed. This
      fully decouples "user sets a preference" from "user is currently
      speaking," so ordering never matters.
    - Persistence: localStorage, keyed by target userId
      (reson8-local-volume-<userId>), applied in renderOccupants() for
      every rendered occupant (idempotent — cheap to call on every tree
      render, and naturally covers both "already consuming" and "not
      consuming yet" cases without extra event plumbing).

  localStorage Keys:
    reson8-local-volume-<userId> — string, 0–200 (percent)

  Key Files Modified:
    apps/client/src/services/voice.service.ts — GainNode-per-participant
      playback graph, remoteUserOverrides, setLocalUserVolume()/
      getLocalUserVolume(), userId threaded through consumeProducer()
    apps/client/src/preload.ts — queueConsumeProducer() calls now pass
      userId; setLocalUserVolume()/getLocalUserVolume() bridge methods
    apps/client/src/renderer/renderer.ts — getSavedLocalVolume()/
      setSavedLocalVolume(), hydration call in renderOccupants(),
      Reson8Api interface extended

Feature/Fix: Channel Reordering via Drag & Drop (PRD 4.6)

  Problem: Channels rendered in creation order (Channel.position, set
  once at creation and never editable) with no way to reorder them
  short of deleting and recreating — e.g. creating "2" then "1" left
  them stuck in that order. Scoped to siblings-only reordering (same
  parent) per an earlier product decision — dragging a channel into a
  different parent group is out of scope.

  Solution: buildChannelTree() already sorted siblings by `position`
  correctly (verified before assuming a fix was needed there — the
  original PRD draft had flagged this as a possible root cause, but it
  wasn't; the actual gap was purely "nothing ever writes a non-default
  position").
    - New REORDER_CHANNELS socket event: client sends the full ordered
      sibling ID list for one parent (`{ parentId, orderedChannelIds }`)
      rather than a single move delta, so the server can validate the
      set atomically and apply it in one transaction (`position = index`
      for each ID) instead of reasoning about incremental moves. Server
      validates the submitted ID set is exactly the current sibling set
      for that parent/server before writing anything — rejects stale or
      foreign IDs rather than partially applying.
    - MANAGE_CHANNELS-gated, same as the other channel-admin actions.
    - Client: HTML5 Drag and Drop API wired onto every channel-tree row
      (both leaf channels and category labels, since categories are
      channels-with-children and are siblings too). Dropping onto a row
      inserts the dragged channel immediately before it and persists
      the recomputed sibling order via reorderChannels(). Drag handlers
      are admin-only and simply skip attaching (attachChannelDragHandlers
      no-ops) for non-admins, so there's no drag affordance at all for
      regular members — a deliberate difference from how Rename/Delete/
      NSFW-toggle are exposed (those rely on server-side permission
      checks + an "insufficient perms" sound on failure), because a
      failed drag gesture is a much worse UX than a disabled menu item.
    - renderChannel()/renderCategory() now take a `siblings: TreeNode[]`
      parameter (the exact array the node belongs to — the root `tree`
      array or a category's `children` array) so drop handlers can
      compute the new sibling order directly by reference instead of
      re-querying the DOM.

Feature/Fix: Unread Text Channel Indicator (PRD 4.13)

  Problem: No visual cue for unseen messages in text channels the user
  didn't have open — easy to miss activity in channels you weren't
  actively watching.

  Solution: New per-user-per-channel read cursor (`ChannelRead`), a
  design directly modeled on the existing DM unread pattern but
  necessarily different in shape: DirectMessage.readAt is a per-row
  flag that works because a DM only has one reader, but a channel has
  many readers, so a per-message flag can't represent "read by whom" —
  a cursor table (lastReadAt per user per channel) is the correct
  analog instead.

  A key architectural finding shaped the whole design: MESSAGE_RECEIVED
  already broadcasts to the entire server room
  (`io.to(server:${serverId})`), not just clients with that channel's
  tab open — confirmed by reading message.handler.ts's SEND_MESSAGE
  broadcast before assuming otherwise. That means every connected
  client already learns about every new message in real time regardless
  of which tab is active, so "is this unread" can be tracked **entirely
  client-side** by comparing the incoming channelId against activeTabId
  — no new server round-trip needed for the live-update path. The
  server only needs to persist a cursor, purely to restore correct
  state on reconnect/fresh load (mirroring how DMs solve the same
  reconnect problem with their own mechanism).

  This also surfaced a real constraint worth remembering for future
  per-user annotations on the channel tree: CHANNEL_TREE_UPDATE is
  broadcast identically to every client in the server room via
  `io.to(...)`, so a per-user field like hasUnread can only be computed
  correctly on the single-socket emission connection.handler.ts sends
  at USER_JOIN_SERVER time — never on the shared broadcasts triggered
  by other users' channel-admin actions (rename/reorder/etc, all of
  which reuse channel.handler.ts's broadcastTreeUpdate()). Left
  IChannelTreeNode.hasUnread optional and undocumented-false-safe for
  exactly this reason: the client only ever ADDs a channel to its local
  unread set when hasUnread is true, never removes based on a false/
  missing value from a shared broadcast, so stale broadcast data can't
  incorrectly clear a real unread flag.

  Server Changes:
    - New ChannelRead model (userId, channelId, lastReadAt,
      @@id([userId, channelId])) — migration 20260812013822_add_channel_read.
    - connection.handler.ts: new annotateUnreadChannels() helper, called
      once during USER_JOIN_SERVER after tree hydration — batches two
      queries (latest message timestamp per text channel via
      Prisma groupBy, and the user's ChannelRead cursors) rather than
      querying per-channel, then walks the tree once to set hasUnread.
    - message.handler.ts: new MARK_CHANNEL_READ handler — upserts the
      cursor to now().

  Client Changes:
    - unreadChannelIds: a client-side Set<channelId>, seeded from
      node.hasUnread on tree renders and otherwise updated purely from
      live MESSAGE_RECEIVED events (see above).
    - markChannelUnread()/markChannelRead() do targeted DOM patches
      (add/remove an .unread class + a red dot) instead of a full
      renderTree() on every message — a full re-render would blow away
      collapsed-category UI state on every single incoming chat
      message, which would have been a bad regression for anyone with
      categories collapsed.
    - switchTab() now calls markChannelRead() unconditionally; it's a
      no-op for tab IDs never in unreadChannelIds (server-log, DM tabs,
      already-read channels), so no extra guarding needed there.
    - Guarded against flagging the currently-active tab's own channel
      as unread when hydrating hasUnread on reconnect (edge case: the
      user reconnects while already viewing that channel).
