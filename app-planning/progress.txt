PROJECT OVERVIEW
================
Reson8 is a high-performance, self-hosted voice and text communication platform
for desktop (Electron). It replicates the TeamSpeak 3 experience — low-latency
voice, hierarchical channel trees, and private server ownership — while
integrating modern persistent text channels.

Tech Stack: Electron + TypeScript, Fastify + Socket.io, mediasoup (SFU),
PostgreSQL + Prisma, Redis, Docker.

Monorepo structure:
  apps/client/            — Electron desktop client
  apps/server/             — Node.js signaling + SFU server
  packages/shared-types/    — Shared DTOs, enums, and Socket.io event types

For build commands, environment variables, ports, and architecture details,
see the root CLAUDE.md (and apps/client/CLAUDE.md, apps/server/CLAUDE.md) —
not duplicated here to avoid drift between docs.

Full unabridged entry-by-entry history (every bug's root cause, every file
touched, every verification step) for everything summarized below lives in
app-planning/archive/progress-phases-1-8.txt (phases 1-8) and
app-planning/archive/progress-phases-9-10.txt (phases 9-10). The original
PRDs that drove this work are in app-planning/archive/ (PRD.md,
Reson8_Evolutions_PRD.md, Reson8_Improvements_PRD.md,
Reson8_NextSteps_PRD.md, Reson8_Phase10_PRD.md). Reach for the archive
when you need the "why" behind a specific decision that this summary
compresses away.

--- Entry: 13/08/2026 ---

Feature/Fix: Phase 11 — PRD 11.1: Fix Random Voice Chat Disconnections

  Problem: Voice chat participants would intermittently and
  unpredictably get dropped from a voice channel with no clear
  trigger. An audit of the full voice lifecycle (Socket.io signaling +
  mediasoup WebRTC handshake) found several independent gaps: nothing
  ever re-established a voice channel after a Socket.io reconnect
  (the server fully tears down mediasoup + presence on every
  disconnect, but the client never replayed the join handshake on
  reconnect); a 10s/5s Socket.io ping/pong timeout tight enough to
  trip a full disconnect on ordinary jitter (GC pause, laptop
  sleep/wake); no client- or server-side WebRTC connection-state
  monitoring, so a pure ICE-level drop (independent of the signaling
  channel) went completely undetected; and a single mediasoup worker
  crash called process.exit(1), taking down every voice session on
  the server instead of just the ones on that worker.

  Solution: Comprehensive fix addressing all four gaps, plus two
  related bugs found during the audit.

  Server Changes:
    - apps/server/src/index.ts: retuned Socket.io pingInterval/
      pingTimeout from 10_000/5_000 to 25_000/20_000 (Socket.io's own
      defaults), which alone removes a class of false-positive
      disconnects.
    - apps/server/src/services/mediasoup.service.ts: MediasoupService
      now extends EventEmitter. Added workerChannels (Worker → Set
      <channelId>) and channelWorker (channelId → Worker) tracking,
      maintained in getOrCreateRouter()/removeRouter(). The worker
      "died" handler no longer calls process.exit(1) — a new
      handleWorkerDeath() looks up exactly which channels were hosted
      on the dead worker, drops the now-unrecoverable routers/
      sessions/observers for just those channels, spawns a
      replacement worker to keep the pool size stable, and emits a
      "workerDied" event with the affected channelIds. Also added an
      icestatechange listener on WebRtcTransport alongside the
      existing dtlsstatechange one — mediasoup's ICE state has no
      "failed" value (unlike DTLS), so a stuck "disconnected" state
      is given a 10s grace period (ICE can self-recover) before the
      transport is force-closed.
    - apps/server/src/handlers/voice.handler.ts: registered a
      one-time mediasoup.on("workerDied", ...) listener that emits
      the new VOICE_SESSION_LOST event to every affected
      `channel:${channelId}` room. Also fixed producer.on
      ("transportclose") to emit PRODUCER_CLOSED to the rest of the
      channel — previously this only nulled the session's producer
      locally, so any transport-level close that wasn't routed
      through the explicit CLOSE_PRODUCER/leave/kick paths (e.g. the
      new ICE-grace-period close above) left peers holding a phantom
      consumer.

  Shared Types Changes:
    - packages/shared-types/src/socket-events.ts: added
      VOICE_SESSION_LOST: (payload: { channelId: string; reason:
      string }) => void to ServerToClientEvents.

  Client Changes:
    - apps/client/src/services/voice.service.ts: added
      connectionstatechange listeners on both sendTransport and
      recvTransport. "disconnected" gets a 4s grace period (mirroring
      the server-side ICE grace period) before being treated as a
      real failure; "failed" is terminal immediately. Reports through
      a new public onConnectionLost callback, at most once per join
      (connectionLossReported flag, reset in cleanup()). Also added a
      bounded retry (3 attempts, 1s apart) to queueConsumeProducer(),
      surfacing a final failure through a new onError callback
      instead of only console.error.
    - apps/client/src/preload.ts: added module-level
      lastVoiceChannelId (set on every successful joinVoiceChannel(),
      cleared on leaveVoiceChannel()/disconnect()) and a new
      attemptVoiceRejoin(channelId) helper that replays the full
      USER_JOIN_CHANNEL + voiceService.joinVoiceChannel() handshake,
      retrying up to 3 times (1.5s apart) before giving up and
      clearing lastVoiceChannelId. Wired to fire from three triggers:
      (1) the socket "connect" handler, when lastVoiceChannelId is
      set (i.e. this is a reconnect, not the first-ever connect); (2)
      VoiceService.onConnectionLost, for a pure WebRTC-level failure
      with no Socket.io disconnect; (3) a new VOICE_SESSION_LOST
      socket listener, for the server-initiated worker-crash case.
      Emits voice-reconnecting / voice-reconnected / voice-rejoin-
      failed / voice-connection-lost / voice-error events for the
      renderer to react to.
    - apps/client/src/renderer/renderer.ts: added a

      spurious join sound; voice-rejoin-failed falls back to a clean
      "left voice" state; voice-connection-lost and voice-error log
      to the server log tab.
    - apps/client/src/renderer/index.html: added

--- Entry: 13/08/2026 ---

Feature/Fix: Phase 11 — PRD 11.2: Fix Voice Session Timer Starting From Negative Numbers

  Problem: Joining a voice channel would briefly show the session
  timer starting at a negative value (e.g. -1:00 or -2:00) before
  counting up to positive. Root cause: the client computed elapsed
  time as `Date.now() - new Date(sessionStartedAt).getTime()`, i.e.
  its own wall clock diffed against a server-issued absolute
  timestamp, with no correction for clock skew between the two
  machines — any skew where the client's clock read behind the
  server's surfaced directly as a negative timer.

  Solution: Derive a client↔server clock offset from the existing
  ping/latency round trip and apply it everywhere sessionStartedAt is
  diffed against, instead of only clamping the visible symptom.

  Shared Types Changes:
    - packages/shared-types/src/socket-events.ts: PING_LATENCY's ack
      signature changed from `() => void` to `(serverTime: number) =>
      void` — the server now hands back its own current timestamp on
      every ping.

  Server Changes:
    - apps/server/src/handlers/connection.handler.ts: the PING_LATENCY
      handler now calls `ack(Date.now())` instead of `ack()`.

  Client Changes:
    - apps/client/src/preload.ts: added module-level clockOffsetMs
      (starts at 0, reset to 0 on disconnect). New
      measureLatencyAndClockOffset() helper replaces the two ad-hoc
      PING_LATENCY call sites (the 3s interval and the immediate
      post-connect measurement) with one shared implementation that
      computes both latencyMs (unchanged RTT calculation) and
      clockOffsetMs using the standard NTP-style approximation:
      offset ≈ serverTime - (localSendTime + rtt / 2). New
      getClockOffset(): number bridge method exposes the latest
      estimate, mirroring the existing getLatency().
    - apps/client/src/renderer/renderer.ts: added a correctedNow() =
      Date.now() + api.getClockOffset() helper (and the matching
      getClockOffset() declaration on the Reson8Api interface). Both
      elapsed-time computation sites — the synchronous timer-badge
      render inside renderChannel() and the 1s setInterval tick that
      updates both the tree badge and the voice panel timer — now
      call correctedNow() instead of a raw Date.now(). formatDuration()
      additionally clamps its input to a minimum of 0 before
      formatting, as a defense-in-depth safety net for any residual
      skew (the offset is a single round-trip estimate, not a full
      NTP sync), not the primary fix.

--- Entry: 13/08/2026 ---

Feature/Fix: Phase 11 — PRD 11.4: Post-Update "What's New" Modal

  Problem: Reson8 had no way to tell a user what changed after an
  update — the auto-updater (Phase 10) installs new versions silently,
  with no in-app summary of what's new beyond manually visiting
  GitHub Releases.

  Solution: On startup, compare the running app version against the
  last version the user actually dismissed this modal for; if they
  differ, fetch that version's GitHub release notes and show them
  once, dismissible via a "Got it" button that persists the new
  version so it doesn't reappear until the next bump.

  Main Process Changes (main.ts):
    - New fetchReleaseNotes(version) — fetches
      https://api.github.com/repos/fbarrella/reson8/releases/tags/v{version}
      (5s timeout via AbortController), returns { name, body, htmlUrl }
      or null on any failure (offline, rate-limited, no matching
      tag). Follows the same fetch-from-main pattern already used by
      fetchLinkPreview().
    - New ipcMain.handle("fetch-release-notes", ...) wired to it.
    - No new "open external" IPC needed — the existing
      mainWindow.webContents.setWindowOpenHandler() already routes
      any http(s) window.open() call from the renderer through
      shell.openExternal(), so the modal's "View on GitHub" button
      reuses that.

  Client Bridge (preload.ts):
    - fetchReleaseNotes(version): Promise<{name, body, htmlUrl} | null>
      bridge method.

  Renderer Changes (renderer.ts, index.html):
    - checkForWhatsNew(currentVersion), called right after the
      existing api.getAppVersion() call in the About-tab startup
      hydration. Compares currentVersion against
      localStorage["reson8-last-seen-version"]:
        - unset (first-ever launch) → silently records currentVersion,
          no modal (a brand-new install shouldn't be greeted with a
          "what's new since your last version" prompt).
        - differs → calls fetchReleaseNotes(); on success shows the
          new #whats-new-modal; on failure (null) does nothing this
          launch — the version is deliberately NOT marked as seen
          yet, so the check retries on the next launch instead of
          the notification being silently lost to one bad network
          moment.
        - matches → no-op.
      The "seen" marker is only written when "Got it" is clicked.
      Clicking the backdrop closes the modal like other modals in

Feature/Fix: Auto-Update Failure Investigation & Fix (v1.3.0 → v1.4.0

Feature/Fix: "What's New" Modal Silently Skipped on Upgrade From a
Pre-11.4 Client

  Problem: After manually uploading the missing latest*.yml files to
  the v1.4.0 GitHub release (closing out the prior entry above), the
  user confirmed the auto-update itself now worked end-to-end — but
  the post-update "What's New" modal (PRD 11.4) never appeared.

  Root cause: The "What's New" modal feature was introduced IN
  v1.4.0 itself. checkForWhatsNew() in renderer.ts treats an unset
  reson8-last-seen-version localStorage key as "first-ever launch,
  nothing to announce" and silently records the current version
  without showing the modal — a deliberate design choice so
  brand-new installs aren't greeted with a "what's new since your
  last version" prompt. But a v1.3.0 client (which predates this
  feature entirely) never wrote that key either, so on the very
  first launch after auto-updating from v1.3.0 to v1.4.0, this code
  saw the same "unset" state as a truly fresh install and incorrectly
  took the silent-record path, permanently losing the modal for that
  transition.

  Solution: Reused an existing, more fundamental "has this client run
  before" signal instead of inventing a new one:
  apps/client/src/instance-id.ts's persisted instance-id.txt file,
  written on this client's actual first-ever launch, independent of
  any single feature's own state. Added hasExistingInstanceId() to
  instance-id.ts (must be called before getInstanceId(), which
  creates the file as a side effect), wired through a new
  is-existing-install IPC handler in main.ts, a new
  isExistingInstall() preload bridge method, and a matching Reson8Api
  interface entry in renderer.ts. checkForWhatsNew() now only takes
  the silent "brand-new install" path when isExistingInstall() is
  false; otherwise (an unset marker on an existing install) it falls
  through to fetch and show the current version's release notes,
  same as any other version bump.

  Key Files Modified:
    apps/client/src/instance-id.ts — new exported hasExistingInstanceId()
    apps/client/src/main.ts — computes isExistingInstall before
      getInstanceId() creates the ID file; new is-existing-install
      IPC handler
    apps/client/src/preload.ts — new isExistingInstall() bridge method
    apps/client/src/renderer/renderer.ts — Reson8Api interface gained
      isExistingInstall(); checkForWhatsNew() no longer conflates
      "unset marker" with "brand-new install"
    app-planning/releases/v1.4.1.md — added this fix to the Bug Fixes
      section
