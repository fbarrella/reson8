PROJECT OVERVIEW
================
Reson8 is a high-performance, self-hosted voice and text communication platform
for desktop (Electron). It replicates the TeamSpeak 3 experience — low-latency
voice, hierarchical channel trees, and private server ownership — while
integrating modern persistent text channels.

Tech Stack: Electron + TypeScript, Fastify + Socket.io, mediasoup (SFU),
PostgreSQL + Prisma, Redis, Docker.

Monorepo structure:
  apps/client/            — Electron desktop client
  apps/server/             — Node.js signaling + SFU server
  packages/shared-types/    — Shared DTOs, enums, and Socket.io event types

For build commands, environment variables, ports, and architecture details,
see the root CLAUDE.md (and apps/client/CLAUDE.md, apps/server/CLAUDE.md) —
not duplicated here to avoid drift between docs.

Full unabridged entry-by-entry history (every bug's root cause, every file
touched, every verification step) for everything summarized below lives in
app-planning/archive/progress-phases-1-8.txt (phases 1-8),
app-planning/archive/progress-phases-9-10.txt (phases 9-10),
app-planning/archive/progress-phases-11-13.txt (phases 11-13), and
app-planning/archive/progress-phases-14-15.txt (the v2.2.1 patch work,
phases 14 and 15). The original PRDs that drove this work are in
app-planning/archive/ (PRD.md, Reson8_Evolutions_PRD.md,

  (Server/Channel/User/Role/Message), flat→nested channel-tree builder.

PHASE 2 — The Voice Bridge (mediasoup)
  mediasoup SFU integrated; full 6-step WebRTC handshake (GET_ROUTER_
  CAPABILITIES → CREATE_WEBRTC_TRANSPORT → CONNECT_TRANSPORT → PRODUCE →
  CONSUME → RESUME_CONSUMER); two-way audio; mute/deafen controls.
  Notable fixes: Electron mic-permission auto-grant, silent-audio race
  (queued consumption until recv transport ready), ICE announced-IP
  defaulting, detached-Audio()-element silence (must attach to DOM),
  deafen-toggle state flag, voice-control UI overflow.

PHASE 3 — Relational Logic & Hierarchy
  DB seeding (default server/channels/roles), channel CRUD over Socket.io,

PHASE 13 FOLLOW-UP — v2.2.1 patch (30/08/2026, 4 entries)
  - Code signing removed from the client build pipeline (the signed v2.2.0
    installer broke auto-update on Windows with "not signed by the
    application owner"): the signing wrapper/env-loader scripts were
    deleted, and `main.ts` now overrides `NsisUpdater`'s
    `verifyUpdateCodeSignature` (Windows only) with a verifier that always
    resolves `null`. Root cause: electron-updater checks each downloaded
    update's Authenticode publisher against the publisher name baked into
    the CURRENTLY-INSTALLED app's own `app-update.yml`, so a client built
    while still signed kept rejecting legitimate unsigned updates. Must be
    removed again if signing is ever reintroduced.
  - AI noise cancelling "Couldn't enable noise cancelling" in packaged
    builds took THREE separate fixes behind one identical generic toast —
    found only by driving the real app over the DevTools protocol, not by
    guessing: the CSP blocked the local `fetch()` of the vendored WASM
    (`connect-src` needed `file:`); a bare-specifier `dynamicImport(
    "pkg")` never worked in any environment (Blink resolves only real
    URLs — resolve to a `file://` URL via `require.resolve()` first); and
    the CSP `script-src` needed `blob:` for the Blob-built AudioWorklet
    module. All now standing gotchas in root CLAUDE.md.
  - v2.2.1 release: combined release notes (so users landing straight on
    v2.2.1 still see v2.2.0's features — the What's New modal only fetches
    the exact running tag), and macOS added to `release:all`.

PHASE 15 — Rich Chat & Sturdier Connections (PRD 15.x — 11 items from
app-planning/nextsteps.txt, reached v2.4.0)
  - Stale-socket race (PRD 15.1, confirmed 5-for-5 from the server log): a
    reconnecting user has an old half-open socket and a new one at once;
    the old one's late `disconnect` ran userId-keyed cleanup that killed
    the LIVE socket's voice session (a second drop ~12s later) and, via an
    uncancelled grace timer, deleted its presence (user in a channel but
    absent from the online list). Fixed with a `SocketOwnership` registry
    (`services/socket-ownership.ts`): join claims ownership and retires
    the displaced socket, `disconnect` ignores non-owners, and the grace
    timer re-checks `hasOwner()`. PRD 15.2 concluded the underlying drops
    were connectivity-side (half-open connections from the network path)
    and unfixable in-app, left the Socket.io ping settings alone, and
    added diagnostics (connect address, disconnect transport/lifetime,
    the disconnect reason and reconnect duration in the Server Log tab)
  - Small fixes/chores: own voice halo now gated on the mic actually
    transmitting (not muted/deafened, PTT held) (15.3); a disabled — not
    hidden — Ban button on your own User Management row, server self-ban

    measured 9.8:1 contrast via `--pin-*` tokens (15.5); window size,
    position and maximized state persisted by a hand-rolled
    `window-state.ts` validated against current displays (15.6)
  - Windows re-launch freeze (15.7) — hypothesis-driven, never reproduced:

    disabled on win32, and one `showMainWindow()` helper (with state

  - Google Noto Color Emoji bundled as a vendored web font so emoji match

  - Image viewer rebuilt (15.9): icon toolbar (zoom, copy image, copy

--- Entry: 07/10/2026 ---

Feature/Fix: PRD 16.1 — "Don't warn me again" for NSFW channels

  Problem: Opening an NSFW text channel always showed the confirmation modal,
  even after the user had already accepted it many times, and even when
  re-focusing a tab that was already open. Users asked to be able to dismiss
  the warning for good.

  Solution: The NSFW modal now has a "Don't warn me again for NSFW channels"
  checkbox, and a new "Content" section in Settings -> Application has a
  "Warn before opening NSFW channels" toggle to turn the warning back on.
  The preference is one global per-install flag (decided with the user:
  covers all NSFW channels, not one channel).

  Client Changes:
    - renderer.ts: isNsfwWarningEnabled()/setNsfwWarningEnabled() accessors
      (try/catch around localStorage; anything other than an explicit "true"
      dismissal means warn, which is also the fallback when storage is
      unavailable).
    - handleChannelClick(): the NSFW branch now prompts only when
      node.isNsfw && isNsfwWarningEnabled() && !chatTabs.has(node.id). An
      already-open NSFW tab was confirmed when it was opened, so re-focusing
      it from the tree no longer re-prompts.
    - The checkbox is reset to unchecked every time the modal opens. The
      tick is persisted only when Continue is pressed; Cancel and backdrop
      close discard it.
    - openSettingsPanel() re-syncs the Settings toggle from storage on every
      open, since the modal can change the value while Settings is closed.
      The toggle shows "checked = warn" (inverse of the stored key) and
      takes effect immediately on change.
    - index.html: checkbox row in #nsfw-confirm-modal with a new
      .modal-check-row style; "Content" section + #chk-nsfw-warn toggle row
      in the Application panel (PRD 16.2 adds its row to the same section).

  localStorage Keys:
    reson8-nsfw-warning-dismissed = "true" when the warning is dismissed
    (key absent = warn, the default)

  Key Files Modified:
    apps/client/src/renderer/index.html
    apps/client/src/renderer/renderer.ts

  Verification:
    npx tsc --noEmit in apps/client passes. No server or shared-types
    change. UI behavior not exercised by Claude; manual testing by the user
    (checklist in PRD 16.1).

  Next Step: PRD 16.2 — optional image blurring in NSFW channels.


--- Entry: 07/10/2026 ---

Feature/Fix: PRD 16.2 — Optional image blurring in NSFW channels (per user)

  Problem: Every image in an NSFW text channel was always blurred behind a
  "click to reveal" overlay, with no way for a user who doesn't want that to
  turn it off.

  Solution: A per-user toggle, "Blur images in NSFW channels", in Settings ->
  Application -> Content (the section created by PRD 16.1). On by default,
  which keeps today's rendering exactly. Off shows NSFW-channel images like

Feature/Fix: PRD 16.4 — Mute text channels (per user, client-side)

  Problem: On busy servers a lot of text channels with unread dots clutter the

  channels they don't care about.

  Solution: Any user can right-click a text channel and choose "Mute Channel" /

  Client Changes:
    - Menu: the mute item is first in the channel context menu, followed by a

      highlight.

      suppressed (renderChannel skips the .unread class/dot for muted

    - setChannelMuted() persists, then applyChannelMuteState() does a targeted

Feature/Fix: PRD 16.6 — Group consecutive messages, header layout, HH:MM timestamps

  Problem: Every message was an independent inline line ("HH:MM:SS nick text")
  with its own nickname, seconds-resolution timestamp and margins, so busy
  chats were cluttered with repeated nicknames.

  Solution: Discord-style layout (user-approved). Each message has a header
  line (nickname + HH:MM) and its text on its own line(s) below. A message
  from the same author within 5 minutes of the FIRST message of the current
  group becomes a "continuation": no header, tight spacing. Applies to
  channel and DM chats; the Server Log is untouched.

  Client Changes:
    - DOM: both builders now share buildMessageShell(): .chat-msg >
      .msg-header (.msg-nick + .msg-time) + .msg-body (.msg-text +
      .msg-edited), with data-created-at. The header is always rendered and
      hidden by CSS on `.msg-continuation`, so regrouping is only a class
      toggle.
    - Rule: shouldGroupMessage() is a pure function — same author, createdAt
      not before the previous message, and createdAt minus the GROUP's first
      message's time under GROUP_WINDOW_MS (5 min). Any non-.chat-msg sibling
      between two messages (date divider, "Unread Messages" separator,
      sentinels) breaks the group. A reply (data-is-reply="1", set by PRD
      16.11) always opens its own group; that condition is a no-op until then.
    - applyGrouping(el) recomputes one element from its previous sibling and
      returns whether it changed (data-grouped, data-group-start, classes).
      regroupFrom(startEl) always recomputes the start and keeps cascading
      only while elements actually change, which bounds the work.
    - Where it runs: append (renderChatMessage/renderDmMessage, covering
      initial load, live messages, jump/rebuild) calls applyGrouping right
      after insertion; prependOlderMessages() calls regroupFrom after
      inserting the page, which also repairs the junction with the
      previously-first message (inside the scroll-anchor measurement, so
      scroll position stays correct); removeMessageElement() regroups from
      the next message after a delete (a removed head promotes the next line;
      removing an in-between message can merge two runs).
    - Time: formatMessageTime() = toLocaleTimeString with hour+minute only
      (respects the OS 12/24h preference). The header time's tooltip, and a
      continuation's tooltip, show the full date and time. The continuation
      tooltip is set on the whole message element rather than on .msg-body,
      because an image-only continuation has an empty body that can't be
      hovered. The Server Log's own timestamps are a separate path, unchanged.
    - "(edited)" moved from after the time to the end of .msg-body
      (ensureEditedLabel(), used by the edit and edit-broadcast paths), and is
      hidden via :has() while the inline edit textarea is open.
    - Spacing: group start margin-top 8px (0 right after a sentinel, date
      divider or unread separator); continuation margin-top -2px to cancel
      the container's flex gap. Reactions need no special handling: PRD 16.5
      made the strip take space only when it has reactions.
    - Solo-emoji messages, Markdown block/inline text, long-message
      truncation and link previews operate on .msg-text / the message
      element as before; block text lost its old margin-top since text is now
      always below the header.

Feature/Fix: PRD 16.7 — Emoji autocomplete while typing :name

  Problem: Emoji could only be inserted through the picker. Custom emoji could
  be typed as :name: but only if the user remembered the exact name, and
  Unicode emoji had no typed form at all.

  Solution: Typing ":" followed by a letter in the chat box opens a floating
  card just above the colon (per print_discord_emoji_autocomplete.png) with
  emoji on the left and :name: on the right, covering both custom and Unicode
  emoji. It filters as the user types and closes on no match, a closing colon,
  whitespace, blur, tab switch, send, or the emoji picker opening.

  Client Changes:
    - Trigger: /(?:^|[\s([{"'])(:([a-zA-Z][a-zA-Z0-9_+-]{0,31}))$/ against the
      text before the caret, so "http://x", "10:30" and "a:b" never trigger.
      Group 1 is ":query", group 2 is "query". Ignored during IME composition.
    - Search (searchEmojiForAutocomplete): ranked name prefix, name-word
      prefix, keyword prefix (how ":laug" finds 🤣, like the reference's
      :rofl:), then substring; ties favour custom emoji, then shorter names;
      max 10. The Unicode index is built once lazily; the custom list is read
      live. toEmojiSnakeName() is now shared with emojiShortName() (reaction
      card) so both name an emoji identically.
    - Card: one shared #emoji-autocomplete element (header "Emoji matching
      :query", rows with glyph/<img> + name, role=listbox/option with
      aria-activedescendant on the textarea). Opens upward, left-aligned to the
      colon, clamped inside the window, max-height fitted to the space above.
      The colon's coordinates come from a local mirror-div helper
      (getTextareaCharCoords) instead of a dependency (no bundler).
    - Keys: Up/Down move (wrapping), Enter/Tab select WITHOUT sending (the
      handler runs first in the chatInput keydown), Escape closes only the card
      (stopPropagation, so PRD 16.11's reply cancel won't also fire),
      Shift+Enter closes the card and inserts a newline. Mouse: hover
      highlights, mousedown is prevented so the textarea keeps focus.
    - Selecting inserts the emoji CHARACTER for Unicode (only custom :name:
      text renders as an emoji) and :name: for custom, plus a trailing space
      unless whitespace already follows. Typing the closing ":" of a complete
      Unicode name (":red_heart:") converts it in place; custom names are left
      as typed since they already render.
    - State/element refs live next to chatInput at the top of the file, not
      beside the logic, because switchTab()/sendChatMessage() call
      closeEmojiAutocomplete() and can run before the later section evaluates
      (a const TDZ otherwise).
    - Out of scope: the inline message-edit textarea and the picker's own
      search box (the module takes the textarea from chatInput only).
